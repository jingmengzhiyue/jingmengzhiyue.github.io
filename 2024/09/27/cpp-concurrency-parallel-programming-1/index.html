并发程序难写，往往不在于接口多，而在于必须回答清楚三个问题：谁拥有数据，谁可以修改它，什么机制保证另一个线程安全地使用它？ 本文围绕这三个问题梳理 C++ 并发与并行编程，代码以 C++20 标准库为核心，不使用第三方并发库。

这是系列的上篇，依次介绍执行模型、编译环境、线程生命周期与参数传递、共享状态与互斥锁、多锁与死锁、条件变量，以及 promise、packaged_task、async 等任务结果通道。下篇继续讨论原子变量与内存序、C++20 的取消与协调工具和工程实践，并实现一个完整的任务处理器。

文中标为“示例 N”的代码都是可以独立编译的完整程序，注释中的 @brief 说明用途，@param / @return 说明接口，@pre / @note / @warning 说明前提与并发边界；标为“片段”的代码只用于局部说明。

1. 先理解程序怎样同时推进

1.1 并发与并行

一个线程是一条执行指令的路径。一个进程可以包含多个线程：线程各有调用栈，但通常共享进程内的对象和地址空间。栈上的对象也可能通过引用被其他线程访问，“局部变量”不等于“线程私有”。

**并发（concurrency）**指多个活动在同一段时间内推进，可以交错执行，也可以同时执行。单核处理器也可以通过调度实现并发。**并行（parallelism）**指多个活动在同一时刻执行，通常需要多个执行资源。

例如，一名厨师轮流煮面和切菜是并发；两名厨师分别做这两件事可以是并行。并发主要帮助组织独立活动，并行主要帮助利用多个执行资源；两者经常一起出现，但不互相等同。

图 1-1：上半图示范单核上的并发交错，下半图示范双核并行；并发并不限于单核，多个并发活动也可以并行执行。

不能假设线程创建后立刻执行，也不能根据源代码中两个线程的排列顺序推断谁先完成。操作系统调度、编译器优化和硬件执行都会影响观察到的行为。

1.2 同步、异步、阻塞、非阻塞是其他维度

这些术语在不同领域略有差别，本文采用以下语境：

维度要回答的问题含义与例子
并发 / 并行活动怎样推进？一段时间内共同推进 / 同一时刻执行
同步 / 异步怎样取得操作的完成结果？调用流程直接得到完成结果 / 启动与取得结果分开
阻塞 / 非阻塞尚不能完成时，当前调用是否等待？等待条件满足 / 立即报告当前状态或暂时无法完成

图 1-2：两组维度互相独立，可以自由组合；异步不代表非阻塞，同步也不代表一定等待。

发起异步任务可以很快返回一个结果句柄，但随后对句柄调用 get()，仍可能阻塞。同步的 try_lock() 直接报告本次尝试的结果，不等待锁变得可用。异步接口不必为每个任务创建新线程。还要注意：std::async 也支持 deferred（延迟执行）策略，但这种策略不会后台执行任务，而是在首次非定时等待时由等待线程执行（§7.4）。

还要区分“接口不阻塞”和算法理论中的进度保证：lock-free 大意是系统整体持续取得进展，wait-free 要求每次操作在有界步骤内完成。循环调用一个非阻塞接口，不会自动得到这些保证。

1.3 正确性包括安全性和活性

  • 安全性：不越界、不访问已销毁对象、不破坏数据规则、不发生数据竞争。
  • 活性：任务最终有机会完成，等待存在退出路径，不永久互相等待。
  • 性能：在正确的前提下，延迟、吞吐量和资源消耗是否满足需求。

“跑了十次都正确”只观察了少量执行。并发程序必须依据同步规则说明为什么所有允许的交错都安全。

3. 线程的第一条规则：先管理生命周期

3.1 std::thread 启动执行，join() 收回执行

std::thread 构造成功后，新的执行线程调用指定函数。线程对象是执行线程的管理句柄：不能复制，可以移动。线程函数已经返回，不代表句柄已经不需要回收。

 * @throws std::system_error 资源不足等原因无法创建线程时；此时没有新线程产生。
 * @note 保存可调用对象或实参时，复制或移动构造抛出的异常也会传给调用方。
 * @note 构造成功即启动新线程：不存在“先创建、后启动”的两步接口。
 */
std::thread worker(f, arg1, arg2); // worker 只是管理句柄；新线程在构造成功后已启动；何时获得调度不确定

f 可以是普通函数、lambda、函数对象，也可以是成员函数指针——此时第一个实参是调用对象（对象副本、指针或 std::ref 包装）。无法启动新线程（如资源不足）时抛出 std::system_error；保存可调用对象和实参时，其复制或移动操作也可能抛出其他异常。这些异常发生在构造线程的调用方，构造未成功时不会留下需要调用方 join 的新线程。实参先按 §3.3 的规则复制或移动进内部存储，再以 INVOKE 方式调用 f。线程函数的返回值被直接丢弃：要把结果带回，需要使用引用参数（示例 1）、受保护的共享状态（§4）或 future 结果通道（§3.4 简介，§7 完整展开）。

其余构造形式：默认构造不关联任何线程；拷贝构造与拷贝赋值被删除（句柄唯一拥有）；移动构造与移动赋值转移管理权，源对象不再关联线程（移动赋值还须注意目标是否已 joinable）。

/**

 * @brief std::thread 的值传递与 std::ref 显式引用传递。
 * @details 工作线程计算 input 的平方，通过引用写回主线程的 result；主线程用 join()
 *          回收线程后再读取结果，依靠 join 建立的同步关系避免数据竞争。
 *          预期输出 49。对应正文 §3.1。
 */
#include <cassert>    // assert：验证计算结果
#include <functional> // std::ref：把引用包装成可复制的 reference_wrapper
#include <iostream>   // std::cout：输出最终结果
#include <thread>     // std::thread：创建并管理执行线程

/**
 * @brief 计算 input 的平方并写入 output。
 * @param[in] input 输入值，按值拷贝进线程函数实参存储，与调用方变量再无关联。
 * @param[out] output 结果写出位置；调用方必须保证其寿命覆盖整个线程执行期。
 * @pre input 的平方可表示为 int；本例固定为 7，不处理任意整数的溢出。
 * @note 与主线程之间靠 join() 建立同步，因此本例无需互斥锁。
 * @warning 本函数要求 int&；直接传 result 的衰减副本无法作为该引用实参，线程构造不通过编译。
 * @see 正文 §3.3“参数、捕获与所有权”
 */
void calculate(int input, int& output) {
    output = input * input; // 在工作线程中执行；写的是主线程拥有的 result
}

/**
 * @brief 程序入口：启动一个工作线程并安全取回结果。
 * @return 隐式返回 0，表示正常结束。
 */
int main() {
    int result = 0; // 主线程拥有的结果变量，寿命覆盖整个 worker 执行期
    // 7 按值保存进线程实参；std::ref 显式要求把 result 按引用传给线程函数。
    std::thread worker(calculate, 7, std::ref(result));
    worker.join(); // 等待线程结束；join 返回后读取 result 才有同步保证
    assert(result == 49); // 此处读到的一定是写入完成的 49
    std::cout << result << '\n'; // 输出 49
}

输出 49。主线程在 join() 之前不读取 result，且 result 一直存活。线程完成与成功的 join() 返回之间有同步关系，所以这里不需要额外的互斥锁。

参数为何需要 std::ref、它与 Lambda 引用捕获有什么区别，见 §3.3。

joinable() 表示句柄仍关联某个线程，不表示它“正在运行”。默认构造、被移走、成功 join() 或 detach() 后的对象不再 joinable。join() 和 detach() 都要求对象仍然 joinable；非 joinable 时调用会报告 std::system_error，不能重复回收或分离。join() 还不能等待当前线程自身。移动后源对象不再 joinable，目标接管原关联；对仍 joinable 的 std::thread 做移动赋值也会调用 std::terminate()。对同一个线程句柄的操作不自动互相同步，应由一个管理者负责。

生命周期红线 std::thread 析构时如果仍然 joinable，会调用 std::terminate() 终止程序。这是标准规定的错误处理策略：避免隐式等待掩盖阻塞，也避免隐式分离放任引用对象寿命失控；必须在析构前明确处理关联。

示例 1 中从成功构造到 join() 之间没有可能抛异常的业务操作；实际复杂代码优先使用 RAII。

3.2 RAII 与 std::jthread

RAII 的做法是把资源的释放绑定到对象析构：离开作用域，包括异常展开时，自动执行清理。锁守卫负责解锁，线程管理对象负责回收线程。

C++20 的 std::jthread 析构时，如果仍然 joinable，会先请求停止，再 join()。请求停止只是通知；线程是否响应取决于线程函数，下篇 §9.1 专门介绍。

与上文 std::thread 的联系和区别。严格说，它们是 <thread> 中的两个类，而不是同一个类的两个成员接口。两者都管理执行线程，都只能移动、不能复制；jthread 不是另一种调度模型，也不是 thread 的子类，二者不能直接相互转换。可以把 jthread 理解为提供了“自动回收 + 协作停止”的线程管理类，但不要据此假定它的具体内部实现。

对比项std::threadstd::jthread
标准版本C++11 起C++20 起，还需标准库实现支持
析构时仍 joinable调用 std::terminate()；必须事先处理线程关联先 request_stop()，再 join()；可能阻塞
停止机制没有内置停止请求接口；需另行设计退出协议内置停止状态与请求接口，线程仍须主动配合
显式等待join() 等待线程结束同样支持 join()，且该调用本身不请求停止

以上行为可对照 C++20 草案的 thread 类与 jthread 类。

分别适用于什么情况？

  • C++20 新代码通常优先考虑 jthread：线程由某个作用域或对象拥有，退出前需要回收，尤其是中途可能抛异常或提前返回的场景。不需要取消的有限任务也可以使用它，下面的示例 2 就没有接收停止令牌。
  • 需要协作停止的长期工作线程适合 jthread：例如处理循环收到停止请求后清理并返回；但计算和等待路径都必须设计退出方式，详见下篇 §9.1。
  • 兼容 C++11/14/17、旧库接口要求 std::thread，或已有完整线程管理封装时，可使用 thread：应由现有封装或 RAII 守卫覆盖正常与异常路径，而不是只在函数末尾写一次 join()。C++20 中也能把独立的 stop_source / stop_token 配合 thread 使用，协作停止并非 jthread 专属。

自动回收不等于自动解决并发问题 jthread 不能强制终止线程；工作若永久等待或不退出，析构也可能永久等待。不要持有工作线程需要的锁去等待它。需要明确等待时机时，仍可提前显式 join()，不必因此改用 thread。两者都支持 detach()，但分离后不再由该对象自动回收，不能把分离当作避免阻塞的通用办法。jthread 也不会自动保护共享数据、延长被引用对象的寿命或转送线程异常。

jthread 的接口一览。它的启动时机、实参传递和 joinable 状态规则与 std::thread 相同（§3.1、§3.3），差异集中在自动回收与协作停止：

/**
 * @file example02.cpp
 * @brief std::jthread 的 RAII 自动回收，以及用 std::exception_ptr 跨线程传递异常。
 * @details 工作线程抛出并自行捕获业务异常，把异常对象存入主线程的 exception_ptr；
 *          jthread 离开作用域时若 joinable，先 request_stop() 再 join()，主线程随后处理异常。
 *          预期输出 "worker failed"。对应正文 §3.2。
 */
#include <cassert>   // assert：验证异常确实被传回
#include <exception> // std::exception_ptr / std::current_exception / std::rethrow_exception
#include <iostream>  // std::cout：输出异常消息
#include <stdexcept> // std::runtime_error：本例使用的业务异常类型
#include <thread>    // std::jthread：C++20 带自动回收的线程句柄

/**
 * @brief 程序入口：演示异常如何跨越线程边界传回主线程。
 * @return 隐式返回 0。
 * @note error 声明在 worker 外层：先构造、后销毁，保证线程执行期间引用始终有效。
 */
int main() {
    std::exception_ptr error; // 主线程拥有的异常句柄：工作线程写入，主线程读取
    {
        // error 的寿命覆盖整个 worker，因此引用捕获是安全的。
        /** @brief 工作线程入口：捕获任意异常并交给主线程。 @note error 的寿命由外层作用域保证。 */
        std::jthread worker([&error] {
            try {
                throw std::runtime_error("worker failed"); // 模拟工作线程中的业务失败
            } catch (...) {
                // 异常不能自动跨越线程边界；先保存为可重新抛出的异常对象。
                error = std::current_exception();
            }
        });
    } // worker 析构：先 request_stop（本例线程函数不检查，无实际效果），再 join 等待完成

    assert(error); // 非空表示工作线程确实保存了异常
    try {
        std::rethrow_exception(error); // 在主线程重新抛出保存的异常
    } catch (const std::runtime_error& e) {
        std::cout << e.what() << '\n'; // 输出 "worker failed"
    }
}

输出 worker failed。这里只有一个线程写入 error，主线程在回收后读取，因此不需要用锁保护它。catch (...) 在此有明确目的：将任意工作异常交给调用者处理，并非静默忽略。

线程入口函数中未捕获的异常会导致 std::terminate()；在创建线程的代码外面加 try/catch，只能捕获创建时的失败，捕获不到另一个线程执行时抛出的异常。jthread 不会自动转送异常。后面的 future 能更自然地承担结果与异常通道。

3.3 参数、捕获与所有权

构造线程时，普通参数会按 std::decay 后的类型（去掉引用与顶层 cv 修饰，数组和函数名退化为指针）复制或移动到内部存储，再用于调用函数。std::ref(x) 不复制 x，也不延长 x 的寿命；std::cref(x) 是对应的 const 引用包装，适合线程只读共享数据的场景。

3.3.1 普通参数与引用包装器

示例 1 的 calculate 是普通函数：参数列表决定它接收什么；std::thread 决定这些实参怎样先保存、再交给函数。std::ref / std::cref 只改变传参语义，不提供加锁或自动续命。

为什么这里必须写 std::ref(result)？ std::thread 构造时会先把实参复制或移动到自己的内部存储，保存的是去掉引用修饰后的类型（§3.3）。如果直接写 result，内部存下的就是一份 int 副本；调用 calculate 时会以右值形式传递它，不能绑定到函数要求的 int& 形参，线程构造在编译期就会失败。

std::ref(result) 不复制 result，而是把它包装成 std::reference_wrapper<int>：包装器本身可以安全地复制进内部存储，调用线程函数时又能隐式转换回 int&，于是线程函数拿到的仍是指向主线程那个 result 的引用。也就是说，std::ref 解决的是“实参必须先复制进存储”与“函数要求按引用接收”之间的矛盾；它既不转移所有权，也不延长 result 的寿命，对象存活仍由调用方负责。构造规则见 C++20 草案的 thread 构造函数。

std::reference_wrapper<T> 常用的两个引用访问方式是：成员函数 get() 显式返回 T&；隐式转换运算符 operator T& 让它能直接用在需要 T& 的地方。std::ref(t) 保留原对象的 const 属性：普通 T 对象得到 reference_wrapper<T>，const 对象得到 reference_wrapper<const T>。std::cref(t) 提供 const 引用访问，选择原则和平时选 T& 还是 const T& 形参一致。

3.3.2 Lambda：捕获是保存环境，参数是调用时输入

Lambda 表达式会创建一个闭包对象，可以理解为“带着所需数据的可调用对象”。写法为 [捕获列表](参数列表) mutable -> 返回类型 { 函数体 }；mutable 和返回类型按需省略。捕获在创建闭包时发生，形参在调用闭包时取得；闭包再按普通可调用对象的规则复制或移动进线程。

写法保存什么并发时要证明什么
[]不捕获外部局部变量；仍可用形参、全局对象等不捕获不等于线程安全，全局共享状态仍需同步
[x]创建闭包时的 x 副本后续修改原 x 不改变这份副本；复制动作本身也不能与写 x 冲突
[&x]对原 x 的引用对象活到最后一次访问；并发冲突访问另需同步
[=] / [&]对需要隐式捕获的局部变量默认按值 / 按引用捕获不会无条件捕获作用域中所有变量；线程入口优先显式列出依赖
[x, &result]输入快照与输出引用输入独立；结果在 join 后读取，不把引用当成锁
[p = std::move(p)]初始化捕获，将资源移入闭包（C++14 起）原所有者不再使用已移走的资源；闭包用 std::move 移入线程
[this]当前对象的指针不拥有当前对象；对象不能在线程使用期间销毁
[*this]当前对象的副本（C++17 起）类型必须可复制；指针等成员仍按各自的复制语义处理

默认情况下，闭包的调用运算符是 const，所以不能直接修改按值捕获的普通副本；加 mutable 后可以修改该副本，不会因此修改原变量。引用捕获仍可以修改原对象，无需为此添加 mutable。同一个可变闭包若被多个线程共享调用，仍可能发生数据竞争；mutable 不是同步机制。

/**
 * @file example03.cpp
 * @brief 用同一个平方计算对比 Lambda 的值捕获、引用捕获与移动捕获。
 * @details 每个工作线程均在内层作用域结束时回收；主线程只在回收后读取输出。
 *          输入固定为 7、8、9，乘法不会溢出。预期输出 "49 64 81 81"。

#include <cassert>
#include <iostream>
#include <memory>
#include <thread>
#include <utility>

/**
 * @brief 逐步验证捕获方式；不依赖线程先后获得调度的顺序。
 * @return 正常结束时隐式返回 0。
 * @note 三个结果对象先于线程构造，且只在对应线程结束后由主线程读取。
 */
int main() {
    int input = 7;
    int snapshot_result = 0;
    {
        /** @brief 捕获当时的输入 7，引用写出结果；不读取主线程后续的 input。 */
        std::jthread worker([input, &snapshot_result] {
            snapshot_result = input * input;
        });
        input = 9; // 线程访问的是副本，因此这里修改原对象没有冲突。
    }
    assert(snapshot_result == 49 && input == 9);

    /**
     * @brief 修改捕获副本，再返回其平方；本闭包仅由主线程调用。
     * @return 第一次调用返回 8 的平方 64。
     * @note 初始化捕获把内部 input 设为 7，与外部同名变量是不同对象。
     */
    auto next_square = [input = 7]() mutable {
        ++input;
        return input * input;
    };
    const int mutable_result = next_square();
    assert(mutable_result == 64 && input == 9);

    int reference_result = 0;
    {
        /** @brief 引用读取原 input 并写回结果；主线程在此期间不改、不读相关对象。 */
        std::jthread worker([&input, &reference_result] {
            reference_result = input * input;
        });
    } // join 建立同步；仅有引用捕获并不足以保证安全。
    assert(reference_result == 81);

    auto data = std::make_unique<int>(9);
    int owned_result = 0;
    /** @brief 独占拥有移入的整数，引用写回平方；解引用不需要 mutable。 */
    auto task = [p = std::move(data), &owned_result] {
        owned_result = *p * *p;
    };
    assert(!data); // unique_ptr 已移入闭包，主线程不能再解引用它。
    {
        std::jthread worker(std::move(task)); // 含 unique_ptr 的闭包不可复制，显式移动。
    }
    assert(owned_result == 81);
    std::cout << snapshot_result << ' ' << mutable_result << ' '
              << reference_result << ' ' << owned_result << '\n';
}

输出 49 64 81 81。[input, &result] 与示例 1 的 calculate(input, std::ref(result)) 表达同一种数据安排：输入独立保存，输出引用调用者对象，join 后读取。改成 [](int value) { return value * value; } 则是在调用时接收输入；把它交给 std::thread 仍会丢弃返回值，§3.4 将用 async 接收返回值。

/**

 * @see 正确写法见示例 2：用内层 jthread 作用域保证先等待、后销毁数据（正文 §3.2）。
 */
void start_bad() {
    int local = 0; // 局部对象：函数返回即销毁，寿命不随分离线程延长
    /** @brief 故意引用局部对象的分离线程入口。 @warning 对象可能在线程写入前已销毁。 */
    std::thread([&local] { local = 42; }).detach(); // 错误：[&local] 留下悬空引用；detach 放弃通过此句柄等待
}

detach() 解除管理句柄和执行线程的关联，既不等待完成，也不延长引用对象的寿命。如果线程在函数返回后访问 local，就是访问已结束生命周期的对象，属于未定义行为；恰好提前执行完时可能看起来正常。

修复是像示例 2 一样用内层 jthread 作用域保证先等待、后销毁数据，或真正转移任务需要的数据所有权。即使改成值捕获解决了悬空引用，分离任务的退出、错误处理、程序关闭问题仍然存在，因此应避免裸 detach()。

声明顺序也很重要：局部对象按构造顺序的逆序销毁。共享数据、互斥锁、条件变量应先构造，引用它们的线程后构造。自动回收不能解决死锁；析构时持锁等待一个需要这把锁的线程，同样会卡住。 C++20 草案的 jthread 规定 给出了停止请求与回收的顺序。

3.4 用 async/future 取回线程的返回值

§3.1 已经说明，线程函数的返回值被直接丢弃；示例 1 的对策是主线程备好结果变量，再用 std::ref 把它的引用传给线程函数，由工作线程“写回来”。还有一条更直接的路：不写回变量，而是让任务把返回值存进一个双方都能看到的结果通道。C++20 草案的 async 规定 中 std::async 负责启动任务并自动接好这条通道，std::future 是通道在调用方一侧的“提货单”。这套机制的完整形态（共享状态、promise、packaged_task、shared_future 与析构规则）在 §7 展开，本节先给出足以覆盖“算个值回来”这一常见需求的组合。

核心是三个动作：显式传 std::launch::async 启动任务，保存返回的 future，最后用 get() 等待并取回值或异常。启动任务不保证 CPU 同时执行它们，也不保证它立即获得调度。

#include <cassert>   // assert：验证取回的值与示例 1 一致、future 状态转换正确
#include <chrono>    // std::chrono::milliseconds：模拟耗时的时长单位
#include <future>    // std::async / std::launch / std::future：任务启动与结果通道

/**
 * @brief 计算整数的平方，代表一段值得单独交给其他线程执行的耗时任务。
 * @param[in] input 本例仅传入 7 或 -5；非负合法值须保证平方可表示为 int。
 * @return input 的平方；写入 async 创建的共享状态，供 future::get() 取回。
 * @throws std::runtime_error input 为负数时抛出；异常对象经共享状态传回主线程。
 * @note 返回值存进共享状态而不是写回某个变量，这是与示例 1 引用写回的本质区别。
 */
int square(int input) {
    std::this_thread::sleep_for(std::chrono::milliseconds(50)); // 模拟真实耗时，让主线程有机会先做自己的事
    if (input < 0) { // 示例业务规则：只接受非负数（负数在数学上同样有平方），用异常报告错误
        throw std::runtime_error("no square for negative input"); // async 把异常对象存入共享状态
    }
    return input * input; // 返回值自动写入共享状态，主线程稍后经 future 取走
}

/**
 * @brief 程序入口：启动异步任务、取回返回值、演示异常传回。
 * @return 隐式返回 0，表示正常结束。
 */
int main() {
    // launch::async：强制立即以新执行线程语义启动 square(7)；7 按值复制进共享状态。
    // 返回的 future 是结果的“提货单”；任务何时真正获得调度不确定，但必然先于 get() 的返回而完成。
    std::future<int> good = std::async(std::launch::async, square, 7);

    std::cout << "task launched; main thread free\n"; // 任务运行期间主线程做自己的事；双方不共享数据，无需加锁

    const int result = good.get(); // 阻塞等待任务完成并取回 49；get 返回与任务完成之间有同步关系
    assert(result == 49); // 与示例 1 的结果一致：引用写回能做到的，future 直接以返回值给出
    std::cout << result << '\n'; // 输出 49

    assert(!good.valid()); // get 之后 future 不再关联共享状态；对它再次 get 是未定义行为

    std::future<int> bad = std::async(std::launch::async, square, -5); // 第二个任务将抛出异常
    try {
        bad.get(); // get() 在主线程重新抛出共享状态里保存的异常对象
        assert(false); // 不应到达：square(-5) 必然抛出异常
    } catch (const std::runtime_error& e) { // 在主线程按普通同步代码的方式捕获
        std::cout << e.what() << '\n'; // 输出 "no square for negative input"
    }
    assert(!bad.valid()); // 与 good 对称：get 取走异常后 bad 同样不再关联共享状态
}

输出 task launched; main thread free、49、no square for negative input 三行，全部由主线程写出，顺序与线程调度无关。与示例 1 对照：计算目标与示例 1 相同，但无需预先提供共享输出变量、std::ref 或显式 join()——“算个值回主线程”被压缩成一行 std::async 加一行 get()。

先保存句柄，再取回结果 普通 future 的 get() 只能消费一次；valid() 只说明有关联状态，不说明任务已经完成。不要丢弃 async 返回的临时句柄，它的析构可能隐含等待。完整接口见 §7.1，执行策略和析构规则见 §7.4–§7.5。

如果任务只是算一个结果，先用本节的 async；如果需要长期工作线程、显式交付时机或队列调度，再使用 §7 的 promise / packaged_task 和下篇 §11 的任务处理器。async 不是 C++20 的通用线程池接口。

4. 共享可变状态为何危险

4.1 data race 与 race condition

**数据竞争（data race）**是 C++ 内存模型中的错误：不同线程对同一内存位置存在冲突访问，至少一个不是原子操作，又没有必要的 happens-before 顺序。常见情形是一个写、另一个读或写普通对象。数据竞争导致未定义行为。

**竞态条件（race condition）**是更广的逻辑问题：结果是否正确取决于事件的交错。即使每次访问都使用原子或锁，没有数据竞争，也可能出现逻辑竞态。

错误示例，请勿照搬（片段；count 为普通整数，初值 0）：

// 线程 A

volatile 不提供线程间的互斥或同步，不能修复这个问题。增加 sleep_for() 也不能建立同步关系。修复需要原子读改写，或将完整操作放进同一把锁保护的临界区。

另一种逻辑竞态：账户余额的查询和扣减分别加锁，两个线程都查询到“余额足够”，随后都扣减。每个单独方法可能没有数据竞争，但“检查并扣减”不是一个整体。应把整个业务规则放在一个临界区内。数据竞争定义可核对 C++20 草案的冲突访问与 happens-before。

4.2 mutex 同时提供互斥和同步

互斥锁 std::mutex 不会给某个变量自动贴上保护标签；程序员必须约定哪些数据由哪把锁保护，并让所有相关访问遵守约定。

它的两个作用：

  1. 互斥：同一时刻只有一个线程持有这把锁，从而让整个临界区不与另一个受保护临界区交错。
  2. 同步：一次解锁与之后取得这把锁的加锁操作建立同步，使先前临界区的写入能够被后续临界区安全观察。

与加锁直接相关的成员函数是三个：lock() 阻塞直至取得锁，try_lock() 尝试一次并立即报告成功与否，unlock() 释放锁且必须由持有线程执行；另有 native_handle() 返回平台原生句柄，供平台特定 API 使用，代价与 §3.1 的同名接口一样是失去可移植性。业务代码不应直接调用这些加锁成员：手工配对容易在异常或提前返回时漏掉 unlock()。这些成员是锁管理对象（§4.3）的底层接口，日常代码通过 RAII 守卫间接使用。std::mutex 默认构造即处于未持有状态，不可复制也不可移动。规定见 C++20 草案的 mutex 类。

 *          因此最终值确定为 20000。预期输出 20000。对应正文 §4.2。
 */
#include <cassert>  // assert：验证最终计数
#include <iostream> // std::cout
#include <mutex>    // std::mutex / std::lock_guard
#include <thread>   // std::jthread

/**
 * @brief 程序入口：两个线程并发累加同一计数器。
 * @return 隐式返回 0。
 * @note 本例故意每次都加锁以展示临界区语义；真实统计宜先局部累计再合并（见下篇 §10.2）。
 */
int main() {
    int count = 0;    // 共享计数器：并发期间用 mutex 保护；全部写线程 join 后可无锁读取
    std::mutex mutex; // 保护 count 的互斥锁；先于线程构造、后于线程销毁
    /** @brief 在同一 mutex 保护下累加；两个线程共享此任务引用的计数器。 */
    auto add = [&] {  // 累加任务：按引用捕获 count 与 mutex（二者寿命覆盖线程执行期）
        for (int i = 0; i < 10000; ++i) {
            std::lock_guard<std::mutex> lock(mutex); // 进入临界区：构造即加锁（RAII）
            ++count; // 从读取到写回都处于同一个临界区，不会被另一线程交错
        } // lock 析构并解锁，异常路径也遵循 RAII
    };
    {
        std::jthread first(add);  // 启动第一个累加线程
        std::jthread second(add); // 启动第二个累加线程
    } // 两个 jthread 在此析构并 join：全部写入完成后主线程才继续
    // 所有写线程已结束，这次读取不再需要持锁。
    assert(count == 20000); // 互斥 + 同步保证不丢更新：恰好 2 × 10000
    std::cout << count << '\n'; // 输出 20000
}

输出 20000。若主线程要在线程运行期间查看 count，也必须加同一把锁。仅锁写、不锁读，或者每个线程用自己的锁，都没有建立所需保护。

这个示例故意每次加锁以展示语义；真实统计更适合各线程先累计到局部变量，再合并，后面讨论原因。标准同步规定见 mutex requirements。

std::mutex 是非递归独占锁：同一线程不能重复加锁，解锁必须由持有者执行。std::lock_guard、std::scoped_lock 不可复制也不可移动；std::unique_lock 和 std::shared_lock 可移动、不可复制，移动转交的是锁所有权管理责任，不延长底层锁的寿命。移动守卫不改变底层互斥锁的持有线程：对于标准互斥锁，不能把已持锁的守卫交给另一线程解锁或析构；共享锁同样要由取得该共享所有权的线程释放。

    m.lock(); // 手工加锁：仅为演示 adopt_lock 的前提“当前线程已持有”
    {

    } // adopted 析构并解锁——手工 lock() 的配对义务已转交给守卫

 *          提前解锁与重新加锁；这是条件变量 wait 只接受它的原因（§6.1）。
 * @note std::timed_mutex 与 std::mutex 都是非递归独占锁；前者额外提供
 *       try_lock_for()/try_lock_until()，unique_lock 的限时加锁依赖这些能力，

 * @note 超时只是本次等锁的预算，不限制临界区执行时间，也不是实际返回的
 *       硬截止时间。仅第一次加锁限时，重新 lock() 仍可能无限等待。
 * @note unique_lock 可移动、不可复制。
 */
bool unique_lock_demo(std::timed_mutex& m, int& shared_data) {
    std::unique_lock<std::timed_mutex> lock(m, std::defer_lock); // 只关联 m，尚未持有
    if (!lock.try_lock_for(std::chrono::milliseconds(10))) { // 限时尝试：预算 10 毫秒，实际返回可能更晚
        return false; // 未持有锁：析构不会解锁，直接放弃本次操作
    }
    ++shared_data; // 临界区：此处 owns_lock() 为 true
    lock.unlock(); // 提前释放：去做不需要持锁的工作，缩短临界区
    // …不持锁的工作（期间 shared_data 可能被其他持锁者改变）…
    lock.lock(); // 重新加锁：业务前提必须重新检查，不能沿用 unlock 前的判断
    ++shared_data; // 第二段临界区
    return true; // 析构时仍持有锁 → 自动 unlock；异常路径同样 RAII
}

移动语义使 unique_lock 可以从函数返回“已加好的锁”，在同一线程内把锁管理责任交给调用者；release() 则只是放弃管理并返回底层锁的指针，不会解锁——这是 lock_guard 做不到的一类设计。代价是需要维护锁拥有状态，使用规则更复杂；实际开销取决于实现与优化，错误使用（如对未持有的守卫 unlock()）会在运行时抛 std::system_error 而不是编译期拦住。

 *       守卫转发版本见上面的 unique_lock_demo。
 */
bool timed_mutex_demo(std::timed_mutex& m, int& shared_data, std::chrono::milliseconds budget) {
    if (!m.try_lock_for(budget)) { // 相对时长形式：使用 budget 预算，含伪失败及返回延迟
        return false; // 未持有锁：业务放弃或稍后重试，不要有“再等等总能等到”的假设
    }
    ++shared_data; // 临界区：独占访问
    m.unlock(); // 手工配对（仅作演示；业务代码应让守卫析构来做，见 unique_lock_demo）

    const auto deadline = std::chrono::steady_clock::now() + budget; // 绝对时间点：用稳定时钟，不受系统时间调整影响
    if (!m.try_lock_until(deadline)) { // 尝试到 deadline 为止
        return false;
    }
    ++shared_data; // 第二段临界区
    m.unlock();
    return true;
}

典型场景：等待超过业务预算后允许放弃，或在超时后记录诊断信息。它不能承诺界面绝不卡顿，也不能保证周期任务按硬截止时间返回。普通后台代码默认 std::mutex 即可，确有超时需求再升级到 timed_mutex——实际成本取决于实现与负载，不应预设定时锁一定使用轮询或一定更慢。规定见 C++20 草案的定时锁要求。

4.4 一次性初始化：std::call_once

有些数据只需要在首次使用时初始化，例如一份全局配置。直觉上可能会写成“先检查，再初始化”，但多个线程可能同时通过检查，造成重复初始化；普通变量上的并发读写还会形成数据竞争。手工的双重检查锁定也不容易写对：即使一个线程看到“已初始化”，没有正确的原子操作和内存序，也不能保证它能看到完整的初始化结果。

使用 std::call_once 时，需要提供一个 std::once_flag 和一个初始化函数。对于同一个 flag，标准库保证：

  • 多个线程同时调用时，一个线程执行初始化函数，其他线程等待；
  • 初始化函数正常返回后，flag 被标记为完成，之后的调用不再执行初始化；
  • 其他正常返回的调用与这次初始化建立同步，因此可以安全读取已经发布的结果。

这里的“一次”指一次成功完成的初始化，不是“初始化函数只能进入一次”。如果初始化抛出异常：

  • 异常会传给实际执行初始化函数的调用者；
  • flag 不会被标记为完成，等待中的其他调用或后续调用可以重试；
  • 失败前已经产生的副作用不会自动撤销，重试时必须考虑这一点。

实际使用时，可以这样选择：

  • 需要跨调用点共享同一个初始化状态：使用 call_once，并确保每次传入同一个 flag。flag 不可复制、不可重置；需要一轮全新的初始化时，应使用新的 flag。
  • 只需要函数内的一份延迟初始化对象：通常优先使用局部 static。自 C++11 起，它的初始化同样线程安全，写法更简单。

4.5 先写不变量，再确定临界区

不变量（invariant）是操作前后必须保持的规则，例如余额非负、账户总额守恒、队列长度不超过容量。锁应保护完整规则：检查前提、计算并提交修改属于一次业务操作，单独给每个字段加锁不够。

设计时写出三件事：谁拥有对象；什么锁保护哪些状态；操作在哪个时刻完整生效。这个生效点常称为线性化点，例如库存扣减成功的 CAS、持队列锁完成入队。观察者也必须遵守协议：多字段一致快照需要同时保护这些字段，单个读取安全不代表组合结果一致。

    std::lock_guard<std::mutex> first(b);  // 线程 B 先持有 b
    std::lock_guard<std::mutex> second(a); // 若 A 已持有 a，形成环；RAII 本身不能破坏它
}

若 A 持有 a 等待 b，同时 B 持有 b 等待 a，两者永远不能继续。这个问题本身不是数据竞争或必然的未定义行为，而是活性失败。某些运行恰好让 A 先取得两把锁，就掩盖了问题。

图 5-1：资源分配图。实线从锁指向持有者，虚线从线程指向它等待的锁；A → b → B → a → A 构成有向环。若省略锁节点，只保留 A 等 B、B 等 A，便得到 wait-for graph（等待关系图）。

上述相反顺序称为 ABBA。统一规定所有路径先锁 a 再锁 b，就能破坏本例的循环等待。经典的 Coffman 四个必要条件是：资源互斥、持有部分资源继续等待、资源不能被强行剥夺、循环等待。可以通过统一加锁顺序、一次安全取得多锁、减少嵌套持锁等方式破坏等待环。

/**
 * @file example06.cpp
 * @brief 故意死锁的演示：两个线程以相反顺序嵌套持有两把锁（ABBA）。
 * @details 线程一在每轮迭代内先锁 mutex_a 再锁 mutex_b，线程二顺序相反；两个
 *          lock_guard 嵌套，使每个线程在持有第一把锁的同时等待第二把，满足死锁的
 *          “持有并等待”条件；一旦交错成“一持 a 等 b、二持 b 等 a”，双方永久互相等待。
 *          两次加锁之间的 sleep_for 只是拉宽危险窗口、提高死锁复现概率，但不保证某次一定发生，
 *          它不是死锁的原因，删去后仍可能死锁，只是要靠调度恰好撞上交错。
 *          若形成等待环：join 永久阻塞且无输出；未形成时可能正常输出 2000 2000。
 *          对应正文 §5.1；正确写法见示例 7（std::lock + defer_lock）与示例 9（scoped_lock）。
 * @warning 故意错误的示例程序，请勿照搬；不要把它当作必须正常退出的程序来测试。
 */
#include <chrono>   // std::chrono::milliseconds：拉宽死锁窗口的演示用时延
#include <iostream> // std::cout：未形成等待环、循环正常结束时才输出
#include <mutex>    // std::mutex / std::lock_guard
#include <thread>   // std::jthread / std::this_thread::sleep_for

/**
 * @brief 程序入口：两个线程以相反的嵌套顺序争用两把锁，复现 ABBA 死锁。
 * @return 正常路径隐式返回 0，但遇到 ABBA 时无法返回；没有形成等待环时正常返回。
 * @note 锁与计数器先构造、后销毁，寿命覆盖两个线程；若形成等待环，线程将无法退出，
 *       发生死锁时，jthread 析构中的 join 也不返回。
 */
int main() {
    int count_a = 0;    // 共享计数器 A：约定由 mutex_a 保护；mutex 不知道这份约定，靠全程序遵守（§4.2）
    int count_b = 0;    // 共享计数器 B：约定由 mutex_b 保护
    std::mutex mutex_a; // 保护 count_a 的互斥锁
    std::mutex mutex_b; // 保护 count_b 的互斥锁

    /** @brief 每轮迭代内嵌套加锁 a→b；与 add_ba 并发时可能持 a 等 b。 */
    auto add_ab = [&] {
        for (int i = 0; i < 1000; ++i) {
            std::lock_guard<std::mutex> lock_a(mutex_a); // 持有 a 且不放手——“持有并等待”的“持有”
            // 拉宽危险窗口：增加对端线程在此刻拿到 b 的机会。删去本行仍可能死锁，只是要靠运气。
            std::this_thread::sleep_for(std::chrono::milliseconds(1));
            std::lock_guard<std::mutex> lock_b(mutex_b); // 若对端已持 b，本线程持 a 永久等待
            ++count_a; // 双锁齐备才能执行到这里；死锁时这两行永远执行不到
            ++count_b;
        }
    };
    /** @brief 每轮迭代内嵌套加锁 b→a，顺序与 add_ab 相反，构成 ABBA 等待环的另一半。 */
    auto add_ba = [&] {
        for (int i = 0; i < 1000; ++i) {
            std::lock_guard<std::mutex> lock_b(mutex_b); // 持有 b
            std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 同样拉宽窗口
            std::lock_guard<std::mutex> lock_a(mutex_a); // 若对端已持 a，本线程持 b 永久等待
            ++count_a;
            ++count_b;
        }
    };
    {
        std::jthread first(add_ab);  // 线程一按 a→b 嵌套加锁
        std::jthread second(add_ba); // 线程二按 b→a 嵌套加锁
    } // 两个 jthread 在此析构并 join：若双方形成 ABBA，join 将无法返回；用独立进程超时观察
    std::cout << count_a << ' ' << count_b << '\n'; // 未形成死锁时输出 2000 2000
}

观察方式：在独立进程中设置超时。若形成 ABBA，程序无输出且无法自行结束；若没有遇到危险交错，也可能完成并输出 2000 2000。sleep_for() 只扩大两次加锁间的窗口，不能保证对方已取得第一把锁。超时也不能单凭一次现象证明死锁；这里的缺陷由锁依赖环说明，测试仅提供补充观察。

为什么“先后两个独立循环”的版本不会死锁。 若把每个线程写成“先用 lock_guard 守护 a 的循环跑完，再开始守护 b 的循环”，任意时刻每线程最多只持有一把锁：开始抢第二把时第一把早已析构释放，“持有并等待”条件不成立，若没有其他等待依赖，就不会由这两把锁形成 ABBA 环。代价是两个计数器的更新不再是一个原子整体——若有观察者要求两者保持一致关系，拆分写法会让它看到“只更新了一半”的中间状态。

写法同时持有的锁可能死锁？适用
先后两个单锁循环最多 1 把不会由这两把锁形成 ABBA（前提是无其他等待依赖）两份数据各自独立、无需整体一致
嵌套 lock_guard，顺序相反（示例 6）2 把可能（ABBA 等待环）错误示范，请勿使用
std::lock + defer_lock（示例 7）或 scoped_lock（示例 9）2 把避免本次多锁获取的死锁；不排除外部等待环必须同时保护多份数据且顺序无法全局约定

规则可以提炼为：本例的独立单锁循环不会形成 ABBA，但“每次只持一把锁”并不保证整个程序无死锁：持锁等待任务、递归锁定非递归 mutex，或线程池资源耗尽，都可能使程序无法推进。顺序能全局统一时，约定统一顺序即可，不必动用 std::lock。

/**
 * @file example07.cpp
 * @brief std::lock + defer_lock 多锁获取：两个线程按相反顺序关联两把锁而不死锁。
 * @details 两个线程各对受两把 mutex 保护的两个计数器累加 10000 次；线程一按 a→b、
 *          线程二按 b→a 的相反顺序构造 unique_lock，统一交给 std::lock 以避免死锁的
 *          算法获取，任意交错都不形成 ABBA 等待环。预期输出 "20000 20000"。对应正文 §5.2。
 * @note 不能用 lock_guard 替代本例写法：lock_guard 构造即加锁、没有 defer_lock，
 *       两个线程按相反顺序各自加锁就会回到“各持一把、再等另一把”的 ABBA 死锁。
 *       unique_lock + defer_lock 把“关联锁”与“实际加锁”拆成两步，std::lock 才有
 *       “try_lock 失败 → 释放已拿到的 → 重试”的回旋余地。
 */
#include <cassert>  // assert：验证最终计数
#include <iostream> // std::cout
#include <mutex>    // std::mutex / std::unique_lock / std::lock / std::defer_lock
#include <thread>   // std::jthread

/**
 * @brief 程序入口：两个线程以相反加锁顺序并发更新同一对计数器。
 * @return 隐式返回 0。
 * @note 锁与计数器先构造、后销毁，寿命覆盖两个线程。本例故意每轮都取两把锁以展示
 *       多锁协议；真实统计宜先局部累计再合并（下篇 §10.2）。
 */
int main() {
    int count_a = 0;    // 共享计数器 A：并发期间由 mutex_a 保护；join 后可无锁读取
    int count_b = 0;    // 共享计数器 B：并发期间由 mutex_b 保护
    std::mutex mutex_a; // 保护 count_a 的互斥锁
    std::mutex mutex_b; // 保护 count_b 的互斥锁

    /** @brief 按 a→b 顺序关联两把锁并累加两个计数器；引用对象寿命覆盖线程执行期。 */
    auto add_ab = [&] {
        for (int i = 0; i < 10000; ++i) {
            // defer_lock：构造守卫只“关联”mutex、记录管理责任，此时尚未持有任何锁；
            // 加锁时机被推迟到下面的 std::lock，这是能交给死锁避免算法统一调度的前提。
            std::unique_lock<std::mutex> first(mutex_a, std::defer_lock);  // 只关联 a，暂不加锁
            std::unique_lock<std::mutex> second(mutex_b, std::defer_lock); // 只关联 b，暂不加锁
            // 加锁时机在此：std::lock 内部可“尝试—释放—重试”，实际的加锁顺序由算法决定，
            // 与上面构造守卫的 a→b 关联顺序无关；成功返回时两把锁都已持有。
            std::lock(first, second); // 多锁算法统一获取；成功返回后两个守卫都拥有锁
            ++count_a; // 两个更新完整落在同一受保护区间内
            ++count_b;
        } // 解锁时机在此：每轮离开作用域时两个守卫析构，自动 unlock（RAII，异常路径同）
    };
    /** @brief 按 b→a 的相反顺序关联同样两把锁；std::lock 保证两线程不形成 ABBA 等待环。 */
    auto add_ba = [&] {
        for (int i = 0; i < 10000; ++i) {
            // 关联顺序与 add_ab 相反，但 defer_lock 下构造时并未加锁，这个顺序对互斥
            // 语义毫无影响——它只是“把哪几把锁交给 std::lock”的形式，不死锁靠算法保证。
            std::unique_lock<std::mutex> first(mutex_b, std::defer_lock);  // 关联顺序与 add_ab 相反
            std::unique_lock<std::mutex> second(mutex_a, std::defer_lock);
            std::lock(first, second); // 内部可尝试加锁、解锁并重试；交错执行也不死锁
            ++count_a;
            ++count_b;
        } // 守卫析构自动解锁；对端线程的下一轮重试才有机会成功
    };
    {
        std::jthread first(add_ab);  // 线程一按 a→b 顺序关联两把锁
        std::jthread second(add_ba); // 线程二按 b→a 顺序关联两把锁
    } // 两个 jthread 析构并 join；此后读取计数不再需要持锁
    assert(count_a == 20000 && count_b == 20000); // 互斥 + 同步保证不丢更新：2 × 10000
    std::cout << count_a << ' ' << count_b << '\n'; // 输出 "20000 20000"
}

输出 20000 20000。两个线程关联锁的顺序相反：若各自直接 lock()，可能形成 §5.1 的 ABBA 死锁；在本例仅涉及这两把锁、没有其他等待依赖的前提下，交给 std::lock 统一获取可避免 ABBA 死锁。示例 9 的 std::scoped_lock 是同一语义的更简洁写法，新项目优先使用它；需要延迟加锁、提前解锁或配合条件变量时，才回到本例的 unique_lock 形态。

图 5-2：示例 7 一轮迭代中的加锁与解锁；这只是标准允许的一种实现与交错。

按四个时刻读图：① 关联，defer_lock 只让守卫记住 mutex；② 获取，std::lock 统一尝试，必要时释放后重试；③ 更新，成功返回后才在双锁临界区修改两个计数器；④ 释放，每轮作用域结束，两个守卫分别析构解锁。

关联顺序与加锁顺序是两回事 unique_lock(m, defer_lock) 本身不加锁；即使不用 std::lock，也可以稍后用成员 lock() 决定顺序。只有直接加锁的构造形式才在构造时锁定。std::lock 不规定内部获取顺序，也不是一次原子获取；异常时会释放本次已经取得的锁。图中的“尝试—释放—重试”不能当作唯一实现。参见 多锁算法规定。

std::lock 避免本次多锁获取的死锁，但不保证公平或每个线程在有界时间内完成；持锁后再等待依赖这些锁的任务，仍会形成外部等待环。若不需要延迟或提前解锁，§5.4 的 scoped_lock 更简洁。

};

/**
 * @brief 尝试从 from 向 to 支付 amount 元。
 * @param[in,out] from 付款账户；本函数执行期间持有其 mutex。
 * @param[in,out] to 收款账户；必须与 from 是不同对象。
 * @param amount 支付金额（元）；要求为正数。
 * @retval true 支付成功：from 已扣款、to 已入账，两步同时生效。
 * @retval false 余额不足：两个账户均未做任何改动。
 * @note “检查余额是否足够”与“扣款 + 入账”在同一个双锁临界区内完成：
 *       任一时刻只有一个线程能对这两个账户做支付判定，判定结果不会被并发转账推翻。
 * @warning 必须用 std::lock（或 std::scoped_lock）一次取得两把锁；
 *          先后 lock() 两把锁在反向支付并存时是 ABBA 死锁（§5.1）。
 */
bool pay(Account& from, Account& to, int amount) {
    // ① defer_lock：两个守卫只关联各自的 mutex，此时尚未持有任何锁。
    std::unique_lock<std::mutex> from_lock(from.mutex, std::defer_lock);
    std::unique_lock<std::mutex> to_lock(to.mutex, std::defer_lock);
    // ② std::lock 采用避免死锁的算法取得两把锁，具体步骤由实现决定；
    //    因此反向支付（B→A）同时发生也不会在本次多锁获取中死锁。
    std::lock(from_lock, to_lock);
    // ③ 临界区开始：本线程独占两个账户。余额检查必须与扣款同处一个临界区，
    //    否则两个线程可能都看到“余额足够”然后都扣款，造成透支（图 5-3 左）。
    if (from.balance < amount) {
        return false; // 余额不足：拒绝支付；守卫析构自动解锁，两账户均未改动
    }
    from.balance -= amount; // 扣款：与上面的检查不可分割
    to.balance += amount;   // 入账：与扣款同处临界区，任何同时持有两把账户锁的观察者都看到总额守恒
    return true;
    // ④ 函数返回时两个守卫析构、自动解锁；此后其他线程才能观察到新余额。
}

/**
 * @brief 程序入口：4 个线程并发从 A 向 B 付款，验证无透支、总额守恒、笔数确定。
 * @return 隐式返回 0。
 * @note 账户先于线程构造、后于线程销毁，寿命覆盖全部支付线程。
 */
int main() {
    Account a;      // 付款账户
    Account b;      // 收款账户
    a.balance = 1000; // 线程启动前的单线程阶段：此时写入无需持锁
    b.balance = 0;

    constexpr int kThreads = 4;   // 付款线程数
    constexpr int kAttempts = 10; // 每线程尝试支付的笔数
    constexpr int kAmount = 30;   // 每笔金额（元）
    std::array<int, kThreads> paid{};   // paid[i] 只由线程 i 写：该线程成功笔数
    std::array<int, kThreads> failed{}; // failed[i] 只由线程 i 写：该线程被拒笔数

    /**
     * @brief 付款任务：反复尝试从 A 向 B 支付，把结果记入自己独占的统计槽位。
     * @param index 本线程独占的数组槽位下标；不同线程写不同元素，无需加锁。
     * @note 按值接收 index；账户按引用共享，其寿命覆盖全部线程。
     */
    auto payer = [&](int index) {
        for (int i = 0; i < kAttempts; ++i) {
            if (pay(a, b, kAmount)) {
                ++paid[index];   // 只写自己的槽位：无共享写冲突
            } else {
                ++failed[index]; // 余额不足的被拒笔数同样分槽统计
            }
        }
    };
    {
        std::jthread p0(payer, 0); // 4 个付款线程并发竞争同一对账户
        std::jthread p1(payer, 1);
        std::jthread p2(payer, 2);
        std::jthread p3(payer, 3);
    } // 全部 jthread 在此析构并 join：所有支付完成后主线程才继续

    int total_paid = 0;   // 成功总笔数
    int total_failed = 0; // 被拒总笔数
    for (int i = 0; i < kThreads; ++i) {
        total_paid += paid[i];     // join 之后读取各槽位，有同步保证
        total_failed += failed[i];
    }
    // 1000 元、每笔 30：恰好 33 笔成功（33 × 30 = 990），第 34 笔起余额 10 < 30 被拒。
    // 每笔支付都是原子的，因此无论线程怎样交错，笔数与余额都是确定值。
    assert(total_paid == 33);                          // 成功笔数确定
    assert(total_failed == kThreads * kAttempts - 33); // 40 - 33 = 7 笔被拒
    assert(a.balance == 1000 - 33 * kAmount);          // 10：余额永不为负
    assert(b.balance == 33 * kAmount);                 // 990
    assert(a.balance + b.balance == 1000);             // 总额守恒：无丢失、无凭空产生
    std::cout << "paid=" << total_paid << " failed=" << total_failed
              << " A=" << a.balance << " B=" << b.balance << '\n'; // paid=33 failed=7 A=10 B=990
}

输出 paid=33 failed=7 A=10 B=990。40 次请求中，每笔 30 元，1000 元只够支付 33 次，因此最终 A=10、B=990，与线程交错无关。这个确定性来自三项约束：

  • 不透支：检查与扣款处于同一双锁临界区，余额判定不会被其他支付推翻。
  • 总额守恒：扣款与入账一起提交；遵守双锁协议的观察者看不到中间状态。
  • 统计隔离：每个线程只写自己的 paid / failed 槽位，join 后由主线程汇总。

std::lock 负责避免本次双锁获取的死锁，临界区负责维护资金规则，两者职责不同。真实支付还需要金额溢出检查、持久化与失败回滚；本例只研究内存中的并发协议。

/**
 * @file example09.cpp
 * @brief 用 std::scoped_lock 一次取得两把账户锁，演示多锁转账如何避免死锁。
 * @details 两个线程沿相反方向同时转账（a→b 与 b→a）；scoped_lock 内部采用避免死锁的
 *          加锁算法，无论执行如何交错都不会形成等待环；总额守恒由断言验证。
 *          预期输出 "110 90"。对应正文 §5.4。
 */
#include <cassert>  // assert：验证转账后的余额
#include <iostream> // std::cout
#include <mutex>    // std::mutex / std::scoped_lock
#include <thread>   // std::jthread

/**
 * @brief 银行账户：余额与保护它的互斥锁绑定在一起。
 * @note mutex 成员不可复制，因此 Account 整体也不可复制；按引用传递使用。
 */
struct Account {
    std::mutex mutex;  ///< 保护本账户 balance 的互斥锁
    int balance = 100; ///< 余额；并发访问需持本账户 mutex，所有线程 join 后可无锁读
};

/**
 * @brief 从 from 向 to 转账 amount；余额检查与两步更新在同一临界区内完成。
 * @param[in,out] from 转出账户；本次调用会持有其 mutex。
 * @param[in,out] to 转入账户；必须与 from 是不同对象。
 * @param amount 转账金额；非正金额直接拒绝。
 * @note scoped_lock 一次性取得两把锁，调用方无需自行约定加锁顺序。
 * @warning 同一账户不能同时作为 from 与 to：同一把非递归 mutex 不能被锁两次。
 * @see 正文 §5.4 的双向转账
 */
void transfer(Account& from, Account& to, int amount) {
    // 同一个账户不能把同一把非递归 mutex 当作两把锁传入；非正金额无意义。
    if (&from == &to || amount <= 0) {
        return;
    }
    std::scoped_lock lock(from.mutex, to.mutex); // 以避免死锁的算法取得两把锁；不是一次硬件原子操作；析构时全部释放
    if (from.balance >= amount) { // 余额检查必须与扣减同处一个临界区，否则判断结果会过时
        from.balance -= amount; // 在同时持有两把账户锁时扣减转出余额
        to.balance += amount; // 两个更新与检查一起完成，保持总额不变
    }
}

/**
 * @brief 程序入口：两个线程沿相反方向同时转账。
 * @return 隐式返回 0。
 */
int main() {
    Account a; // 初始余额 100
    Account b; // 初始余额 100
    {
        /** @brief 第一条工作线程执行 a 到 b 的转账；引用活到 join 后。 */
        std::jthread first([&] { transfer(a, b, 10); });  // a → b 转 10
        /** @brief 第二条工作线程执行 b 到 a 的转账；由 scoped_lock 处理多锁顺序。 */
        std::jthread second([&] { transfer(b, a, 20); }); // b → a 转 20；锁顺序相反也不死锁
    } // 两个 jthread 析构并 join；此后读取余额不再需要持锁
    assert(a.balance == 110 && b.balance == 90); // 总额守恒：200 = 110 + 90
    std::cout << a.balance << ' ' << b.balance << '\n'; // 输出 "110 90"
}

输出 110 90。固定输入确保任一转账顺序都满足余额要求，不涉及整数溢出。若扩展为真实账户系统，还应明确金额上限、失败结果和持久化规则。

scoped_lock 避免这里的多锁取得死锁，但不能修复整个程序的所有等待环。例如，持有账户锁的线程等待另一个任务，而那个任务又要账户锁，仍会死锁。

5.5 活锁与饥饿

  • 活锁：线程一直重试或相互让步，看似忙碌却没有完成业务。例如两个线程同步地释放锁、重试，又同时冲突。
  • 饥饿：系统整体在推进，但某个线程长期得不到锁或执行机会。标准 mutex 不承诺公平排队。
  • 死锁：参与者互相等待，无法继续。

try_lock() 加循环不是万能修复，忙等可能加重竞争。优先简化资源依赖；需要公平性、超时或队列顺序时，必须把这些写进设计，而不是假设调度器会照顾每个线程。

6. 条件变量：等待状态，而不是等待通知

6.1 为什么有了锁还需要等待工具

锁回答“现在谁能访问数据”，条件变量回答“条件不满足时，怎样暂时让出执行资源”。例如消费者发现队列为空，不应该一直持锁检查：生产者需要同一把锁才能放入数据。

一个正确的条件变量协议通常有三部分：

  • 共享状态：例如 ready 的值或队列中保存的数据。
  • 共享谓词：判断能否继续的表达式，例如 ready、closed || !queue.empty()。
  • 同一把 mutex：保护状态修改和谓词检查，并配合等待操作。

先理解“谓词”：它回答“现在能不能继续”。 谓词（predicate）并不神秘，它就是一个返回 bool 的判断：true 表示“条件满足，可以继续”，false 表示“条件还不满足，需要等待”。在条件变量中，谓词通常是一个读取共享状态的 lambda，而不是一种新的数据类型。

可以把它想成在餐厅等取餐：ready 或队列内容是屏幕上的状态，“我的餐是否已经做好”是谓词，notify_one() 只是提醒顾客再看一次屏幕。提醒本身不等于餐已经做好；真正能不能取餐，仍由谓词判断。

/**
 * @file example10.cpp
 * @brief 条件变量标准协议：同一把锁 + 共享谓词 + 通知，主线程向工作线程交付一份数据。
 * @details 消费者用带谓词的 wait 等待 ready；生产者在临界区内同时发布 payload 与
 *          ready，解锁后 notify_one。消费者被唤醒后必须重新获得锁并再次检查谓词，
 *          确认 ready 为真后才读取 payload，算出 42。预期输出 42。对应正文 §6.1。
 */
#include <cassert>            // assert：验证传递结果
#include <condition_variable> // std::condition_variable：等待与通知
#include <iostream>           // std::cout：输出最终结果
#include <mutex>              // std::mutex / std::lock_guard / std::unique_lock
#include <thread>             // std::jthread：创建并回收消费者线程

/**
 * @brief 程序入口：演示"等待状态，而不是等待通知"。
 * @return 隐式返回 0。
 * @note cv、mutex 与全部共享数据先构造、后销毁，寿命覆盖整个消费者线程。
 */
int main() {
    // 以下对象都由主线程拥有，并一直存活到消费者线程结束之后。
    std::mutex mutex;           // 同一把锁：保护 payload、ready 以及对谓词的检查
    std::condition_variable cv; // 只负责等待与唤醒；不保存 ready，也不传递 payload
    bool ready = false;         // 共享谓词状态：false 表示尚未发布，true 表示数据已发布
    int payload = 0;            // 主线程写入、消费者读取的共享数据
    int result = 0;             // 并发阶段只由消费者写入；主线程在 join 后读取，无需再加锁

    /**
     * @brief 消费者等待 ready，持锁读取 payload；主线程在 join 后读取结果。
     * @note [&] 按引用捕获主线程中的对象，但不会延长它们的寿命；
     *       本例通过后面的 join 保证这些对象在使用期间始终存活。
     */
    std::jthread consumer([&] {
        // 构造 unique_lock 时立即锁住 mutex。
        // 与 lock_guard 不同，unique_lock 允许 wait 在等待期间暂时解锁、醒来后再加锁。
        std::unique_lock<std::mutex> lock(mutex);

        // wait(lock, pred) 的逻辑等价于：while (!pred()) { cv.wait(lock); }
        // 1. 首次检查谓词时，消费者必须持有 mutex。
        // 2. 若 ready 为 false，wait 将"解锁 mutex 并进入等待"作为一个原子步骤完成，
        //    因而生产者无法插入到"检查 false"与"进入等待"之间修改状态并丢失通知。
        // 3. 等待期间消费者不持有 mutex，主线程才能进入下面的生产者临界区。
        // 4. 被唤醒后，wait 会先重新获得 mutex，再检查谓词；若仍为 false 就继续等待。
        //    因此，虚假唤醒或无关通知都不会被误当成"数据已经就绪"。
        cv.wait(lock, [&] {
            // 谓词可能执行多次；这里只读取共享状态，不修改业务数据。
            return ready;
        });

        // wait 返回时有双重保证：当前线程仍持有 mutex，并且刚才检查的 ready 为 true。
        // 锁建立的同步关系保证主线程对 payload 的写入对当前线程可见。
        result = payload * 2; // 在临界区内读到 21，计算并写入 42
        // 离开 lambda 时，lock 析构并自动解锁；随后消费者线程函数返回、线程结束。
    });

    // 主线程与消费者线程从这里开始并发推进，谁先获得 mutex 由实际调度决定。
    {
        // 若消费者正在等待，它已经释放 mutex；若它尚未检查，也会与此处互斥。
        std::lock_guard<std::mutex> lock(mutex); // 构造时加锁，进入生产者临界区
        payload = 21; // 先填写交付数据
        ready = true; // 再把状态设为已发布；两次写入必须位于同一个临界区
        // 这样其他持锁检查者不可能看到"ready 已为 true、payload 却尚未写好"。
    } // 离开作用域，lock_guard 析构并解锁；本例选择在解锁后通知

    // notify_one 只唤醒一个等待者，不传递数据，也不保证谓词已经成立。
    // 解锁后通知可以减少被唤醒线程立即争锁的可能；即使没有等待者，通知也不会被保存。
    // 若主线程先完成发布，消费者随后第一次检查就会看到 ready == true，根本无需等待。
    cv.notify_one();

    // 主线程在此等待消费者结束；消费者计算完成后，join 才返回。
    // join 建立的同步关系保证这里能安全读取消费者写入的 result。
    consumer.join();
    assert(result == 42); // 验证消费者已完成计算
    std::cout << result << '\n'; // 输出 42
}

    M->>M: 离开作用域，解锁 mutex
    M->>C: notify_one()，唤醒一个等待者
    M->>M: 调用 join()，等待消费者结束
    C->>C: 收到通知后醒来，重新获得 mutex
    C->>C: 再次检查谓词，ready == true
    Note right of C: wait 返回时仍持有锁
醒来不等于条件成立，必须重查谓词
    C->>C: result = payload * 2，得到 42
    C->>C: 离开 lambda，unique_lock 自动解锁
    C-->>M: 消费者线程结束，join() 返回
    M->>M: 读取 result，断言并输出 42

关键点是：notify_one() 只负责提醒等待者醒来，真正决定能否继续的是重新加锁后的谓词检查。 如果主线程先发布数据，消费者第一次检查 ready 就会得到 true，不会进入等待；即使之前的通知没有等待者，也不影响正确性。

输出 42。线程结束前不销毁 cv、锁或数据；主线程在 join 后读取 result。本例工作线程等待、主线程负责生产，因此不需要再创建一个生产线程。

}

wait(lock) 将“释放锁并进入等待”作为一个原子步骤；被唤醒后重新取得锁，才返回。它需要 unique_lock，因为等待期间必须临时释放并重新取得锁。

谓词版本先检查条件。如果生产者早已完成，消费者直接继续，完全不需要接收到那次通知。

核心原则 状态保存事实，通知只提示重新检查。

虚假唤醒指没有对应业务通知也可能结束一次等待。即使没有虚假唤醒，多消费者中也可能由另一个消费者先拿走了数据。单次 if 或不带检查的 wait() 不能证明条件成立，必须循环重新判断。

notify_one() 唤醒一个等待者，适合同种等待条件下新增一个可消费任务；notify_all() 唤醒所有等待者，适合关闭、全局状态切换。多个不同谓词共用一个条件变量时，notify_one() 可能选中无法继续的线程，应拆分条件变量或使用适当的全体通知。

通知可以在锁内，也可以在锁外；核心要求是状态协议与对象寿命正确。锁外通知前若对象可能被销毁，还需要额外的生命周期约束。通知不等于对任意共享数据的自动保护。接口语义见 条件变量等待规定。

6.4 超时、退出与关闭

wait_for 的谓词重载返回谓词最终是否成立，不能把“醒了”理解成“有数据”。若手写循环，每次重新等完整时长可能无限延长总等待；应基于 steady_clock 计算一次绝对截止时间，反复 wait_until，或者直接用谓词重载。超时不是实时返回保证：调度延迟以及重新取得 mutex 都可能让实际返回更晚。

队列通常使用 closed || !queue.empty()：醒后如果有数据就取数据；只有“已关闭且为空”才退出。必须先在锁内设置 closed，再通知等待者，最后回收线程并销毁队列。这比发送一个无法区分业务数据的“特殊数字”更明确。下篇 §11 的任务处理器会实现这个协议。

有界队列还需要生产者等待容量：生产者谓词为 closed || size < capacity，消费者谓词为 closed || !empty。用同一把 mutex 保护队列与关闭标志，通常分别使用“非满”和“非空”两个条件变量。成功取出通知生产者，成功放入通知消费者；关闭通知两组等待者。关闭后，已经阻塞的生产者也必须醒来并拒绝入队；消费者排空后退出。容量为零应在构造时拒绝。销毁前调用者必须先关闭并回收所有访问线程。

7. 从线程转向任务：结果如何回来

7.1 线程、任务与共享状态

§3.4 已用 async 完成一次平方计算；本章解释它背后的结果通道，并扩展到显式交付与队列调度。先区分“执行谁来安排”和“结果由谁保存”，再选择接口。

线程是执行资源，任务是要完成的工作，future 是取得某次工作结果的句柄。一个线程可以处理许多任务；拥有一个 future 并不意味着已经有线程在执行任务。

future<T> 与生产结果的一端通过一个异步共享状态相连。不要把它和“随意共享业务变量”混为一谈：这个状态由标准库管理，用于保存结果、异常和就绪信息。

图 7-1：异步结果通道。生产端把值或异常写入共享状态并使其就绪；消费端通过 future 等待并读取。

“有状态”和“状态就绪”是两回事。默认构造的 future 没有关联状态；一个有效 future 可能仍在等待结果。

操作等待吗？是否消费结果？
valid()不等待计算只判断是否关联共享状态，不表示任务成功或完成
wait()未就绪时等待；延迟任务可在这里执行不取值，不抛出已存储的任务异常
wait_for() / wait_until()在指定等待范围内检查状态返回 ready、timeout 或 deferred
future<T>::get()必要时等待取出值或重抛异常，并释放本句柄的状态关联
shared_future<T>::get()必要时等待可重复读取，普通 T 返回 const T&

普通 future 只能移动，不能复制；成功调用 share() 后，原 future 失去状态。对无状态 future 调用 get() 或等待函数违反接口要求，不能依赖实现一定抛出友好的 future_error。先写清所有权，避免重复消费，也不要让一个线程移动或消费句柄时另一个线程仍在访问该句柄。

就绪通知与成功检测到就绪之间提供同步，因此结果取得后可安全使用已经发布的数据；但返回引用或指针仍要求被引用对象存活，future 不会替外部对象续命。参见 异步共享状态 与 future 的消费语义。

7.2 promise：显式交付值或异常

promise<T> 是写入端：通常先 get_future() 取得唯一的读取端，再将 promise 移给负责完成工作的线程。一个状态只能满足一次，重复取 future 或重复设置结果会产生 future_error。

promise 的接口一览（promise<T&> 与 promise<void> 是特化，语义对应相同）：

/**

 * @details compute 用 promise 显式交付值或异常；main 另演示 promise 未满足就被销毁时，

#include <exception> // std::current_exception
#include <limits>    // numeric_limits<int>::max：确定翻倍不溢出的输入上界
#include <future>    // std::promise / std::future / std::future_error / std::future_errc
#include <iostream>  // std::cout
#include <stdexcept> // std::invalid_argument
#include <thread>    // std::jthread
#include <utility>   // std::move

/**
 * @brief 计算 input 的两倍；非法输入通过 future 通道抛出 std::invalid_argument。
 * @param input 业务输入；合法范围为 [0, INT_MAX / 2]，按值捕获进工作线程。
 * @return 正常路径返回 input * 2。
 * @throws std::invalid_argument 输入不在合法范围时，经共享状态在 get() 处重抛。
 * @note result.get() 在返回前等待工作线程交付；异常展开时 worker 由 jthread 自动回收。
 * @see 正文 §7.2“promise：显式交付值或异常”
 */
int compute(int input) {
    std::promise<int> producer;          // 写入端：负责向共享状态交付值或异常
    auto result = producer.get_future(); // 读取端：每个共享状态只能取得一次；源 promise 被移出后即无状态，故在移交前取得
    /** @brief 工作线程拥有移入的 promise，交付值或异常。 @note input 按值捕获，p 可修改。 */
    std::jthread worker([input, p = std::move(producer)]() mutable {
        // promise 的所有权移入线程；mutable 允许对这个捕获副本调用非 const 的 set_*。
        try {
            if (input < 0 || input > std::numeric_limits<int>::max() / 2) {
                throw std::invalid_argument("input outside safe doubling range"); // 业务失败，避免溢出
            }
            p.set_value(input * 2); // 交付值：使共享状态就绪，等待方随即可取
        } catch (...) {
            // 本例只有这个线程满足状态；业务失败也必须给等待方一个结果。
            p.set_exception(std::current_exception()); // 交付异常，避免 promise 未满足就被销毁
        }
    });
    return result.get(); // 必要时等待；失败时在当前线程重抛；展开时 worker 仍会自动回收
}

/**
 * @brief 程序入口：依次验证正常值、业务异常与 broken promise。
 * @return 隐式返回 0。
 */
int main() {
    assert(compute(21) == 42); // 正常路径：21 × 2
    const int limit = std::numeric_limits<int>::max() / 2; // 最大安全输入
    assert(compute(limit) == limit * 2); // 上界仍可表示，不能发生有符号溢出
    bool overflow_rejected = false; // 记录上界之外的输入是否被拒绝
    try {
        (void)compute(limit + 1); // 在工作线程中判定非法，再经 future 传播
    } catch (const std::invalid_argument&) {
        overflow_rejected = true; // 调用线程接收到预期的业务异常
    }
    assert(overflow_rejected); // 越界输入必须走异常通道
    bool received_error = false; // 主线程记录是否经 future 收到业务异常
    try {
        (void)compute(-1); // 业务异常路径：经 future 重抛到本线程
    } catch (const std::invalid_argument&) {
        received_error = true; // 预期异常已在调用线程捕获
    }
    assert(received_error); // 验证负数输入未被当作正常结果

    std::future<int> abandoned; // 将关联一个"注定不会被满足"的共享状态
    {
        std::promise<int> producer; // 此作用域拥有写入端；下面故意不满足它
        abandoned = producer.get_future(); // 取得读取端，但 promise 从未设置结果
    } // 未满足的 promise 被销毁，状态保存 broken_promise 异常并就绪
    bool broken = false; // 区分 broken_promise 与其他 future 协议错误
    try {
        (void)abandoned.get(); // 重抛状态中保存的 future_error
    } catch (const std::future_error& e) {
        broken = e.code() == std::make_error_code(std::future_errc::broken_promise); // 核对精确错误码
    }
    assert(broken); // 确认未满足写入端的销毁使状态带异常就绪
    std::cout << "value, exception, broken_promise checked\n"; // 三个结果通道检查都通过才输出
}

set_value() 通常在调用时使状态就绪，并不等到线程函数返回。消费者读到结果后，生产线程可能还在执行收尾操作；如果需要证明整个线程已结束，仍要 join。另有 set_value_at_thread_exit() 等接口用于推迟就绪，本文不涉及它们。

销毁未满足的 promise 会让消费者收到 broken_promise，而不是保证它永远等待。但是，如果 promise 一直活着、没有任何路径设置结果或销毁它，消费者仍可能永久等待。promise 的协议错误和任务本身的业务异常是不同的错误来源。参见 promise 规定。

7.3 packaged_task：把可调用对象和结果通道绑在一起

它保存一个可调用对象，调用任务时自动把返回值或抛出的异常存进共享状态。它不会自己创建线程。适合“先封装任务，稍后交给工作线程”的设计。

接口要点：

  • 模板参数是函数签名，例如 packaged_task<int(int)> 表示“接收 int、产出 int”；构造时传入任何匹配签名的可调用对象。
  • get_future() 对同一个共享状态只能成功调用一次，且只能在仍拥有状态的对象上调用；通常在任务被移走之前取得读取端（移出后的源对象已无状态，再调用会抛出 future_error；接管了任务的新对象仍可以取得）。
  • operator()(args...) 执行任务并交付结果；同一共享状态只能成功交付一次；调用目标抛出异常也会消耗该状态的交付机会，对已执行过的任务再次调用会抛出 future_error。需要复用时先 reset()：它放弃旧共享状态并建立新状态——此前取得的 future 并不失效：若旧任务已执行，它仍持有原结果或异常；若旧任务未执行，放弃旧状态会使它收到 broken_promise；必须针对新状态重新调用 get_future() 取得新的读取端。
  • 只能移动，不能复制；这决定了示例 12 中任务以 std::move 移交线程的写法。

#include <cassert>  // assert：验证结果
#include <future>   // std::packaged_task / std::future
#include <iostream> // std::cout
#include <thread>   // std::jthread
#include <utility>  // std::move

/**
 * @brief 程序入口：封装任务 → 取 future → 移交线程执行 → 取结果。
 * @return 隐式返回 0。
 */
int main() {
    // int(int) 表示任务接收一个 int，完成后提供一个 int 结果。
    /** @brief 在工作线程中计算平方。 @param x 本例固定为 9，平方可表示为 int。 @return x 的平方。 */
    std::packaged_task<int(int)> task([](int x) { return x * x; });
    auto result = task.get_future(); // 每个共享状态只能取得一次读取端；源任务被移出后即无状态，故先取得
    std::jthread worker(std::move(task), 9); // 移交任务所有权，随后在新线程执行 task(9)
    const int value = result.get(); // 等待任务完成并取出 81；任务抛出的异常也在此重抛
    assert(value == 81); // 验证 packaged_task 返回的平方结果
    std::cout << value << '\n'; // 输出已取回的结果
}

输出 81。移动后的原任务不再拥有这个状态。未执行就销毁的有效 packaged_task 同样会放弃状态，消费者可收到 broken_promise。一般把任务看成一次性对象；重复调用、状态重置会使协议复杂，不应当作普通可重复函数随意使用。

7.4 async：简洁，但要选择执行策略

示例 4 已演示返回值和异常；示例 13 只补充两个任务的结果合并与 deferred 的触发时机，避免重复前面的示例。

策略行为
std::launch::async以新执行线程的语义执行，返回 future；创建资源可能失败
std::launch::deferred保存任务；首次非定时等待（如 get()、wait()）在调用者线程执行它
不显式传策略相当于允许 async 或 deferred，由实现选择；不保证并行执行

/**
 * @file example13.cpp
 * @brief std::async 两种启动策略：launch::async 异步执行，launch::deferred 延迟执行。
 * @details 两个 async 任务并发得出 20 与 22；deferred 任务在 get() 之前不会运行，
 *          由 wait_for(0) 返回 future_status::deferred 证实。预期输出 "42 7"。
 *          对应正文 §7.4。
 */
#include <cassert>  // assert：验证结果与执行时机
#include <chrono>   // std::chrono::milliseconds：定时等待的时长
#include <future>   // std::async / std::launch / std::future_status
#include <iostream> // std::cout

/**
 * @brief 程序入口：对比两种策略的执行时机。
 * @return 隐式返回 0。
 */
int main() {
    /** @brief 第一条异步任务。 @return 独立常量 20，无共享写入。 */
    auto first = std::async(std::launch::async, [] { return 20; });  // 新执行线程语义；实际何时获得调度不确定
    /** @brief 第二条异步任务。 @return 独立常量 22，无共享写入。 */
    auto second = std::async(std::launch::async, [] { return 22; }); // 与 first 并发推进
    const int total = first.get() + second.get(); // 分别等待并取值：20 + 22
    assert(total == 42); // 验证两份结果合计为 42

    bool ran = false; // 只需主线程访问：deferred 任务最终也在主线程同步执行
    /** @brief 首次非定时等待时执行；本例在主线程内修改 ran。 @return 常量 7。 */
    auto lazy = std::async(std::launch::deferred, [&ran] {
        ran = true; // 本例由下方 main 中的 get 同步执行，不与 main 并发访问
        return 7; // 结果存入 deferred 共享状态，随后由 get 取回
    });
    // 定时等待不会启动 deferred 任务，只报告其状态。
    assert(lazy.wait_for(std::chrono::milliseconds(0)) == std::future_status::deferred);
    assert(!ran); // 证明任务尚未执行
    const int value = lazy.get(); // 首次非定时等待：任务在调用线程（此处即 main）中执行
    assert(ran && value == 7); // 验证延迟任务确实由本次 get 执行且值正确
    std::cout << total << ' ' << value << '\n'; // 输出 "42 7"
}

输出 42 7。这些工作很小，只演示行为，不暗示使用两个线程比直接相加更快。future 没有标准的取消接口；超时只代表此次等待结束，不代表任务被取消或失败。

7.5 析构到底等不等待

必须根据状态来源判断，而不能只看类型名 future：

  • promise / packaged_task 创建的状态：future 析构释放关联，通常不等待生产者线程；线程的寿命另行管理。
  • 选择了 async 策略的 std::async 状态：尚未完成、且最后一个引用释放时，释放操作可能等待关联线程完成。移动给别人或者转成 shared_future 后，最后释放者也可能承担等待。
  • deferred 状态：若从未被非定时等待触发，释放它不会为了“做完工作”而执行任务。

析构与锁 不要在持有任务所需锁时销毁可能等待的最后一个句柄，也不要把 future 析构当作主动取消。

wait() 或析构不会把任务中保存的异常抛给调用方；要观察异常，需要 get()。未取出的异常可能随状态销毁而被丢弃。策略与等待规则见 async 规范。

7.6 shared_future：多方读取同一份结果

它可以复制，每个使用线程持有自己的句柄副本。普通 T 的 get() 返回共享状态内的 const T&，必须让至少一个相关句柄维持状态寿命；需要长期保存时复制结果。T&、void 有各自的返回语义。

/**
 * @file example14.cpp
 * @brief std::shared_future：把同一份结果安全地分发给多个线程只读。
 * @details promise 先交付字符串，两个 jthread 各持一份 shared_future 副本读取长度。
 *          预期输出 "5 5"。对应正文 §7.6。
 */
#include <array>    // std::array：两个线程各自的输出槽位
#include <cassert>  // assert：验证读取结果
#include <future>   // std::promise / std::shared_future
#include <iostream> // std::cout
#include <string>   // std::string：被共享的只读结果
#include <thread>   // std::jthread

/**
 * @brief 程序入口：一次发布，多方读取。
 * @return 隐式返回 0。
 * @note 先 set_value 再启动线程：即使线程创建失败，也不会留下永远等配置的线程。
 */
int main() {
    std::promise<std::string> producer; // 主线程拥有只读配置的写入端
    auto config = producer.get_future().share(); // 立即转成 shared_future：可复制、可重复 get
    // 先满足状态，线程启动失败时也不会留下一个永远等待配置的线程。
    producer.set_value("ready"); // 交付共享状态；此后多个读取端可并发读取同一字符串
    std::array<std::size_t, 2> lengths{}; // 每个元素只由一个线程写，元素间无冲突
    {
        /** @brief 第一条线程以句柄副本只读配置，并写自己的 lengths[0]。 */
        std::jthread first([config, &lengths] { lengths[0] = config.get().size(); });  // 按值复制句柄
        /** @brief 第二条线程以句柄副本只读配置，并写自己的 lengths[1]。 */
        std::jthread second([config, &lengths] { lengths[1] = config.get().size(); }); // 各持一份副本
    } // 两个 jthread 析构并 join；此后主线程读取 lengths 有同步保证
    assert(lengths[0] == 5 && lengths[1] == 5); // "ready" 长度为 5
    std::cout << lengths[0] << ' ' << lengths[1] << '\n'; // 输出 "5 5"
}

输出 5 5。两个线程只读同一个字符串，分别写数组的不同元素，主线程回收后读取。shared_future 保证共享状态读取机制，不保证结果内部指针指向的可变对象线程安全；共享 shared_ptr<Mutable> 的结果也不能省去对 Mutable 的同步。
