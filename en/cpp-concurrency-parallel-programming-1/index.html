Concurrent programs are hard to write not so much because of the sheer number of APIs, but because you must answer three questions clearly: Who owns the data, who may modify it, and what mechanism lets another thread use it safely? This article organizes C++ concurrency and parallel programming around those three questions. The code centers on the C++20 standard library and uses no third-party concurrency library.

This is Part I of the series. It covers, in order, the execution model, the build environment, thread lifecycles and argument passing, shared state and mutexes, multiple locks and deadlock, condition variables, and task result channels such as promise, packaged_task, and async. Part II goes on to discuss atomic variables and memory ordering, C++20’s cancellation and coordination facilities, engineering practice, and the implementation of a complete task processor.

Every block marked “Example N” is a complete program that compiles on its own. In its comments, @brief describes the purpose, @param / @return describe the interface, and @pre / @note / @warning spell out preconditions and concurrency boundaries. Blocks marked “snippet” serve only for local illustration.

1. Understanding How a Program Makes Progress Concurrently

1.1 Concurrency and Parallelism

A thread is a path along which instructions execute. A process may contain several threads: each has its own call stack, but they normally share the objects and address space of the process. An object living on a stack can also be reached by other threads through references, so “local variable” does not mean “private to the thread.”

Concurrency means that multiple activities make progress within the same span of time; they may be interleaved or may execute simultaneously. Even a single-core processor achieves concurrency through scheduling. Parallelism means that several activities execute at the same instant, which typically requires more than one execution resource.

For example, a chef who alternates between boiling noodles and chopping vegetables is being concurrent; two chefs, each doing one of those tasks, can be parallel. Concurrency mainly helps organize independent activities, whereas parallelism mainly helps exploit multiple execution resources. They often appear together, yet neither implies the other.

Figure 1-1: The upper diagram shows concurrent interleaving on a single core; the lower one shows parallelism on two cores. Concurrency is not confined to a single core—several concurrent activities may also run in parallel.

You cannot assume a thread starts running merely because it was created, nor infer which of two threads will finish first from their order in the source. Operating-system scheduling, compiler optimizations, and hardware execution all shape the behavior you observe.

1.2 Synchronous, Asynchronous, Blocking, and Non-Blocking Are Different Axes

These terms differ slightly across fields; this article uses them in the following sense:

AxisQuestion it answersMeaning and example
Concurrency / parallelismHow do activities progress?Advancing together over a span of time / executing at the same instant
Synchronous / asynchronousHow is a completed operation’s result obtained?The call yields the result directly / launching the operation and obtaining its result are separate
Blocking / non-blockingWhen completion is not yet possible, does the current call wait?Wait for the condition to hold / report the current state or temporary inability at once

Figure 1-2: The two sets of axes are independent and combine freely; asynchronous does not imply non-blocking, nor does synchronous necessarily imply waiting.

Launching an asynchronous task can return a result handle promptly, yet a later get() on that handle may still block. The synchronous try_lock() reports the outcome of the current attempt immediately, without waiting for the lock to become available. An asynchronous API need not create a new thread per task. Note also that std::async supports a deferred strategy: it does not run the task in the background but executes it on the waiting thread at the first non-timed wait (§7.4).

Also distinguish a “non-blocking API” from the progress guarantees studied in algorithm theory. Lock-free roughly means the system as a whole keeps making progress, while wait-free requires every operation to finish within a bounded number of steps. Calling a non-blocking API in a loop does not automatically earn you either guarantee.

1.3 Correctness Covers Both Safety and Liveness

  • Safety: no out-of-bounds access, no touching destroyed objects, no broken data invariants, no data races.
  • Liveness: tasks eventually get a chance to finish, waits have a way out, and threads do not wait on one another forever.
  • Performance: given correctness, whether latency, throughput, and resource consumption meet the requirements.

“It ran correctly ten times” samples only a handful of executions. For a concurrent program you must use the synchronization rules to explain why every allowed interleaving is safe.

GCC’s official status table lists jthread, stop_token, and interruptible condition-variable waits as available since libstdc++ 10.1, and semaphores, latches, barriers, and atomic waits since 11.1. 3. The First Rule of Threads: Manage the Lifecycle

3.1 std::thread Starts Execution; join() Reaps It

Once a std::thread is constructed successfully, a new thread of execution invokes the designated function. The thread object is a management handle for that thread of execution: it cannot be copied, but it can be moved. That the thread function has returned does not mean the handle is finished with reaping.

Let us first look at the class’s interface as a whole; Example 1 then shows its minimal usage.

std::thread worker(f, arg1, arg2); // worker is only a management handle; the new thread has started once construction succeeds; when it is scheduled is unspecified

f may be an ordinary function, a lambda, a function object, or a pointer to member function—in the last case the first argument is the calling object (an object copy, a pointer, or a std::ref wrapper). If the thread cannot be started (because resources are exhausted, say), std::system_error is thrown; copying or moving the callable and arguments into storage may throw other exceptions too. These exceptions occur in the caller that constructs the thread, and a failed construction leaves behind no new thread that the caller would need to join. The arguments are first copied or moved into internal storage per §3.3, and only then is f invoked via INVOKE. The thread function’s return value is thrown away: to bring a result back, use a reference argument (Example 1), guarded shared state (§4), or a future result channel (introduced in §3.4 and developed fully in §7).

The remaining construction forms: default construction associates no thread; copy construction and copy assignment are deleted (the handle owns uniquely); move construction and move assignment transfer management, after which the source has no associated thread (move assignment also requires care about whether the destination is already joinable).

/**
 * @file example01.cpp
 * @brief Passing by value with std::thread and passing by explicit reference with std::ref.
 * @details The worker computes the square of input and writes it back to the main thread's result through a reference; the main thread
 *          reaps the thread with join() before reading the result, relying on the synchronization established by join to avoid a data race.
 *          Expected output: 49. See §3.1 in the text.
 */
#include <cassert>    // assert: verifies the computed result
#include <functional> // std::ref: wraps a reference into a copyable reference_wrapper
#include <iostream>   // std::cout: prints the final result
#include <thread>     // std::thread: creates and manages a thread of execution

/**
 * @brief Computes the square of input and writes it into output.
 * @param[in] input The input value, copied by value into the thread-argument storage and thereafter unrelated to the caller's variable.
 * @param[out] output Where the result is written; the caller must ensure its lifetime spans the whole execution of the thread.
 * @pre input's square is representable as an int; this example fixes it at 7 and does not handle overflow for arbitrary integers.
 * @note Synchronization with the main thread comes from join(), so no mutex is needed here.
 * @warning This function requires an int&; a decayed copy of result cannot serve as that reference argument, so thread construction fails to compile.
 * @see §3.3, "Arguments, Captures, and Ownership," in the text
 */
void calculate(int input, int& output) {
    output = input * input; // Runs in the worker; writes the result owned by the main thread
}

/**
 * @brief Program entry point: starts a worker and safely retrieves the result.
 * @return Implicitly returns 0 to indicate normal termination.
 */
int main() {
    int result = 0; // Result variable owned by the main thread; its lifetime spans the whole worker execution
    // 7 is stored by value in the thread arguments; std::ref explicitly requests that result be passed by reference.
    std::thread worker(calculate, 7, std::ref(result));
    worker.join(); // Waits for the thread to end; only after join returns is reading result synchronized
    assert(result == 49); // The value read here is guaranteed to be the completed 49
    std::cout << result << '\n'; // Prints 49
}

The output is 49. The main thread does not read result before join(), and result stays alive throughout. A successful join() return synchronizes with the thread’s completion, so no additional mutex is needed here.

Why the argument needs std::ref, and how that differs from a lambda’s reference capture, is covered in §3.3.

joinable() means the handle still has an associated thread, not that it is “running.” A default-constructed object, one moved from, and one successfully join()ed or detach()ed are no longer joinable. Both join() and detach() require the object to remain joinable; calling either when it is not reports std::system_error, and you cannot reap or detach twice. join() also cannot wait on the calling thread itself. After a move the source is no longer joinable and the destination takes over the association; move-assigning to a std::thread that is still joinable likewise calls std::terminate(). Operations on one and the same thread handle are not automatically synchronized with each other, so a single owner should be responsible for it.

Lifecycle red line If a std::thread is destroyed while still joinable, std::terminate() is called and the program ends. This is the error-handling policy prescribed by the standard: it keeps an implicit wait from masking a block, and keeps an implicit detach from letting referenced objects’ lifetimes run wild. You must settle the association explicitly before destruction.

Figure 3-1: State transitions of a thread handle; the red line marks the consequence of destroying a joinable object outright. That is not the only way a program can trigger std::terminate().

In Example 1 nothing between successful construction and join() can throw; in real, more intricate code, prefer RAII.

3.2 RAII and std::jthread

RAII binds a resource’s release to an object’s destructor: cleanup happens automatically when the scope is left, exception unwinding included. A lock guard takes care of unlocking; a thread-management object takes care of reaping the thread.

When a C++20 std::jthread is destroyed while still joinable, it first requests a stop and then calls join(). A stop request is only a notification; whether the thread reacts depends on the thread function, a topic taken up in Part II, §9.1.

How it relates to std::thread, and how it differs. Strictly speaking, these are two classes in <thread>, not two member interfaces of one class. Both manage a thread of execution and both are move-only and non-copyable; jthread is not another scheduling model, nor a subclass of thread, and the two cannot be converted into one another directly. You may think of jthread as a thread-management class offering “automatic reaping plus cooperative stop,” but do not infer any particular internal implementation from that.

Aspectstd::threadstd::jthread
Standard versionSince C++11Since C++20, with standard-library support required
Destroyed while joinableCalls std::terminate(); the association must be settled beforehandCalls request_stop() then join(); may block
Stopping mechanismNo built-in stop-request interface; an exit protocol must be designed separatelyBuilt-in stop state and request interface, though the thread must still cooperate
Explicit waitjoin() waits for the thread to endAlso supports join(), which by itself requests no stop

These behaviors can be checked against the C++20 draft’s thread class and the jthread class.

When to reach for each?

  • In new C++20 code, prefer jthread when a scope or object owns the thread and must reap it before exit—especially where an exception or early return may intervene. Finite tasks needing no cancellation can use it as well; Example 2 below accepts no stop token.
  • Long-lived workers that need cooperative stopping suit jthread: a processing loop, for example, can clean up and return on a stop request, but both the compute path and any wait path must provide a way out; see Part II, §9.1.
  • Use thread for compatibility with C++11/14/17, when a legacy library interface demands std::thread, or when a complete thread-management wrapper already exists. In that case the wrapper or an RAII guard should cover normal and exceptional paths alike, rather than a lone join() at the function’s end. In C++20 you can also pair a standalone stop_source / stop_token with thread; cooperative stopping is not exclusive to jthread.

Automatic reaping does not automatically solve concurrency problems jthread cannot forcibly terminate a thread; if the work waits forever or never exits, destruction may wait forever as well. Do not hold a lock the worker needs while waiting for it. When you want to control when the wait happens, an explicit early join() remains perfectly fine—no reason to switch to thread for that. Both classes support detach(), but once detached the object no longer reaps automatically, so detachment is no universal cure for blocking. jthread also does not protect shared data, extend the lifetime of referenced objects, or forward thread exceptions.

 * @brief std::jthread's RAII automatic reaping and carrying an exception across threads with std::exception_ptr.
 * @details The worker throws and catches a business exception itself, storing the exception object in the main thread's exception_ptr;
 *          when the jthread leaves scope while joinable, it calls request_stop() and then join(), and the main thread handles the exception afterwards.
 *          Expected output "worker failed". See §3.2 in the text.
 */
#include <cassert>   // assert: verifies the exception really made it back
#include <exception> // std::exception_ptr / std::current_exception / std::rethrow_exception
#include <iostream>  // std::cout: prints the exception message
#include <stdexcept> // std::runtime_error: the business exception type used here
#include <thread>    // std::jthread: a C++20 thread handle with automatic reaping

/**
 * @brief Program entry: shows how an exception travels back to the main thread across a thread boundary.
 * @return Implicitly returns 0.
 * @note error is declared outside worker: constructed first and destroyed last, so the reference stays valid throughout the thread's execution.
 */
int main() {
    std::exception_ptr error; // Exception handle owned by the main thread: written by the worker, read by the main thread
    {
        // error outlives the whole worker, so capturing it by reference is safe.
        /** @brief Worker entry: catches any exception and hands it to the main thread. @note error's lifetime is guaranteed by the outer scope. */
        std::jthread worker([&error] {
            try {
                throw std::runtime_error("worker failed"); // Simulates a business failure in the worker
            } catch (...) {
                // Exceptions do not cross thread boundaries by themselves; save a rethrowable exception object first.
                error = std::current_exception();
            }
        });
    } // worker destruction: request_stop first (ignored here), then join to wait for completion

    assert(error); // Non-null means the worker really saved an exception
    try {
        std::rethrow_exception(error); // Rethrow the saved exception on the main thread
    } catch (const std::runtime_error& e) {
        std::cout << e.what() << '\n'; // Prints "worker failed"
    }
}

The output is worker failed. Only one thread writes error, and the main thread reads it after reaping, so no lock protects it. The catch (...) has a clear purpose here: handing any worker exception to the caller rather than silently swallowing it.

An uncaught exception in a thread’s entry function calls std::terminate(); a try/catch around the code that creates the thread catches only failures at creation time, never exceptions thrown while another thread runs. jthread does not forward exceptions automatically. Futures, introduced later, serve as a more natural channel for both results and exceptions.

3.3 Arguments, Captures, and Ownership

When constructing a thread, ordinary arguments are copied or moved into internal storage using their std::decayed types (references and top-level cv-qualifiers stripped, arrays and function names decayed to pointers), then used to call the function. std::ref(x) neither copies x nor extends its lifetime; std::cref(x) is the corresponding const-reference wrapper, appropriate when the thread only reads shared data.

3.3.1 Ordinary Arguments and Reference Wrappers

calculate in Example 1 is an ordinary function: its parameter list fixes what it receives, while std::thread decides how those arguments are stored first and then handed over. std::ref / std::cref alter only the passing semantics; they provide neither locking nor automatic lifetime extension.

Why must you write std::ref(result) here? During construction std::thread first copies or moves the arguments into its own internal storage, using the types with references stripped away (§3.3). Pass result directly and the stored value is an int copy; calling calculate then passes it as an rvalue, which cannot bind to the function’s int& parameter, so thread construction fails at compile time.

std::ref(result) does not copy result; it wraps it as a std::reference_wrapper<int>. The wrapper itself copies safely into internal storage and converts implicitly back to int& when the thread function is invoked, so the function still gets a reference to the main thread’s original result. In short, std::ref resolves the tension between “arguments must first be copied into storage” and “the function expects a reference.” It transfers no ownership and extends no lifetime; keeping the object alive remains the caller’s job. The construction rules are in the C++20 draft’s thread constructors.

std::reference_wrapper<T> offers two common ways to reach the reference: the member get() returns T& explicitly, while the implicit conversion operator operator T& lets the wrapper be used wherever a T& is wanted. std::ref(t) preserves the original object’s constness: an ordinary T gives reference_wrapper<T>, a const object gives reference_wrapper<const T>. std::cref(t) supplies const-reference access; choose between the two just as you would between T& and const T& parameters.

3.3.2 Lambdas: Captures Save an Environment, Parameters Are Call-Time Inputs

A lambda expression creates a closure object—think of it as a callable carrying the data it needs. Its form is [capture list](parameter list) mutable -> return type { body }, with mutable and the return type omitted when appropriate. Captures happen when the closure is created, parameters are supplied when the closure is called; the closure is then copied or moved into the thread like any other callable.

4. Why Shared Mutable State Is Dangerous

4.1 Data Races and Race Conditions

A data race is an error in the C++ memory model: conflicting accesses to one memory location by different threads, at least one of them non-atomic, with no required happens-before ordering between them. The common case is one thread writing an ordinary object while another reads or writes it. A data race causes undefined behavior.

A race condition is a broader logical problem: whether the result is correct depends on how events interleave. Even when every access uses atomics or locks and no data race exists, a logical race can still arise.

4.2 A Mutex Provides Both Mutual Exclusion and Synchronization

A std::mutex does not automatically tag any variable as protected; the programmer must agree on which data each lock guards and ensure every relevant access honors that agreement.

It plays two roles:

  1. Mutual exclusion: only one thread holds the lock at a time, so one whole critical section cannot interleave with another protected critical section.
  2. Synchronization: an unlock synchronizes with a later lock acquisition on that mutex, letting writes from the earlier critical section be observed safely by the later one.

Three member functions deal directly with locking: lock() blocks until it acquires the mutex, try_lock() makes one attempt and reports the outcome immediately, and unlock() releases the mutex and must be called by the owning thread. There is also native_handle(), which returns the platform’s native handle for platform-specific APIs, at the same cost of portability as the similarly named interface in §3.1. Application code should not call these locking members directly: manual pairing tends to miss unlock() on exceptions or early returns. They are the low-level interface beneath lock-management objects (§4.3), which everyday code uses indirectly through RAII guards. A default-constructed std::mutex is unlocked and is neither copyable nor movable. The specification is in the C++20 draft’s mutex class.

    auto add = [&] {  // Add task: captures count and mutex by reference (both outlive the thread execution)

 *          early unlock, and relocking; this is why a condition-variable wait accepts only this guard (§6.1).
 * @note std::timed_mutex and std::mutex are both non-recursive exclusive locks; the former additionally provides

 *       hard deadline for the actual return. Only the first lock is timed; a later lock() may wait indefinitely.
 * @note unique_lock is movable, not copyable.

bool unique_lock_demo(std::timed_mutex& m, int& shared_data) {
    std::unique_lock<std::timed_mutex> lock(m, std::defer_lock); // Associates m only; not held yet
    if (!lock.try_lock_for(std::chrono::milliseconds(10))) { // Timed attempt: 10 ms budget; actual return may be later
        return false; // No lock held: destruction will not unlock; simply abandon this operation
    }
    ++shared_data; // Critical section: owns_lock() is true here
    lock.unlock(); // Release early to do work needing no lock, keeping the critical section short
    // …work without the lock (shared_data may change under other owners meanwhile)…
    lock.lock(); // Relock: business preconditions must be rechecked; do not reuse the pre-unlock decision
    ++shared_data; // Second critical section
    return true; // Still holding the lock at destruction → automatic unlock; exception paths use RAII too
}

Move semantics allow unique_lock to return an “already-locked” guard from a function, handing lock-management responsibility to the caller within the same thread; release() merely abandons management and returns a pointer to the underlying lock without unlocking—a design lock_guard cannot express. The price is maintaining ownership state and more involved usage rules; the real cost depends on the implementation and optimization, and misuse (such as calling unlock() on a guard that holds no lock) throws std::system_error at runtime rather than being caught at compile time.

bool timed_mutex_demo(std::timed_mutex& m, int& shared_data, std::chrono::milliseconds budget) {

        return false; // No lock held: the business abandons or retries later; do not assume "waiting a bit longer always works"

    m.unlock(); // Manual pairing (demonstration only; application code should let a guard's destructor do it, see unique_lock_demo)

    if (!m.try_lock_until(deadline)) { // Tries until deadline
        return false;
    }
    ++shared_data; // Second critical section
    m.unlock();
    return true;
}

A typical case is allowing abandonment once waiting exceeds a business budget, or logging diagnostics after a timeout. The approach cannot promise that an interface never stutters, nor that a periodic task returns by a hard deadline. Ordinary background code can stick with std::mutex and upgrade to timed_mutex only when timeouts are genuinely needed—the real cost depends on implementation and load, so do not assume timed locks must poll or must be slower. The specification is in the C++20 draft’s timed-mutex requirements.

4.4 One-Time Initialization: std::call_once

Some data needs initializing only on first use—a global configuration, for example. The instinct is to “check, then initialize,” but several threads may pass the check at once and initialize repeatedly; concurrent reads and writes of an ordinary variable also create a data race. Hand-rolled double-checked locking is hard to get right as well: even if a thread sees “initialized,” without proper atomics and memory ordering it cannot be sure of seeing the fully initialized result.

With std::call_once you supply a std::once_flag and an initialization function. For one and the same flag, the standard library guarantees:

  • When several threads call concurrently, one executes the initialization function while the others wait.
  • Once that function returns normally, the flag is marked complete and later calls do not initialize again.
  • Other normally returning calls synchronize with that initialization, so the published result can be read safely.

Here “once” means one initialization that completes successfully, not “the initialization function is entered only once.” If initialization throws:

  • The exception propagates to the caller that actually ran the initialization function.
  • The flag is not marked complete, so other waiting calls or later calls may retry.
  • Side effects produced before the failure are not rolled back automatically, and a retry must account for that.

Distinguish the standard’s rule from one implementation: an implementation’s retry timeout does not turn the rule into “throwing also counts as completed initialization.”

In practice you can choose as follows:

  • One initialization state shared across call sites: use call_once and pass the same flag every time. Flags are neither copyable nor resettable; when you need a completely fresh round of initialization, use a new flag.
  • One lazily initialized object inside a single function: prefer a local static. Since C++11 its initialization is thread-safe too, and the code is simpler.

The interface semantics are in the C++20 draft’s call_once specification.

4.5 Write the Invariant First, Then Fix the Critical Section

An invariant is a rule that must hold before and after an operation—a non-negative balance, conservation of the total across accounts, a queue length within its capacity. A lock should protect the entire rule: checking preconditions, computing, and committing the change constitute one business operation, and locking each field separately will not do.

At design time, write down three things: who owns the object; which lock protects which state; and the instant at which the operation takes effect as a whole. That instant is often called the linearization point—a successful CAS that decrements stock, say, or an enqueue completed while holding the queue lock. Observers must honor the protocol too: a consistent snapshot of several fields requires protecting all of them together, and individually safe reads do not make a combined result consistent.

 * @brief Program entry: two threads contend for two locks in opposite nested orders, reproducing ABBA deadlock.
 * @return The normal path implicitly returns 0, but under ABBA it cannot return; it returns normally if no wait cycle forms.
 * @note The locks and counters are constructed first and destroyed last, outliving both threads; if a wait cycle forms the threads cannot exit,

    int count_a = 0;    // Shared counter A: conventionally guarded by mutex_a; the mutex knows nothing of the convention—the whole program must honor it (§4.2)
    int count_b = 0;    // Shared counter B: conventionally guarded by mutex_b
    std::mutex mutex_a; // Mutex protecting count_a
    std::mutex mutex_b; // Mutex protecting count_b

    /** @brief Nests a→b locking each iteration; may hold a while waiting for b when run alongside add_ba. */
    auto add_ab = [&] {
        for (int i = 0; i < 1000; ++i) {
            std::lock_guard<std::mutex> lock_a(mutex_a); // Holds a and will not let go—the "hold" in "hold and wait"
            // Widens the danger window: raises the chance the other thread grabs b at this instant. Removing this line still permits deadlock, just with luck involved.
            std::this_thread::sleep_for(std::chrono::milliseconds(1));
            std::lock_guard<std::mutex> lock_b(mutex_b); // If the other thread holds b, this one waits forever while holding a
            ++count_a; // Both locks must be present to reach here; under deadlock these two lines are never executed
            ++count_b;
        }
    };
    /** @brief Nests b→a locking each iteration, the reverse of add_ab and the other half of the ABBA cycle. */
    auto add_ba = [&] {
        for (int i = 0; i < 1000; ++i) {
            std::lock_guard<std::mutex> lock_b(mutex_b); // Holds b
            std::this_thread::sleep_for(std::chrono::milliseconds(1)); // Also widens the window
            std::lock_guard<std::mutex> lock_a(mutex_a); // If the other thread holds a, this one waits forever while holding b
            ++count_a;
            ++count_b;
        }
    };
    {
        std::jthread first(add_ab);  // Thread one nests locks a→b
        std::jthread second(add_ba); // Thread two nests locks b→a
    } // Both jthreads are destroyed and joined here: under ABBA join never returns; observe with a separate process timeout
    std::cout << count_a << ' ' << count_b << '\n'; // Prints 2000 2000 when no deadlock occurs
}

How to observe it: set a timeout in a separate process. Under ABBA the program produces no output and cannot finish on its own; if it never hits the dangerous interleaving, it may complete and print 2000 2000. sleep_for() only widens the window between the two locks and cannot guarantee that the other side has taken its first lock. Nor can a timeout prove deadlock from a single observation; the fault is established by the cycle in lock dependencies, with the test offering only supplementary evidence.

Why a version with two separate sequential loops does not deadlock. If each thread is written as “finish a loop guarded by lock_guard on a, then start a loop guarded by b,” each thread holds at most one lock at any moment: by the time it contends for the second, the first has long been destroyed and released, so hold-and-wait fails and, absent other wait dependencies, these two locks cannot form an ABBA cycle. The cost is that the two counters are no longer updated as one atomic whole—an observer requiring them to remain in a consistent relation would see a “half-updated” intermediate state.

 * @details Each of the two threads adds 10000 to two counters protected by two mutexes; thread one constructs its unique_locks in a→b

 *       orders fall back into the ABBA deadlock of "each holds one and waits for the other." unique_lock + defer_lock splits
 *       "associate the lock" from "actually lock it," giving std::lock room to try, release what it has taken, and retry.
 */
#include <cassert>  // assert: verifies the final counts

#include <mutex>    // std::mutex / std::unique_lock / std::lock / std::defer_lock
#include <thread>   // std::jthread

/**
 * @brief Program entry: two threads update the same pair of counters concurrently with opposite locking orders.
 * @return Implicitly returns 0.
 * @note The locks and counters are constructed first and destroyed last, outliving both threads. This example deliberately takes both locks
 *       every round to exhibit the multi-lock protocol; real statistics would accumulate locally first and then merge (Part II, §10.2).
 */
int main() {
    int count_a = 0;    // Shared counter A: guarded by mutex_a during concurrency; readable without the lock after join
    int count_b = 0;    // Shared counter B: guarded by mutex_b during concurrency
    std::mutex mutex_a; // Mutex protecting count_a
    std::mutex mutex_b; // Mutex protecting count_b

    /** @brief Associates the two locks in a→b order and adds to both counters; referenced objects outlive the threads. */
    auto add_ab = [&] {
        for (int i = 0; i < 10000; ++i) {
            // defer_lock: constructing the guard only "associates" the mutex and records the management duty; no lock is held yet;
            // the actual locking is deferred to std::lock below, which is what lets the deadlock-avoidance algorithm schedule it.
            std::unique_lock<std::mutex> first(mutex_a, std::defer_lock);  // Associates a, no lock yet
            std::unique_lock<std::mutex> second(mutex_b, std::defer_lock); // Associates b, no lock yet
            // Locking happens here: std::lock can "try—release—retry," and the actual order is decided by the algorithm,
            // independent of the a→b association order above; on success both locks are held.
            std::lock(first, second); // Acquired together by the multi-lock algorithm; both guards own locks on success
            ++count_a; // Both updates land wholly in one protected span
            ++count_b;
        } // Unlocking happens here: each round the guards are destroyed on scope exit and unlock (RAII, exception paths too)
    };
    /** @brief Associates the same two locks in the opposite b→a order; std::lock keeps the threads from forming an ABBA cycle. */
    auto add_ba = [&] {
        for (int i = 0; i < 10000; ++i) {
            // The association order is the reverse of add_ab, but under defer_lock construction takes no lock, so the order has no
            // bearing on mutual exclusion—it merely says which locks go to std::lock; avoiding deadlock is the algorithm's job.
            std::unique_lock<std::mutex> first(mutex_b, std::defer_lock);  // Association order opposite to add_ab
            std::unique_lock<std::mutex> second(mutex_a, std::defer_lock);
            std::lock(first, second); // May try, unlock, and retry internally; no deadlock even when interleaved
            ++count_a;
            ++count_b;
        } // Guards unlock on destruction; only then can the other thread's next attempt succeed
    };
    {
        std::jthread first(add_ab);  // Thread one associates locks a→b
        std::jthread second(add_ba); // Thread two associates locks b→a
    } // Both jthreads are destroyed and joined; reading the counters needs no lock afterwards
    assert(count_a == 20000 && count_b == 20000); // Mutual exclusion plus synchronization prevent lost updates: 2 × 10000
    std::cout << count_a << ' ' << count_b << '\n'; // Prints "20000 20000"
}

Example 9’s std::scoped_lock expresses the same semantics more concisely and is preferred in new code; return to this example’s unique_lock form only when deferred locking, early unlock, or a condition variable is needed.

Read the figure in four moments: ① Association—defer_lock merely makes the guard remember the mutex; ② Acquisition—std::lock tries uniformly, releasing and retrying where necessary; ③ Update—only after a successful return are the two counters modified inside the double-lock critical section; ④ Release—as each round’s scope ends, the two guards are destroyed and unlock separately.

Association order and locking order are two different things unique_lock(m, defer_lock) locks nothing by itself; even without std::lock you could decide the order later with member lock(). Only the directly locking constructor form locks at construction. std::lock prescribes no internal acquisition order and is not a single atomic acquisition; on exception it releases the locks already taken. The “try—release—retry” drawn in the figure must not be read as the only implementation. See the multi-lock algorithm specification.

std::lock avoids deadlock within this acquisition but promises neither fairness nor completion within a bounded time for every thread; waiting on tasks that depend on those locks while holding them still creates an external wait cycle. If deferred or early unlocking is unnecessary, scoped_lock in §5.4 is the more concise choice.

/**
 * @file example08.cpp
 * @brief Concurrent payment simulation: four threads pay from account A to account B, with std::lock's double lock making each payment atomic.
 * @details Each thread attempts 10 payments of 30 yuan each; A starts at 1000 yuan, so at most 33 succeed (990 yuan),
 *          after which insufficient funds cause every attempt to be rejected. Balance check, debit, and credit all happen in one
 *          double-lock critical section: no overdraft, a conserved total, and a success count independent of thread interleaving.
 *          Expected output "paid=33 failed=7 A=10 B=990". See §5.3 in the text.
 */
#include <array>    // std::array: statistic slots owned exclusively by each thread
#include <cassert>  // assert: verifies conservation of funds and the counts
#include <iostream> // std::cout
#include <mutex>    // std::mutex / std::unique_lock / std::lock / std::defer_lock
#include <thread>   // std::jthread

/**
 * @brief Account: the balance and the mutex protecting it are bound together as one unit.
 * @note std::mutex is non-copyable, so Account is non-copyable as well; share it with threads only by reference.
 */
struct Account {
    std::mutex mutex;  ///< Protects this account's balance; any concurrent access must hold it first
    int balance = 0;   ///< Balance in yuan; business invariant: balance >= 0, maintained by pay()'s critical section
};

/**
 * @brief Attempts to pay amount yuan from from to to.
 * @param[in,out] from The paying account; its mutex is held for the duration of this call.
 * @param[in,out] to The receiving account; must be a different object from from.
 * @param amount The payment amount in yuan; required to be positive.
 * @retval true Payment succeeded: from was debited and to credited, both taking effect together.
 * @retval false Insufficient funds: neither account was modified.
 * @note "Check whether funds suffice" and "debit + credit" happen in one double-lock critical section:
 *       at any instant only one thread can make a payment decision about these two accounts, and a concurrent transfer cannot overturn it.
 * @warning You must take both locks at once with std::lock (or std::scoped_lock);
 *          locking them in sequence is an ABBA deadlock when reverse payments coexist (§5.1).
 */
bool pay(Account& from, Account& to, int amount) {
    // ① defer_lock: the two guards only associate their mutexes; no lock is held yet.
    std::unique_lock<std::mutex> from_lock(from.mutex, std::defer_lock);
    std::unique_lock<std::mutex> to_lock(to.mutex, std::defer_lock);
    // ② std::lock takes both locks with a deadlock-avoidance algorithm, whose exact steps are implementation-defined;
    //    therefore a simultaneous reverse payment (B→A) cannot deadlock in this acquisition.
    std::lock(from_lock, to_lock);
    // ③ Critical section begins: this thread has exclusive access to both accounts. The balance check must share a critical section with the debit,
    //    otherwise two threads could each see "sufficient funds" and both debit, overdrawing the account (left side of Figure 5-3).
    if (from.balance < amount) {
        return false; // Insufficient funds: reject; the guards unlock on destruction and neither account changed
    }
    from.balance -= amount; // Debit: indivisible from the check above
    to.balance += amount;   // Credit: in the same critical section as the debit, so any observer holding both account locks sees a conserved total
    return true;
    // ④ On return both guards are destroyed and unlock; only then can other threads observe the new balances.
}

/**
 * @brief Program entry: four threads pay concurrently from A to B; verifies no overdraft, conserved total, and a fixed count.
 * @return Implicitly returns 0.
 * @note The accounts are constructed before the threads and destroyed after them, outliving all payment threads.
 */
int main() {
    Account a;      // Paying account
    Account b;      // Receiving account
    a.balance = 1000; // Single-threaded phase before the threads start: no lock needed for these writes
    b.balance = 0;

    constexpr int kThreads = 4;   // Number of payment threads
    constexpr int kAttempts = 10; // Attempts per thread
    constexpr int kAmount = 30;   // Amount per payment, in yuan
    std::array<int, kThreads> paid{};   // paid[i] is written only by thread i: its successful payments
    std::array<int, kThreads> failed{}; // failed[i] is written only by thread i: its rejected payments

    /**
     * @brief Payment task: repeatedly attempts to pay from A to B, recording the outcome in its own statistic slot.
     * @param index Index of this thread's exclusive array slot; different threads write different elements, so no lock is needed.
     * @note index is taken by value; the accounts are shared by reference and outlive all threads.
     */
    auto payer = [&](int index) {
        for (int i = 0; i < kAttempts; ++i) {
            if (pay(a, b, kAmount)) {
                ++paid[index];   // Writes only its own slot: no competing writes
            } else {
                ++failed[index]; // Rejections due to insufficient funds are counted per slot too
            }
        }
    };
    {
        std::jthread p0(payer, 0); // Four payment threads compete for the same pair of accounts
        std::jthread p1(payer, 1);
        std::jthread p2(payer, 2);
        std::jthread p3(payer, 3);
    } // All jthreads are destroyed and joined here: the main thread proceeds only after every payment finishes

    int total_paid = 0;   // Total successful payments
    int total_failed = 0; // Total rejected payments
    for (int i = 0; i < kThreads; ++i) {
        total_paid += paid[i];     // Slots are read after join, with synchronization guaranteed
        total_failed += failed[i];
    }
    // 1000 yuan at 30 each: exactly 33 succeed (33 × 30 = 990); from the 34th onward, the balance 10 < 30 is rejected.
    // Every payment is atomic, so counts and balances are fixed regardless of how threads interleave.
    assert(total_paid == 33);                          // The success count is fixed
    assert(total_failed == kThreads * kAttempts - 33); // 40 - 33 = 7 rejections
    assert(a.balance == 1000 - 33 * kAmount);          // 10: the balance never goes negative
    assert(b.balance == 33 * kAmount);                 // 990
    assert(a.balance + b.balance == 1000);             // Total conserved: nothing lost, nothing conjured
    std::cout << "paid=" << total_paid << " failed=" << total_failed
              << " A=" << a.balance << " B=" << b.balance << '\n'; // paid=33 failed=7 A=10 B=990
}

The output is paid=33 failed=7 A=10 B=990. Of 40 requests at 30 yuan each, 1000 yuan covers only 33 payments, so the final state is A=10, B=990 regardless of interleaving. That determinism rests on three constraints:

  • No overdraft: the check and the debit share one double-lock critical section, so no other payment can overturn the balance decision.
  • Conserved total: the debit and credit commit together; observers following the double-lock protocol never see an intermediate state.
  • Isolated statistics: each thread writes only its own paid / failed slot, and the main thread aggregates them after join.

std::lock is responsible for avoiding deadlock in this double-lock acquisition; the critical section is responsible for maintaining the funds rule. The two duties are distinct. Real payments would also need amount-overflow checks, persistence, and rollback on failure; this example studies the in-memory concurrency protocol only.

/**
 * @brief Transfers amount from from to to; the balance check and both updates happen in one critical section.
 * @param[in,out] from The source account; its mutex is held during this call.
 * @param[in,out] to The destination account; must be a different object from from.
 * @param amount The transfer amount; non-positive amounts are rejected outright.
 * @note scoped_lock takes both locks in one operation, so the caller need not agree on a locking order.
 * @warning The same account cannot be both from and to: one non-recursive mutex cannot be locked twice.
 * @see The bidirectional transfer in §5.4 of the text
 */
void transfer(Account& from, Account& to, int amount) {
    // The same account cannot pass the same non-recursive mutex as two locks; non-positive amounts are meaningless.
    if (&from == &to || amount <= 0) {
        return;
    }
    std::scoped_lock lock(from.mutex, to.mutex); // Both locks taken by a deadlock-avoidance algorithm; not one hardware atomic action; all released on destruction
    if (from.balance >= amount) { // The balance check must share a critical section with the debit, or the decision goes stale
        from.balance -= amount; // Debits the source while both account locks are held
        to.balance += amount; // Both updates complete with the check, keeping the total unchanged
    }
}

/**
 * @brief Program entry: two threads transfer in opposite directions at the same time.
 * @return Implicitly returns 0.
 */
int main() {
    Account a; // Initial balance 100
    Account b; // Initial balance 100
    {
        /** @brief First worker performs the a-to-b transfer; the references stay alive through join. */
        std::jthread first([&] { transfer(a, b, 10); });  // a → b, 10
        /** @brief Second worker performs the b-to-a transfer; scoped_lock handles the multi-lock order. */
        std::jthread second([&] { transfer(b, a, 20); }); // b → a, 20; no deadlock even with the reverse lock order

    std::cout << a.balance << ' ' << b.balance << '\n'; // Prints "110 90"

scoped_lock prevents deadlock in this multi-lock acquisition but cannot repair every wait cycle in the program. For instance, a thread holding an account lock may wait on another task that itself wants an account lock, and that still deadlocks.

5.5 Livelock and Starvation

  • Livelock: threads keep retrying or yielding to one another, looking busy while no business completes. Two threads might release their locks and retry in lockstep, only to collide again.
  • Starvation: the system makes progress overall, yet one thread goes without a lock or an execution opportunity for a long time. Standard mutexes promise no fair queueing.
  • Deadlock: the participants wait on one another and cannot proceed.

Wrapping try_lock() in a loop is no universal fix; busy-waiting can intensify contention. Simplify resource dependencies first. Where fairness, timeouts, or queue ordering matter, build them into the design instead of assuming the scheduler will look after every thread.

6. Condition Variables: Waiting for State, Not for Notifications

6.1 Why a Lock Alone Is Not Enough: The Need to Wait

A lock answers “who may access the data right now”; a condition variable answers “how to give up execution resources temporarily when the condition is not met.” A consumer finding the queue empty should not keep the lock while checking repeatedly: the producer needs that same lock to put data in.

A correct condition-variable protocol usually has three parts:

  • Shared state: the value of ready, say, or the data held in a queue.
  • Shared predicate: an expression deciding whether progress is possible, such as ready or closed || !queue.empty().
  • One mutex: guarding both state modification and predicate checks, and paired with the wait operation.

First, what a predicate is: it answers “can we go on now?” A predicate is nothing mysterious—just a test returning bool: true means “the condition holds, carry on,” false means “not yet, wait.” With a condition variable the predicate is normally a lambda that reads shared state, not a new kind of data type.

Think of waiting for a meal at a restaurant: ready or the queue contents are the status on the screen, “is my order ready?” is the predicate, and notify_one() merely reminds the customer to look at the screen again. The reminder does not make the food ready; the predicate still decides whether it can be collected.

 */
#include <cassert>            // assert: verifies the delivered result
#include <condition_variable> // std::condition_variable: waiting and notifying
#include <iostream>           // std::cout: prints the final result
#include <mutex>              // std::mutex / std::lock_guard / std::unique_lock
#include <thread>             // std::jthread: creates and reaps the consumer thread

/**
 * @brief Program entry: demonstrates "waiting for state, not for notifications."
 * @return Implicitly returns 0.
 * @note cv, mutex, and all shared data are constructed first and destroyed last, outliving the whole consumer thread.
 */
int main() {
    // The following objects are all owned by the main thread and stay alive until after the consumer ends.
    std::mutex mutex;           // The one lock: protects payload, ready, and checks of the predicate
    std::condition_variable cv; // Only waits and wakes; stores no ready and carries no payload
    bool ready = false;         // Shared predicate state: false means not published, true means data published
    int payload = 0;            // Shared data written by the main thread and read by the consumer
    int result = 0;             // Written only by the consumer during concurrency; read by the main thread after join, with no extra lock

    /**
     * @brief The consumer waits for ready and reads payload under the lock; the main thread reads the result after join.
     * @note [&] captures the main thread's objects by reference but does not extend their lifetimes;
     *       the join below guarantees they are alive throughout use in this example.
     */
    std::jthread consumer([&] {
        // Constructing the unique_lock locks the mutex immediately.
        // Unlike lock_guard, unique_lock lets wait temporarily unlock during the wait and relock on waking.
        std::unique_lock<std::mutex> lock(mutex);

        // wait(lock, pred) is logically equivalent to: while (!pred()) { cv.wait(lock); }
        // 1. The consumer must hold mutex when first checking the predicate.
        // 2. If ready is false, wait performs "unlock mutex and start waiting" as a single atomic step,
        //    so the producer cannot slip in between "checked false" and "started waiting" to change state and lose the notification.
        // 3. While waiting the consumer holds no mutex, so the main thread can enter the producer critical section below.
        // 4. On waking, wait first reacquires mutex, then checks the predicate; if it is still false it waits again.
        //    Thus a spurious wakeup or an unrelated notification cannot be mistaken for "data is ready."
        cv.wait(lock, [&] {
            // The predicate may run repeatedly; here it only reads shared state and changes no business data.
            return ready;
        });

        // On return wait offers a double guarantee: this thread still holds mutex, and the ready it just checked is true.
        // The synchronization established by the lock makes the main thread's write to payload visible here.
        result = payload * 2; // Reads 21 inside the critical section, computes and writes 42
        // As the lambda is left, lock is destroyed and unlocks automatically; then the consumer function returns and the thread ends.
    });

    // From here the main and consumer threads advance concurrently; which one first obtains mutex is up to the scheduler.
    {
        // If the consumer is waiting it has released mutex; if it has not checked yet, it will still contend with this section.
        std::lock_guard<std::mutex> lock(mutex); // Locks on construction, entering the producer critical section
        payload = 21; // First fill in the delivered data
        ready = true; // Then mark the state published; both writes must lie in the same critical section
        // No other lock-holding checker can then see "ready already true but payload not yet written."
    } // Scope exit destroys lock_guard and unlocks; this example chooses to notify after unlocking

    // notify_one wakes one waiter; it carries no data and does not guarantee the predicate holds.
    // Notifying after unlocking reduces the chance the woken thread immediately contends for the lock; notifications are not saved if there is no waiter.
    // If the main thread publishes first, the consumer's first check sees ready == true and never waits at all.
    cv.notify_one();

    // The main thread now waits for the consumer to end; join returns only after the consumer finishes computing.
    // The synchronization established by join makes it safe to read the result written by the consumer here.
    consumer.join();
    assert(result == 42); // Verifies the consumer completed its computation
    std::cout << result << '\n'; // Prints 42
}

6.4 Timeouts, Exit, and Shutdown

The predicate overload of wait_for reports whether the predicate ultimately holds, so do not read “woke up” as “data available.” In a hand-written loop, waiting the full duration again each time can stretch the total wait without bound; compute one absolute deadline from steady_clock and call wait_until repeatedly, or simply use the predicate overload. A timeout is no real-time return guarantee: scheduling delays and reacquiring the mutex can both push the actual return later.

Queues usually use closed || !queue.empty(): on waking, take data if there is any; exit only when “closed and empty.” Set closed under the lock first, then notify the waiters, and finally reap the threads and destroy the queue. That is clearer than sending a “special number” indistinguishable from business data. The task processor in Part II, §11 implements this protocol.

A bounded queue additionally needs producers to wait for capacity: the producer predicate is closed || size < capacity, the consumer predicate closed || !empty. Protect the queue and the closed flag with one mutex, and typically use two condition variables—“not full” and “not empty.” Notify producers after a successful removal, consumers after a successful insertion, and both groups on shutdown. After closing, producers already blocked must wake and reject their enqueues; consumers exit once the queue is drained. A zero capacity should be rejected at construction. Before destruction the caller must close and reap every thread that accesses the queue.

7. From Threads to Tasks: How Results Come Back

7.1 Threads, Tasks, and Shared State

§3.4 used async for one square computation; this chapter explains the result channel behind it and extends it to explicit delivery and queue-based scheduling. First separate “who schedules execution” from “who stores the result,” and only then choose an interface.

A thread is an execution resource, a task is the work to be done, and a future is the handle for obtaining that work’s result. One thread can process many tasks; holding a future does not imply that a thread is already executing the task.

A future<T> connects to the producing end through an asynchronous shared state. Do not confuse this with “sharing business variables at will”: the state is managed by the standard library and holds the result, any exception, and readiness information.

Figure 7-1: An asynchronous result channel. The producing end writes a value or exception into the shared state and makes it ready; the consuming end waits and reads through the future.

Having a state and having a ready state are two different things. A default-constructed future has no associated state; a valid future may still be awaiting its result.

An ordinary future is move-only; after a successful share() the original loses its state. Calling get() or a wait function on a stateless future violates the interface contract, and you cannot count on the implementation throwing a friendly future_error. Make ownership explicit up front, avoid consuming twice, and never let one thread move or consume a handle while another is still accessing it.

Synchronization exists between making a state ready and successfully detecting readiness, so once the result is retrieved the published data can be used safely; returning a reference or pointer still requires the referred-to object to be alive—a future does not extend external objects’ lifetimes. See asynchronous shared state and future consumption semantics.

/**
 * @brief Computes twice input; illegal inputs raise std::invalid_argument through the future channel.
 * @param input Business input; the legal range is [0, INT_MAX / 2], captured by value into the worker.
 * @return input * 2 on the normal path.
 * @throws std::invalid_argument When input lies outside the legal range, rethrown at get() via the shared state.
 * @note result.get() waits until the worker delivers before returning; during unwinding worker is reaped automatically by jthread.
 * @see §7.2, "promise: Explicitly Delivering a Value or Exception," in the text
 */
int compute(int input) {
    std::promise<int> producer;          // Writing end: delivers the value or exception into the shared state
    auto result = producer.get_future(); // Reading end: obtainable once per state; the source has no state after a move, so get it before handing over
    /** @brief The worker owns the moved-in promise and delivers a value or exception. @note input is captured by value; p is modifiable. */
    std::jthread worker([input, p = std::move(producer)]() mutable {
        // Ownership of the promise moves into the thread; mutable allows non-const set_* calls on the captured copy.
        try {
            if (input < 0 || input > std::numeric_limits<int>::max() / 2) {
                throw std::invalid_argument("input outside safe doubling range"); // Business failure, avoiding overflow
            }
            p.set_value(input * 2); // Delivers the value: marks the state ready so the waiter can take it at once
        } catch (...) {
            // Only this thread satisfies the state here; a business failure must still give the waiter an outcome.
            p.set_exception(std::current_exception()); // Delivers the exception, avoiding destruction of an unsatisfied promise
        }
    });
    return result.get(); // Waits if needed; rethrows failures on this thread; worker is still reaped automatically during unwinding
}

/**
 * @brief Program entry: verifies in turn a normal value, a business exception, and a broken promise.
 * @return Implicitly returns 0.

int main() {
    assert(compute(21) == 42); // Normal path: 21 × 2
    const int limit = std::numeric_limits<int>::max() / 2; // Largest safe input
    assert(compute(limit) == limit * 2); // The upper bound is still representable; no signed overflow
    bool overflow_rejected = false; // Records whether an out-of-range input was rejected
    try {
        (void)compute(limit + 1); // Determined illegal in the worker, then propagated through the future
    } catch (const std::invalid_argument&) {
        overflow_rejected = true; // The calling thread received the expected business exception
    }
    assert(overflow_rejected); // An out-of-range input must take the exception channel
    bool received_error = false; // Main thread records whether a business exception arrived via the future
    try {
        (void)compute(-1); // Business-exception path: rethrown onto this thread through the future
    } catch (const std::invalid_argument&) {
        received_error = true; // The expected exception was caught on the calling thread
    }
    assert(received_error); // Verifies a negative input was not treated as a normal result

    std::future<int> abandoned; // Will be associated with a state "destined never to be satisfied"
    {
        std::promise<int> producer; // This scope owns the writing end; we deliberately leave it unsatisfied
        abandoned = producer.get_future(); // Takes the reading end, but the promise never sets a result
    } // The unsatisfied promise is destroyed, storing a broken_promise exception and making the state ready
    bool broken = false; // Distinguishes broken_promise from other future protocol errors
    try {
        (void)abandoned.get(); // Rethrows the future_error saved in the state
    } catch (const std::future_error& e) {
        broken = e.code() == std::make_error_code(std::future_errc::broken_promise); // Checks the exact error code
    }
    assert(broken); // Confirms destroying an unsatisfied writing end makes the state ready with an exception
    std::cout << "value, exception, broken_promise checked\n"; // Printed only if all three result channels pass
}

set_value() normally makes the state ready at the call and does not wait for the thread function to return. After the consumer reads the result, the producing thread may still be doing cleanup; if you need proof that the whole thread has ended, join it regardless. Interfaces such as set_value_at_thread_exit() delay readiness; this article does not go into them.

Destroying an unsatisfied promise gives the consumer broken_promise rather than guaranteeing it waits forever. If the promise stays alive, however, with no path either setting a result or destroying it, the consumer may indeed wait forever. A promise protocol error and the task’s business exception are different sources of error. See the promise specification.

7.3 packaged_task: Bundling a Callable with Its Result Channel

A packaged_task stores a callable and, when the task is invoked, automatically deposits its return value or any thrown exception into the shared state. It creates no thread of its own. It suits a design that wraps a task first and hands it to a worker later.

Key interface points:

  • The template argument is a function signature—packaged_task<int(int)> means “takes an int, yields an int”—and the constructor accepts any callable matching that signature.
  • get_future() succeeds only once per shared state and only on an object that still owns that state. Usually take the reading end before the task is moved away (the moved-from source has no state and throws future_error if called; the new owner that took over the task can still obtain it).
  • operator()(args...) runs the task and delivers the result; each shared state can be satisfied only once. An exception from the target also consumes that state’s delivery opportunity, and invoking an already-run task again throws future_error. To reuse the object, call reset() first: it abandons the old shared state and establishes a new one—a previously obtained future does not become invalid: if the old task ran, that future still holds the original result or exception; if the old task never ran, abandoning the state makes it receive broken_promise. You must call get_future() again against the new state to obtain a new reading end.
  • Move-only and non-copyable; this is why Example 12 hands the task over to a thread with std::move.

The specification is in the C++20 draft’s packaged_task.

7.5 Does Destruction Wait or Not?

You must decide based on the state’s origin, not merely on the type name future:

  • A state created by promise / packaged_task: the future’s destructor releases the association and normally does not wait for the producing thread; that thread’s lifetime is managed separately.
  • A std::async state that selected the async policy: if it is unfinished when the last reference is released, that release may wait for the associated thread to finish. After a move to another owner or a conversion to shared_future, the last releaser may carry the wait as well.
  • A deferred state: if no non-timed wait ever triggered it, destroying it does not run the task simply to “get the work done.”

Destruction and locks Do not destroy the last handle that may wait while holding a lock the task needs, and never treat a future’s destructor as active cancellation.

Neither wait() nor destruction throws a task’s saved exception to the caller; to observe it you need get(). An unretrieved exception may be discarded along with the state. Launch policies and wait rules are in the async specification.

 * @brief std::shared_future: safely distributing one result to several threads for read-only use.
 * @details The promise first delivers a string, then two jthreads each hold a shared_future copy and read its length.
 *          Expected output "5 5". See §7.6 in the text.
 */
#include <array>    // std::array: output slots for the two threads
#include <cassert>  // assert: verifies the read results
#include <future>   // std::promise / std::shared_future
#include <iostream> // std::cout
#include <string>   // std::string: the shared read-only result
#include <thread>   // std::jthread

/**
 * @brief Program entry: publish once, read from several places.
 * @return Implicitly returns 0.
 * @note set_value comes before starting the threads: even if thread creation fails, no thread is left waiting forever for the configuration.
 */
int main() {
    std::promise<std::string> producer; // Writing end for the read-only configuration, owned by the main thread
    auto config = producer.get_future().share(); // Convert to shared_future at once: copyable and repeatably gettable
    // Satisfy the state first, so a thread-creation failure cannot leave a thread waiting forever for the configuration.
    producer.set_value("ready"); // Delivers the shared state; multiple reading ends may now read the same string concurrently
    std::array<std::size_t, 2> lengths{}; // Each element is written by only one thread; no conflict between elements
    {
        /** @brief First thread reads the configuration through its handle copy and writes its own lengths[0]. */
        std::jthread first([config, &lengths] { lengths[0] = config.get().size(); });  // Copies the handle by value
        /** @brief Second thread reads the configuration through its handle copy and writes its own lengths[1]. */
        std::jthread second([config, &lengths] { lengths[1] = config.get().size(); }); // Each holds one copy
    } // Both jthreads are destroyed and joined; the main thread's reads of lengths are then synchronized
    assert(lengths[0] == 5 && lengths[1] == 5); // "ready" has length 5
    std::cout << lengths[0] << ' ' << lengths[1] << '\n'; // Prints "5 5"
}

The output is 5 5. Both threads read the same string read-only and write different array elements; the main thread reads them after reaping. A shared_future guarantees the mechanism for reading the shared state, not the thread safety of mutable objects pointed to from inside the result; sharing a shared_ptr<Mutable> result does not remove the need to synchronize Mutable.
