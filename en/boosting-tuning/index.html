Boosting performance depends heavily on hyperparameters. Unlike random forests, which work out of the box, boosting’s default settings tend to be aggressive (XGBoost’s max_depth=6, eta=0.3), and getting the best out of it takes systematic tuning. This article lays out a general staged tuning framework, gives concrete parameter advice for each algorithm, and offers fixes for the common traps.

10.1 A general strategy: staged tuning

Boosting has many parameters that interact (the learning_rate/n_estimators trade-off, for one). A blind full grid search is both expensive and prone to landing in a local optimum. Staged tuning — layering the work by importance, refining step by step — works better.

The logic of staged tuning

Stage 1: control the complexity of a single tree

Boosting is a weighted combination of weak learners. If a single weak learner is too complex (a very deep tree, say), the model overfits even with few rounds. So the first step is to limit how much one tree can express:

  • max_depth (XGBoost, CatBoost) or num_leaves (LightGBM): cap depth or leaf count. Rules of thumb:

    • Shallow (max_depth=3~5): suits noisy data with simple feature interactions; generalizes well
    • Medium (max_depth=6~8): suits moderately complex interactions; the range competitions tend to use
    • Deep (max_depth=10+): only for large, low-noise data with complex interactions, and only with strong regularization

  • min_child_weight (XGBoost: a lower bound on the sum of second derivatives in a child, default 1) or min_data_in_leaf (LightGBM: minimum samples per leaf, default 20): raising it makes the model more conservative and stops leaves from overfitting a handful of samples. Under squared loss the Hessian is 1, so min_child_weight is just a minimum sample count; under log loss the Hessian is $p(1-p)$, so samples the model is confident about ($p$ near 0 or 1) contribute less. Typical values: min_child_weight=1~10 for classification, 3~30 for regression.

  • gamma / min_split_gain: the minimum loss reduction a split must deliver. Only splits whose gain exceeds it are allowed. Larger means simpler trees. Typical range: 0 to 5.

Stage 2: add randomness to cut variance

Having bounded single-tree complexity, sampling and regularization bring down the ensemble’s variance further:

  • subsample (row sampling): each round trains the current tree on a random subset of samples. Typical 0.6-0.9. Smaller means more randomness and faster training, but possibly more iterations to converge.

  • colsample_bytree / colsample_bylevel (column sampling): randomly select some features per tree or per level. This decorrelates trees much as random forests do and is especially effective on high-dimensional data. Typical 0.6-1.0. Note XGBoost’s colsample_by* settings compound: each level samples from the features this tree already selected, so with colsample_bytree=0.8, colsample_bylevel=0.8 each level effectively sees about 64% of the features.

  • lambda / reg_lambda (L2): penalizes squared leaf weights, keeping any single leaf output from growing too large. XGBoost defaults to 1, LightGBM’s lambda_l2 to 0, CatBoost’s l2_leaf_reg to 3; raising it smooths the model. Typical 0.1-10.

  • alpha / reg_alpha (L1): penalizes leaf weights in absolute value, shrinking some to exactly 0 (Lasso-like). XGBoost and LightGBM default to 0; CatBoost has no matching leaf-L1 parameter. Typical 0-1. Note this sparsifies leaf outputs, which isn’t the same as feature selection.

Stage 3: tune learning rate and iteration count together

learning_rate ($\eta$) and n_estimators trade off:

$$ \eta \times M \approx \text{const} $$

where $\eta$ is learning_rate (written as the shrinkage coefficient $\nu$ in Chapter 5) and $M$ is n_estimators.

This is a rough empirical relation, not an exact conservation law. It rests on Friedman’s (2001) observation that a smaller learning rate needs more iterations but usually yields lower test error; ESL §10.12 accordingly recommends a small rate (say $\eta < 0.1$) with early stopping to pick $M$. Concrete guidance (a starting point only — let early stopping decide the actual count):

learning_rateSuggested n_estimatorsWhen
0.350-100Quick experiments, large datasets
0.1100-500Standard starting point
0.05500-1000Chasing higher accuracy
0.011000-5000Fine tuning, small datasets
0.0015000+Very fine optimization, complex interactions

In practice, fix learning_rate=0.1, use early stopping to find a suitable n_estimators, then lower the rate and raise n_estimators to the equivalent count early stopping gave, and repeat until performance plateaus.

10.2 Tuning AdaBoost

sklearn’s AdaBoostClassifier has few parameters, but there’s still room.

ParameterMeaningRangeAdvice
n_estimatorsNumber of weak classifiers50-1000Default 50; tune with learning_rate. sklearn’s AdaBoost has no built-in early stopping, so evaluate round by round on a validation set with staged_predict / staged_score and pick the best count
learning_rateShrinkage on each weak classifier’s weight0.01-1.0The default 1.0 usually works; if overfitting, drop to 0.1-0.5 and raise n_estimators
estimatorBase learnerDecision stumps / treesDefault DecisionTreeClassifier(max_depth=1); for complex data try max_depth=2~3
algorithmAlgorithm typeRemovedSAMME.R deprecated in 1.4 and removed in 1.6; the algorithm parameter deprecated in 1.6 and removed in 1.8. Newer versions use SAMME exclusively and raise an error if you pass this argument

AdaBoost-specific notes:

  1. Base-learner depth: the theory only requires weak learners slightly better than chance, so stumps (max_depth=1) are the default and the common choice. But a stump can only express one feature’s main effect and can’t capture interactions; ESL §10.11 notes that for boosting a leaf count $J$ between 4 and 8 usually works well. So max_depth=2~3 is also worth trying via cross-validation, while very deep trees make each round fit too strongly and soak up noise.

  2. The learning_rate / n_estimators trade-off: sklearn’s docs state it plainly — lowering learning_rate usually requires more n_estimators to reach a similar level of fitting. There’s no fixed product relation; settle it with staged_score or cross-validation.

  3. Noisy data: AdaBoost is very sensitive to noise and outliers. With heavy noise, don’t spend a lot of time tuning it; switch to a gradient boosting method that handles noise better (XGBoost with L1/L2 regularization, say).

sklearn’s GradientBoostingClassifier/GradientBoostingRegressor are richly parameterized, with plenty of room to tune.

Regression: ‘squared_error’, ‘absolute_error’, ‘huber’, ‘quantile’‘huber’ for noisy data; ‘quantile’ for prediction intervals
learning_rateLearning rate (shrinkage)0.01-0.3Start at 0.1; drop to 0.05 for the final fit
n_estimatorsNumber of trees100-2000Tune with learning_rate and early stopping
subsampleSubsample fraction0.5-1.00.8 is a general starting point; 0.5-0.7 cuts variance noticeably
max_depthMaximum depth3-8One of the most important parameters, default 3; 3-6 is often best, confirmed by cross-validation
max_featuresFeature sampling per tree‘sqrt’, ’log2’, 0.5-1.0‘sqrt’ for high-dimensional data; 1.0 for low-dimensional
min_samples_splitMinimum samples to split2-50Default 2; raising it guards against overfitting
min_samples_leafMinimum samples per leaf1-50Default 1; 5+ for regression, 1-5 for classification

Suggested order for GBM:

  1. Fix learning_rate=0.1 and n_estimators=500 (generously large), set n_iter_no_change for early stopping, and find the best iteration count (check the n_estimators_ attribute afterwards).
  2. Search max_depth=[3, 4, 5, 6], the most influential parameter.
  3. Around the best max_depth, adjust min_samples_leaf and min_samples_split.
  4. Introduce subsample=0.8 and max_features='sqrt' (if there are more than 30 features).
  5. Lower learning_rate to 0.05 or 0.01, scale n_estimators up accordingly, and early stop again.

Notes on HistGradientBoosting:

HistGradientBoostingClassifier / HistGradientBoostingRegressor arrived as experimental in sklearn 0.21 and became a stable API in 1.0 (no more enable_hist_gradient_boosting). The docs note it is much faster than GradientBoostingClassifier once you have thousands of samples ($n \ge 10\,000$), so it should be the first choice on large datasets. Its parameters differ somewhat from classic GBM:

  • max_iter (default 100) instead of n_estimators
  • Both max_leaf_nodes (default 31) and max_depth (default None, unlimited); complexity is controlled by leaf count by default, much like LightGBM’s num_leaves
  • Regularization via l2_regularization (default 0) and min_samples_leaf (default 20)
  • max_bins defaults to 255 (also the maximum), with one bin reserved for missing values
  • Native missing-value support (NaN): each split learns whether missing values go left or right
  • Native categorical support (categorical_features, defaulting to 'from_dtype' in recent versions, which detects category columns in a DataFrame)
  • Built-in early stopping: with early_stopping='auto' it’s enabled only when there are more than 10,000 samples (or, from 1.7, when X_val/y_val are passed to fit)
  • Supports monotonic_cst (monotonic constraints), interaction_cst (interaction constraints) and class_weight (1.2+)

10.4 Tuning XGBoost

XGBoost has the most elaborate parameter set, but staged tuning handles it systematically.

ParameterAliasMeaningRangeAdvice
etalearning_rateLearning rate0.01-0.3Start at 0.1; 0.01-0.05 for the final fit
max_depth-Maximum depth3-10The key parameter; start at 5-6; 3-4 for small or noisy data
min_child_weight-Minimum Hessian sum in a child1-30Default 1; 1-5 for classification, 3-10 for regression; larger is more conservative
gammamin_split_lossMinimum split gain0-10Default 0, meaning any positive-gain split is allowed; raise it to fight overfitting
lambdareg_lambdaL2 coefficient0.1-10Default 1; larger smooths the model
alphareg_alphaL1 coefficient0-1Default 0; 0.1-0.5 when sparsity is wanted
subsample-Row sampling fraction0.5-1.0Default 1; 0.8 is a general start; 0.6 on large data
colsample_bytree-Column sampling per tree0.5-1.0Default 1; start at 0.8; 0.6-0.8 on high-dimensional data
colsample_bylevel-Column sampling per level0.5-1.0Default 1; samples from this tree’s chosen features, multiplying with colsample_bytree
scale_pos_weight-Multiplier on positive-class weight1-99Default 1; for class imbalance the docs suggest sum(negative) / sum(positive) (see trap 4)

Staged tuning in practice:

Step 1 — a first quick search: fix learning_rate=0.1 and n_estimators=1000, set early_stopping_rounds=50 in the constructor (moved out of fit() in XGBoost 2.1), and find the best iteration count. Search combinations of max_depth=[3, 5, 7] and min_child_weight=[1, 3, 5]. This step establishes the rough complexity range.

Step 2 — refine regularization: around the best max_depth and min_child_weight from step 1, search gamma=[0, 0.1, 0.5, 1, 2], lambda=[0.1, 1, 3] and alpha=[0, 0.1, 0.5]. gamma tends to pay off most when the data are noisy.

Step 3 — tune sampling: search subsample=[0.6, 0.8, 1.0] and colsample_bytree=[0.6, 0.8, 1.0]. Note that subsample < 1.0 lowers variance but slows convergence, so you may need more iterations.

Step 4 — lower the rate and refine: drop learning_rate to 0.05 or 0.01, raise n_estimators following learning_rate * n_estimators ≈ 0.1 * n_estimators_initial, and early stop for the new best count. Repeat the local refinements from steps 2-3.

XGBoost-specific tips:

  • tree_method='hist' (the default since 2.0): histogram methods are far faster than exact greedy with almost no accuracy cost on large data. For GPU training use device='cuda' with tree_method='hist'; the old tree_method='gpu_hist' was deprecated in 2.0 and removed in 3.1.
  • grow_policy='lossguide': enables LightGBM-style leaf-wise growth (hist / approx only), usually paired with max_leaves; it can win accuracy on some datasets but demands stricter regularization.
  • max_bin: histogram bin count, default 256. Raising it to 512 or 1024 can help on data with complex feature distributions, at more memory and compute.

10.5 Tuning LightGBM

Leaf-wise growth makes LightGBM’s parameter set markedly different from XGBoost’s: num_leaves replaces max_depth as the core complexity control.

ParameterMeaningRangeAdvice
num_leavesMaximum leaves15-150The key parameter, default 31; controls model complexity. With max_depth = $d$, set it well below $2^d$ (the official example: 70-80 when $d=7$)
max_depthMaximum depth-1 (unlimited) to 12Works with num_leaves; -1 means only num_leaves binds; set it explicitly (6-10, say)

n_estimators / num_boost_roundIterations100-5000Use with early stopping

bagging_fractionData sampling fraction0.5-1.0Alias subsample; only takes effect with bagging_freq > 0
bagging_freqSampling frequency1-10Default 0 (no sampling); resample every bagging_freq rounds; 1 means every round
min_data_in_leafMinimum samples per leaf5-100Default 20 (alias min_child_samples); the key guard against leaf-wise overfitting
lambda_l1L1 regularization0-1Default 0 (alias reg_alpha); L1 penalty on leaf weights
lambda_l2L2 regularization0-10Default 0 (alias reg_lambda); 0.1-1 usually suffices
min_gain_to_splitMinimum split gain0-5Corresponds to gamma; default 0 (alias min_split_gain)
cat_smoothCategorical smoothing1-100Default 10; dampens noise in categorical features, especially useful for rare categories
cat_l2L2 on categorical features1-100Default 10; L2 regularization within categorical splits

LightGBM-specific notes:

  1. num_leaves and max_depth together: under leaf-wise growth, num_leaves is the main complexity control. But constraining only num_leaves can produce unbalanced trees with some branches very deep and others very shallow. A rough relation:

    $$ L_{\max} \approx 0.6 \times 2^d $$

    where $L_{\max}$ is num_leaves and $d$ is max_depth. This is only a heuristic, grounded in LightGBM’s official tuning example: at max_depth=7 a depth-wise tree already performs well, and setting num_leaves to $2^7=127$ may overfit, while 70-80 often beats depth-wise. If you set num_leaves without limiting max_depth, the model can overfit along some paths.

  2. Declaring categorical features correctly: pandas DataFrame columns with dtype category are detected automatically under the default categorical_feature='auto'; numpy input needs explicit column indices via categorical_feature. Category values are cast to int32 (pandas categories use their integer codes), and negative values count as missing, so integer codes should be non-negative. LightGBM partitions categories specifically (one-vs-other when there are at most max_cat_to_onehot categories, default 4), which usually beats one-hot encoding.

  3. GOSS parameters (top_rate, other_rate): gradient-based one-side sampling keeps the samples with the largest absolute gradients (fraction top_rate, default 0.2) and draws randomly from the rest (fraction other_rate, default 0.1). GOSS is off by default: from 4.0, set data_sample_strategy='goss' (the old boosting_type='goss' still runs but is no longer an official boosting option). It speeds training further at a slight accuracy cost.

  4. force_row_wise and force_col_wise: these control how histograms are built on CPU (by row or by column). Both default to false, in which case LightGBM tries both and picks the faster. The docs advise col-wise when there are many features, many total bins, many threads (over 20) or memory is tight; row-wise when there are many samples but few bins and few threads (16 or fewer) — though it doubles the Dataset’s memory. Setting it manually skips the test.

10.6 Tuning CatBoost

CatBoost is known for strong defaults, but understanding the parameters still helps in specific situations.

ParameterMeaningRangeAdvice

CatBoost-specific advice:

  1. Start with the defaults: CatBoost’s defaults already perform well on many datasets. Establish a baseline with them, and tune only if results fall short.

  2. Only a few parameters usually need attention: typically depth (4-8), l2_leaf_reg (1-10) and learning_rate (with iterations). Adjust random_strength and bagging_temperature when overfitting.

  3. Ordered boosting is controlled by boosting_type (values 'Ordered' or 'Plain'; there is no parameter named ordered_boosting in CatBoost). The default depends on device and data: 'Plain' on CPU; on GPU 'Ordered' when there are at most 50,000 samples and the task isn’t multiclass, otherwise 'Plain'. The docs say 'Ordered' usually gives better quality on small datasets but is slower than 'Plain', so small datasets are where it’s worth trying boosting_type='Ordered' explicitly.

  4. GPU training: CatBoost 1.2+ has a substantially faster GPU implementation, especially on large datasets and at greater depths. Just set task_type='GPU' and devices='0'.

10.7 Using early stopping

Early stopping is one of the most effective ways to keep boosting from overfitting. The idea: monitor validation loss during training, stop when it hasn’t improved for some number of rounds, and use the round with the lowest validation loss as the final model (whether each library rolls back to the best round automatically is in the table below).

The principle:

Because boosting trains iteratively, training loss falls almost monotonically, while validation loss typically follows a U shape — down and then up. Early stopping halts at the minimum of validation loss and skips the overfitting that later rounds would bring.

$$ t^{*} = \mathop{\arg\min}_{1 \le t \le T} L_{\text{val}}(t), \qquad \text{stop at round } T \text{ if } T - t^{*} \ge p $$

where $L_{\text{val}}(t)$ is the loss of the model after $t$ rounds on the validation set and $p$ is the patience. In words: stop when the lowest validation loss hasn’t been beaten in the last $p$ rounds, and take the first $t^{*}$ rounds as the final model.

Best practices:

  1. The validation set must be separate from both training data and the final test set: a set used for early stopping has taken part in model selection, so it can’t report final performance. Under cross-validation, early stop separately inside each fold.

  2. Setting patience:

    • 50-100 rounds is common; with a large learning rate (0.1-0.3), 10-30 often suffices
    • The smaller the rate, the smaller each round’s improvement, so patience should grow; the smaller and noisier the validation set, the larger it should be, to avoid stopping too soon
    • For implementations that roll back to the best round (XGBoost’s sklearn predict, LightGBM, CatBoost’s use_best_model), excess patience mostly costs compute — the final model won’t include trees after the best round

  3. Early stopping and n_estimators: set n_estimators generously (5000, say) and let early stopping decide the real count. That’s more reliable than guessing.

  4. Stability across runs: the stopping point depends on randomness (from subsample, for instance), so fix random_state and average over several runs, or early stop inside cross-validation.

10.8 Cross-validation

Cross-validation (CV) is the gold standard for estimating generalization and selecting hyperparameters. For boosting, pay particular attention to how data are split and how early stopping interacts with the folds.

K-fold cross-validation:

Standard K-fold splits the data into K parts and rotates which part is held out. For boosting:

  • Early stop inside each fold: within each fold’s training, split the fold’s training data further into a sub-training set and an early-stopping set. In 5-fold CV, for instance, each fold trains on 80% of the data, holds out 10% of that for early stopping, and fits on the remaining 70%.
  • Record the best iteration per fold: folds may disagree on the best n_estimators. The final count can be the mean or median across folds, or you can simply retrain on all the data.
  • Aggregate feature importance: each fold yields an importance vector; averaging them across folds gives a steadier final ranking.

Stratified K-fold (classification):

For imbalanced classification, use StratifiedKFold so each fold preserves the overall class proportions. With plain K-fold some folds may lack minority samples, which either breaks training or biases the estimate.

Time series data:

Boosting is often used for time series forecasting (sales, stock prices). Standard random K-fold then causes data leakage (predicting the past with the future). Use time series splitting; if features include lags or rolling-window statistics, TimeSeriesSplit(gap=...) (sklearn 0.24+) leaves a gap between train and validation so windows can’t straddle the boundary:

10.9 Common traps and fixes

Trap 1: overfitting

Symptoms: excellent on the training set (AUC around 0.99), poor on validation (AUC around 0.70), a wide gap between them.

Causes:

  • Single trees too complex (max_depth or num_leaves too large)
  • Too many iterations with no early stopping
  • Regularization too weak (lambda, alpha too small)
  • Little data but high model complexity
  • The model memorizing noise or outliers

Fixes:

  1. Lower max_depth (XGBoost) or num_leaves (LightGBM), and lower max_depth as an extra bound
  2. Use early stopping (early_stopping_rounds) with a generous n_estimators
  3. Raise min_child_weight / min_data_in_leaf so leaves can’t overfit single samples
  4. Add subsample (0.6-0.8) and colsample_bytree (0.6-0.8) to cut variance
  5. Raise lambda (L2) and alpha (L1) to smooth the model
  6. Clip or Winsorize outliers

Trap 2: underfitting

Symptoms: poor on both training and validation; the model hasn’t captured the patterns.

Causes:

  • Single trees too simple (max_depth=1 or num_leaves too small)
  • Learning rate too small, or too few iterations
  • Regularization too strong (lambda or gamma too large)
  • No real relationship between features and target, or insufficient feature engineering

Fixes:

  1. Raise max_depth or num_leaves so the model can learn more complex interactions
  2. Raise learning_rate (from 0.01 to 0.1, say) or increase n_estimators
  3. Lower gamma and lambda to relax the regularization
  4. Revisit feature engineering: is an important feature missing? Are features scaled and encoded sensibly?
  5. Check data quality: are the labels right? Are the distributions plausible?

Trap 3: data leakage

Symptoms: excellent offline, sharply worse in production. Or CV scores far above an independent test set.

Causes:

  • Target leakage: a feature contains information only available after prediction (using “did the user buy tomorrow” to predict “will the user buy tomorrow”)
  • Temporal leakage: predicting the past with the future (failing to use TimeSeriesSplit)
  • Preprocessing leakage: standardizing, imputing or target-encoding over the whole dataset before cross-validation, which leaks validation information into training
  • Sample leakage: duplicates between train and test (the same user in both)

Fixes:

  1. The Pipeline rule: wrap every preprocessing step (scaling, encoding, imputation) in a Pipeline so it’s fitted on each fold’s training data and applied to validation, keeping validation information out
  2. Strict temporal splitting: use TimeSeriesSplit so training data strictly precede validation data
  3. Careful target encoding: if you use target encoding, compute it per fold from the training data only, never globally in advance
  4. CatBoost’s Ordered TS: for categorical features, CatBoost’s native support uses only the labels of samples “before” the current one, which markedly reduces the leakage target encoding brings
  5. Keep the early-stopping set separate from the test set: if the test set is used for early stopping or tuning, its score is no longer unbiased (see the Bayesian optimization example in 10.10)

Trap 4: class imbalance

Symptoms: in binary classification the majority class is predicted well but minority recall is very low (in fraud detection, 99% of transactions are legitimate, so predicting “all legitimate” already gives 99% accuracy).

Fixes:

  1. Sample weights: each library’s parameter, so the algorithm attends to the minority class:
LibraryParameterNotes
XGBoostscale_pos_weightThe docs suggest sum(negative) / sum(positive)
LightGBMis_unbalance=True or scale_pos_weightPick one, not both; the sklearn interface also accepts class_weight
CatBoostauto_class_weights='Balanced' / 'SqrtBalanced', or scale_pos_weightDon’t combine with class_weights
sklearnHistGradientBoostingClassifier(class_weight='balanced') (1.2+)GradientBoostingClassifier has no class_weight; pass weights via fit(sample_weight=...)

Note that reweighting changes what predicted probabilities mean. XGBoost’s tuning docs point out that if you only care about a ranking metric such as AUC, scale_pos_weight is fine; if you need accurate probabilities, don’t rebalance the data, and instead set max_delta_step to a finite value (1, say) to help convergence. LightGBM’s docs likewise warn that is_unbalance / scale_pos_weight degrade per-sample probability estimates. When probabilities matter, train with weights and then calibrate (sklearn’s CalibratedClassifierCV, for instance). 2. Resampling (only on training folds; validation and test data keep the original distribution — imbalanced-learn’s Pipeline helps enforce this):

  • Oversampling (SMOTE): oversample the minority class in the training set
  • Undersampling: undersample the majority class (watch for information loss)
  • Combined sampling (SMOTEENN, say): oversampling plus undersampling
  1. Change the metric: replace accuracy with AUC-ROC, AUC-PR (area under the precision-recall curve), F1 or balanced accuracy
  2. Adjust the threshold: the default 0.5 may be wrong for imbalanced data. Pick the operating threshold that fits the business need (precision versus recall), using the ROC or PR curve
  3. Focal loss: in extreme imbalance (1:1000 or worse), a custom focal loss down-weights easy samples and concentrates on the hard ones

from sklearn.model_selection import GridSearchCV, StratifiedKFold
from xgboost import XGBClassifier

# parameter grid (only two key parameters, so 3*3=9 combinations)
param_grid = {
    'max_depth': [3, 5, 7],           # tree depth: conservative to moderate
    'min_child_weight': [1, 3, 5]     # minimum child weight: against overfitting
}

# base model with fixed parameters
xgb_base = XGBClassifier(
    learning_rate=0.1,               # fixed rate; not optimized during the grid search
    n_estimators=300,                # fixed iteration count (GridSearchCV does no early stopping; see the note below)
    subsample=0.8,                   # fixed row sampling
    colsample_bytree=0.8,            # fixed column sampling
    reg_lambda=1,                    # fixed L2 regularization
    random_state=42,                 # fixed seed for reproducibility
    eval_metric='logloss'            # evaluation metric
)

# stratified K-fold (5 folds, preserving class proportions)
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)

# build the search
grid_search = GridSearchCV(
    estimator=xgb_base,              # base model
    param_grid=param_grid,           # parameter grid
    scoring='roc_auc',               # optimize AUC
    cv=cv,                           # cross-validation scheme
    n_jobs=-1,                       # in parallel on all cores
    verbose=2                        # verbose progress
)

# run the search.
# note: do NOT pass the test set as eval_set for early stopping inside GridSearchCV,
# which would leak data.
grid_search.fit(X_train, y_train)

# report the best result
print(f"Best params: {grid_search.best_params_}")
print(f"Best CV AUC: {grid_search.best_score_:.4f}")
print(f"Best model test AUC: {grid_search.score(X_test, y_test):.4f}")

# grab the best model
# note: early stopping wasn't used, so best_estimator_.best_iteration doesn't exist
# (accessing it raises AttributeError). To settle the iteration count, retrain with
# the chosen parameters on a separate validation set and early_stopping_rounds.
best_model = grid_search.best_estimator_
print(f"Trees used by the best model: {best_model.get_booster().num_boosted_rounds()}")

Bayesian optimization

Bayesian optimization — more generally, sequential model-based optimization (SMBO) — fits a surrogate model to the results so far and uses an acquisition function to choose the next point to evaluate, which usually finds better parameters than random search for the same number of evaluations. The classic surrogate is a Gaussian process; Optuna’s default TPESampler uses TPE (Tree-structured Parzen Estimator, Bergstra et al., 2011), which splits existing trials into “good” and “bad” groups by objective value, models each with a kernel density estimate $\ell(x)$ and $g(x)$, and prefers parameters with a large ratio $\ell(x)/g(x)$. Optuna (Akiba et al., 2019) is the recommended library.

Bergstra & Bengio (2012) showed that when only a few hyperparameters really matter, random search beats grid search — which is why full grids aren’t recommended when there are many parameters.

import optuna
from sklearn.metrics import roc_auc_score
from sklearn.model_selection import cross_val_score, train_test_split

def objective(trial):
    """
    Optuna objective: defines the search space and the evaluation.
    The trial object offers suggest methods that sample from the given distributions.
    """
    # define the search space
    params = {
        'max_depth': trial.suggest_int('max_depth', 3, 10),
        'min_child_weight': trial.suggest_int('min_child_weight', 1, 10),
        'subsample': trial.suggest_float('subsample', 0.6, 1.0),
        'colsample_bytree': trial.suggest_float('colsample_bytree', 0.6, 1.0),
        'reg_lambda': trial.suggest_float('reg_lambda', 0.1, 10.0, log=True),
        'reg_alpha': trial.suggest_float('reg_alpha', 0.0, 1.0),
        'gamma': trial.suggest_float('gamma', 0.0, 5.0),
        'learning_rate': 0.1,  # fixed; lower it in the refinement stage
        'n_estimators': 300,     # fixed iteration count (no early stopping inside CV)
        'random_state': 42,
        'eval_metric': 'logloss'
    }

    # build the model
    model = XGBClassifier(**params)

    # evaluate by cross-validation (3-fold for brevity; 5-fold in production)
    # note: early stopping inside CV needs a more involved setup (a validation set
    # per fold), so the iteration count is fixed here.
    scores = cross_val_score(
        model, X_train, y_train,
        cv=StratifiedKFold(n_splits=3, shuffle=True, random_state=42),
        scoring='roc_auc',
        n_jobs=-1
    )

    # return the mean AUC (Optuna minimizes by default, so the study below sets
    # direction='maximize')
    return scores.mean()

# create the study
study = optuna.create_study(
    direction='maximize',              # maximize AUC
    sampler=optuna.samplers.TPESampler(seed=42)  # TPE sampler, the core of the Bayesian approach
)

# run 100 trials
study.optimize(objective, n_trials=100, show_progress_bar=True)

# report the best result
print(f"Best AUC: {study.best_value:.4f}")
print(f"Best params: {study.best_params}")

# retrain with the best parameters on the full training data (early stopping allowed)
best_params = study.best_params
best_params.update({
    'learning_rate': 0.05,             # lower the rate for the final fit
    'n_estimators': 2000,
    'random_state': 42,
    'eval_metric': 'logloss',
    'early_stopping_rounds': 50
})

# the early-stopping validation set must come out of the training data; using the
# test set would make its score optimistic (leakage)
X_tr_final, X_val_final, y_tr_final, y_val_final = train_test_split(
    X_train, y_train, test_size=0.15, stratify=y_train, random_state=42
)

final_model = XGBClassifier(**best_params)
final_model.fit(
    X_tr_final, y_tr_final,
    eval_set=[(X_val_final, y_val_final)],
    verbose=False
)
print(f"Best iteration: {final_model.best_iteration}")

print(f"Final model test AUC: {roc_auc_score(y_test, final_model.predict_proba(X_test)[:, 1]):.4f}")

10.11 Monotonic and interaction constraints

In credit risk, pricing and medicine, business requirements often impose prior knowledge on the model: “higher income shouldn’t raise default probability,” “a larger house shouldn’t be valued lower.” Left to tuning alone, a model can learn sawtooth relationships that violate common sense in sparse regions. All four libraries support monotonic constraints: 1 means predictions are monotonically non-decreasing in that feature, -1 non-increasing, and 0 unconstrained.

LibraryMonotonic constraintInteraction constraintNotes
XGBoostmonotone_constraintsinteraction_constraintsAccepts a tuple (in feature order) or a dict keyed by feature name; interaction constraints are nested lists such as [[0, 1], [2, 3, 4]]
LightGBMmonotone_constraintsinteraction_constraintsMust list all features in order; monotone_constraints_method offers basic (default, fastest), intermediate and advanced
CatBoostmonotone_constraints—Numeric features only
sklearn HistGBmonotonic_cstinteraction_cstFor classification, monotonic constraints apply only to binary problems, acting on the positive-class probability

Interaction constraints restrict which features may appear on the same root-to-leaf path. [[0, 1], [2, 3, 4]], for instance, allows interaction within features 0 and 1 and within 2, 3 and 4, but not across the two groups. They’re commonly used to improve interpretability, or as regularization when some features are known to act independently.

Constraints usually cost some training fit, but the model matches the business logic better and behaves more sensibly out of distribution. Whether a constraint is worth it should be judged by validation metrics together with business review. import numpy as np
from xgboost import XGBRegressor
from lightgbm import LGBMRegressor
from catboost import CatBoostRegressor
from sklearn.ensemble import HistGradientBoostingRegressor

# synthetic data: y rises monotonically with x0, varies non-monotonically with x1, plus noise
rng = np.random.default_rng(42)
X_mono = rng.uniform(0, 1, size=(2000, 2))
y_mono = 5 * X_mono[:, 0] + np.sin(10 * X_mono[:, 1]) + rng.normal(0, 1.0, 2000)

# require predictions non-decreasing in x0 (1) and unconstrained in x1 (0)
models = {
    'XGBoost': XGBRegressor(n_estimators=200, max_depth=4, monotone_constraints=(1, 0)),
    'LightGBM': LGBMRegressor(n_estimators=200, monotone_constraints=[1, 0], verbose=-1),
    'CatBoost': CatBoostRegressor(iterations=200, monotone_constraints=[1, 0], verbose=False),
    'HistGB': HistGradientBoostingRegressor(max_iter=200, monotonic_cst=[1, 0]),
}

# hold x1 fixed and sweep x0 from 0 to 1, checking monotonicity
grid = np.column_stack([np.linspace(0, 1, 201), np.full(201, 0.3)])
for name, model in models.items():
    model.fit(X_mono, y_mono)
    pred = model.predict(grid)
    print(f"{name:<9} monotone non-decreasing in x0: {bool(np.all(np.diff(pred) >= -1e-9))}")

Run under XGBoost 3.4.1, LightGBM 4.7.0, CatBoost 1.2.10 and scikit-learn 1.9.1, all four models print True.
