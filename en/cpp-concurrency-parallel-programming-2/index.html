This article is Part II of the C++ Concurrency and Parallel Programming series. Part I covered the execution model, thread lifecycles, mutexes, condition variables, and futures as a result channel; this installment continues with atomics and memory order, C++20’s cancellation and coordination facilities (stop_token, semaphore, latch, barrier), the engineering practices that take code from “correct” to “maintainable and measurable,” and finally a shutdown-capable concurrent task processor that computes squares.

To keep cross-references consistent, chapter and example numbering continues from Part I: this installment begins with Chapter 8 and Example 15, and references to Part I material are marked “Part I.”

8. Atomics: Establish the Boundaries Before Discussing Memory Order

8.1 A Single Atomic Operation Is Not an Atomic Business Transaction

std::atomic<T> provides operations that cannot be subdivided for eligible types. Integer atomics commonly use load, store, exchange, and fetch_add. fetch_add returns the value prior to modification and performs the read, add, and write as a single atomic read-modify-write.

The commonly used operations are listed below. The corresponding overloads of load, store, exchange, fetch_*, and CAS let you specify a memory order explicitly; when it is omitted, the default is seq_cst. Operator forms always use seq_cst and accept no memory-order argument. Lock-free capability queries do not involve memory order (§8.3):

OperationSemanticsReturns
load()Atomically read the current valueThe value read
store(v)Atomically write a valueNone
exchange(v)Atomically replace the valueThe previous value
fetch_add(n) / fetch_sub(n)Atomic addition / subtraction (eligible integer and pointer types; C++20 also supports floating-point specializations)The value before modification
operator++ / operator+= etc.Shorthand for the corresponding fetch operationPrefix ++ returns the value after modification; postfix ++, like fetch_add, returns the value before modification
compare_exchange_weak/strong(expected, desired)Replace with desired only if the value still equals expected (§8.7)Whether it succeeded; on failure expected is updated to the observed value
is_lock_free() / is_always_lock_freeQuery whether this object / type has a lock-free implementationThe answer at runtime / compile time

The assignment operator performs a store with the default memory order and returns the value written, while implicit conversion performs a load with the default memory order; consequently count = count + 1 still involves two separate operations, a read and a write, with the same problem as the faulty snippet below. C++20 also offers atomic wait / notify_one / notify_all; their absence in older TDM-GCC environments is noted in Part I §2.2, and this article avoids them to keep the examples coherent. The specification for types and operations appears in the C++20 draft’s atomic generic types.

/**
 * @file example15.cpp
 * @brief A std::atomic<int> counter: fetch_add is a single, indivisible atomic read-modify-write.
 * @details Two jthreads each increment 10000 times using the default seq_cst memory order;
 *          the final value is read after joining. Expected output: 20000. See §8.1.
 */
#include <atomic>   // std::atomic
#include <cassert>  // assert: verify the final count
#include <iostream> // std::cout
#include <thread>   // std::jthread

/**
 * @brief Program entry point: atomic accumulation without lost updates.
 * @return Implicitly returns 0.
 */
int main() {
    std::atomic<int> count{0}; // Atomic counter: each operation is indivisible, no mutex needed
    /** @brief The worker accumulates via atomic read-modify-write; the referenced count outlives both threads. */
    auto add = [&] {           // Capture count by reference; its lifetime spans both threads
        for (int i = 0; i < 10000; ++i) {
            count.fetch_add(1); // Default seq_cst; read, add, and write are merged into one atomic read-modify-write
        }
    };
    {
        std::jthread first(add);  // Both threads run the same accumulation task concurrently
        std::jthread second(add); // The second thread accesses the same atomic counter
    } // join/reap: thread completion synchronizes with the main thread's subsequent read
    const int result = count.load(); // Read after both threads finish; default seq_cst
    assert(result == 20000);         // Atomic read-modify-write guarantees no lost updates
    std::cout << result << '\n';     // Output: 20000
}

Multiple atomics likewise do not automatically form a transaction. If two account balances are each atomic and you debit A before crediting B, an observer may see the total decrease between the two steps—even when every operation uses the default memory order. Guarding the shared invariant with a lock is usually easier to maintain than designing a multi-variable lock-free protocol.

Atomic objects, too, must be constructed before publication and destroyed only after no one accesses them. atomic<T> is not available for arbitrary T and does not guarantee lock-free operation for every type; you can check is_lock_free() or is_always_lock_free. Some types and targets require linking libatomic explicitly; the small-integer examples here have no such requirement.

8.2 happens-before: The Links in a Correctness Proof

The memory model is not a programming interface for “flushing some level of cache.” It specifies which executions and observations are permitted; the compiler and hardware are responsible for realizing them.

First, distinguish three relationships:

  • sequenced-before: Within a single thread, the ordering established by the rules of evaluation; you cannot infer the order of just any expression from the way it is written.
  • synchronizes-with: A cross-thread synchronization edge designated by the standard, such as from an unlock to a subsequent lock, or from thread completion to a join returning.
  • happens-before: The ordering formed by joining intra-thread sequencing with cross-thread synchronization. This article does not use consume, so you can reason along these links and their transitive closure.

Figure 8-1: A complete synchronization chain (using the publication in Example 16 as an illustration). In thread A, sequenced-before links “write payload” to the release store; the release and the acquire load that reads that value form a synchronizes-with edge; adding the sequenced-before within thread B yields “write payload happens-before read payload.” The synchronization edge between an unlock and a subsequent lock works the same way.

Modification order is the total order formed by all modifications to a given atomic object; every thread must respect that object’s atomicity and coherence constraints. Distinct atomic objects each have their own modification order, and these do not automatically combine into a single global order—a property that holds even with relaxed.

Seeing an operation “appear to have happened first” in real time does not establish happens-before; sleep_for(), log output, and the number of CPU cores are none of them the proof you need. Lock-free code in particular cannot infer cross-platform correctness from the observed behavior of a single x86 machine.

8.3 What Each Memory Order Is Responsible For

Memory orderMain roleGood starting point
seq_cstRetains the corresponding acquire/release effects and provides a single total order over all seq_cst operations, subject to the standard’s constraintsThe default choice
releasePublishes prior operations within a matching synchronization relationshipA store that publishes a ready state
acquireReceives published operations within a matching synchronization relationshipA load that observes a ready state
acq_relBoth acquires and releasesA read-modify-write that needs synchronization in both directions
relaxedGuarantees this atomic access and the object’s modification order, without publishing other dataStandalone counters with no publication duty
consumePropagates publication along data dependencies, with rules more intricate than acquireDiscouraged by the standard since C++17 (formally deprecated in C++26); ordinary code should avoid it

C++20 defines six memory orders in all, whose full names are std::memory_order_relaxed, std::memory_order_consume, std::memory_order_acquire, std::memory_order_release, std::memory_order_acq_rel, and std::memory_order_seq_cst. consume has long been difficult to implement and use correctly; mainstream implementations usually treat it as acquire, and it is formally deprecated in C++26, so this article avoids it. load cannot use release or acq_rel; store cannot use consume, acquire, or acq_rel.

Release and acquire synchronize only when they actually connect: they must operate on the same atomic object, and the acquire must read the value written by the corresponding release—or a value from the release sequence that begins with it. Any two operations bearing those two words do not automatically pair up.

This article uses a single publication to avoid such complexity. In C++20, a release sequence is the longest contiguous subsequence in an object’s modification order that begins with a release operation and is followed entirely by atomic read-modify-writes; inserting an ordinary atomic store truncates it, whereas a plain load is not a modification and does not truncate it. The older textbook claim that “an ordinary atomic store by the same thread can extend the sequence” no longer applies (proposal P0982R1 deliberately narrowed this definition—a breaking change to the old rule, so code that relied on the removed extension loses its synchronization guarantee). The precise rules appear in C++20 memory order.

/**
 * @file example16.cpp
 * @brief The acquire/release publication protocol: safely publishing ordinary (non-atomic) data with a pair of memory-order operations.
 * @details The producer writes payload first, then stores ready with release; the consumer reads true with acquire,
 *          forming a synchronizes-with edge with the release, and then safely reads payload.
 *          Expected output: 42. See §8.4.
 */
#include <atomic>   // std::atomic / std::memory_order_release / std::memory_order_acquire
#include <cassert>  // assert: verify the data read
#include <iostream> // std::cout
#include <thread>   // std::jthread / std::this_thread::yield

/**
 * @brief Program entry point: demonstrates the chain 'write data → publish flag → observe flag → read data'.
 * @return Implicitly returns 0.
 */
int main() {
    int payload = 0;                // Ordinary data: protected by ready's publication protocol, not atomic itself
    std::atomic<bool> ready{false}; // Publication flag: false → true happens only once
    /** @brief The producer writes payload once, publishes with release, and never overwrites it afterward. */
    std::jthread producer([&] {
        payload = 42;                                 // ① Write the data first (sequenced-before ② within the thread)
        ready.store(true, std::memory_order_release); // ② release publication: the write in ① becomes visible together with the flag
        // payload is not modified after publication; this example delivers it once.
    });

    while (!ready.load(std::memory_order_acquire)) { // ③ acquire observation: reading true pairs and synchronizes with ②
        std::this_thread::yield(); // Merely a scheduling hint; the real synchronization comes from the acquire that reads true
    }
    const int value = payload; // Deliberately placed before join, relying on the publication protocol for safety (the ①→②→③→④ chain)
    producer.join();           // Reap the thread; here only for lifetime management, since synchronization is already established by the publication protocol
    assert(value == 42); // Verify the read of ordinary data protected by the acquire publication chain
    std::cout << value << '\n'; // Output: 42
}

The proof has three steps:

  1. The write to payload is sequenced-before the release store within the thread.
  2. The initial value is false and only the producer writes true, so an acquire that reads true must have observed that publication.
  3. That acquire is sequenced-before the read of payload, linking the whole into a happens-before chain, so the ordinary integer’s write and read do not race.

The weaker memory orders here are used to expose the synchronization edge, not as measured performance advice; keeping the default seq_cst is equally correct. When real waiting times may be long, use a condition variable; busy-waiting and yield promise neither fairness nor bounded response time. C++20 also offers atomic wait/notify, whose absence in older toolchains is recorded in Part I §2.2; this article continues to use condition variables for a uniform waiting protocol.

You cannot turn a one-shot publication protocol into repeated transfers simply by clearing ready back to false: the producer might overwrite the data while the consumer is still reading the old value. Multi-round handoffs need an additional acknowledgement, mutual exclusion, or a queue protocol.

8.5 What seq_cst Guarantees—and What It Does Not

If a program has no data races and all relevant atomic operations use seq_cst, you can reason as if all atomic operations were interleaved in a single global order consistent with each thread’s sequencing. This total order is not a lock around the whole function, does not guarantee that several loads form a snapshot at one instant, and says nothing about real-time scheduling or about reading the “latest” value at some wall-clock moment.

For example, with x and y initially 0 and both threads using seq_cst:

1
2

Thread A: x.store(1) → rA = y.load()
Thread B: y.store(1) → rB = x.load()

You cannot get rA == 0 and rB == 0 at the same time: that would require each load to be ordered before the other thread’s store, forming an impossible cycle together with the intra-thread ordering. With relaxed, such an outcome is permitted; and even with release stores and acquire loads, reading the initial 0 fails to connect to the other thread’s publication, so the outcome still cannot be ruled out.

Once weak memory orders are mixed with seq_cst, you can no longer apply the “global interleaving” picture to every operation; the formal constraints are finer. Without a concrete performance requirement, keeping the default order is easier to prove correct than weakening operations piecemeal. seq_cst will not repair unprotected ordinary data accesses, dangling references, or a business operation that has been split apart.

8.6 When relaxed Is Already Enough

If Example 15 needs only an independent count whose final value is read after all threads join, you can change its fetch_add and final load to relaxed: the atomic read-modify-write prevents lost updates, join handles synchronization after thread completion, and the counter itself publishes no other business data.

This is a correctness argument, not a promise of speed; whether the change is worthwhile requires measurement. Do not generalize it into “once the count reaches N, you can directly read N ordinary results”: if you treat the counter as a readiness signal, data publication needs a separate proof.

8.7 CAS: Replace It If It Has Not Changed

CAS stands for compare-and-swap and is provided in C++ by compare_exchange_weak/strong. Understanding expected is the key: it is both an input and a value that may be modified.

OutcomeAtomic objectexpected
Success, returns trueWrite desiredRetains the value used for this comparison
Failure, returns falseNo write performedUpdated to the atomic value just observed

weak permits spurious failure: it may report failure even when the values compare equal, which is why it is usually placed in a loop. strong has no such spurious failures, but it still fails when another thread changes the value. A CAS comparison does not call a custom operator==; this article uses simple integers to avoid complications with exotic representations.

/**
 * @file example17.cpp
 * @brief A CAS retry loop: decrement stock atomically only when it is positive, demonstrating correct use of expected/desired.
 * @details Two threads compete to decrement 100 units of stock; on failure compare_exchange_weak automatically
 *          updates expected to the value just observed, and the target is recomputed each round, so the stock never
 *          goes negative and the total is conserved. Expected output: 100 (how much each thread gets is nondeterministic). See §8.7.
 */
#include <array>    // std::array: a separate counting slot per thread
#include <atomic>   // std::atomic
#include <cassert>  // assert: verify conservation of the total
#include <iostream> // std::cout
#include <thread>   // std::jthread

/**
 * @brief Attempt to decrement stock by one atomically.
 * @param[in,out] stock The shared stock; an atomic object, safe for concurrent access.
 * @retval true This decrement took effect.
 * @retval false Stock was already zero; nothing was decremented.
 * @note Each loop iteration rechecks the precondition against the latest expected and recomputes the target.
 * @warning Do not place non-repeatable side effects such as payments or notifications inside the loop (see the retry side-effect discussion in §8.7).
 */
bool take_one(std::atomic<int>& stock) {
    int expected = stock.load(); // First guess: start from whatever value we read
    while (expected > 0) {       // Precondition check: attempt a decrement only while positive
        // Compute the target from the latest expected each round; the default memory order keeps the argument simple.
        if (stock.compare_exchange_weak(expected, expected - 1)) {
            return true; // Success: stock changed from expected to expected - 1 at precisely this instant
        }
        // Failure updates expected; once stock is zero, the loop condition exits on the next iteration.
    }
    return false; // Stock exhausted
}

/**
 * @brief Program entry point: two threads compete to consume; verify conservation of the total.
 * @return Implicitly returns 0.
 */
int main() {
    std::atomic<int> stock{100}; // Shared stock
    std::array<int, 2> taken{};  // taken[i] is written only by thread i, so no extra synchronization is needed
    /** @brief Repeatedly decrement stock. @param index This thread's exclusive array slot, 0 or 1 here. */
    auto consume = [&](int index) {
        while (take_one(stock)) {
            ++taken[index]; // Each thread modifies only its own element
        }
    };
    {
        std::jthread first(consume, 0);  // index is passed into the thread by value
        std::jthread second(consume, 1); // The second thread writes only taken[1]; stock is shared through CAS
    } // join/reap both threads
    assert(stock.load() == 0);              // Stock is exactly used up
    assert(taken[0] + taken[1] == 100);     // Total is conserved: neither more nor less
    std::cout << taken[0] + taken[1] << '\n'; // Output: 100
}

The output is 100; how much each thread gets is nondeterministic. A successful CAS is the only moment at which a decrement takes effect: the write of expected minus one happens only while the value still equals a positive expected, so the stock never goes negative.

The fix is to recheck the precondition and recompute desired on every round, as in Example 17. The retry body must not perform non-repeatable side effects such as payments or notifications; those belong after the operation succeeds.

When you supply explicit memory orders, CAS has a success order and a failure order: success is a read-modify-write, failure is only a read, so the failure order cannot be release or acq_rel. The old precondition that “the failure order must not be stronger than the success order” was removed in C++17 and should not be treated as a C++20 rule; the success order applies to the read-modify-write, while the failure order must still be a valid order for a read. In practice, use a combination you know and have proved correct, such as acq_rel/acquire or release/relaxed; here the defaults suffice and no manual pairing is needed. The single-order overload adjusts the failure order automatically: acq_rel maps to acquire and release maps to relaxed. The precise rules appear in C++20 atomic operations.

CAS does not imply that the whole algorithm is lock-free, still less that a given thread cannot starve. If a value goes A→B→A, a CAS may not notice the intervening change—the ABA problem. With pointers you must also handle object reclamation and dangling accesses. Do not jump from this integer example straight to writing your own lock-free linked list.

A common remedy for ABA is the tagged pointer: compare and update the pointer together with a version number as a single atomic object. When the value goes A → B → A, CAS detects the change as long as the version has not wrapped. Tags have finite bits and can wrap, so you must prove that a tag is not reused while an older observation is still in use. Updating a plain counter and an atomic pointer separately does not provide this guarantee; the availability of wide CAS, whether it is lock-free, and pointer-bit encoding all depend on the implementation, so do not assume 64-bit machines support it automatically.

Detecting ABA and managing object lifetime are separate matters. Ownership through shared_ptr can extend an object’s lifetime, but the shared-pointer variables themselves still require synchronization, and reference counting cannot be generalized into a cure for every logical ABA. Hazard pointers prevent premature reclamation by publishing the node being accessed and rechecking it; epoch reclamation waits until old visitors have passed a safe epoch before freeing nodes. Both require a complete reclamation protocol and neither automatically resolves A → B → A in arbitrary business state. This section only delineates the boundaries; it does not implement a lock-free list.

/**
 * @brief A minimal spin-lock protocol demonstrated with an atomic flag.
 * @note The lock must be constructed before any user and destroyed after all users; suitable only for very short critical sections.
 * @warning Non-recursive, with no fairness guarantee; a lock-free atomic flag does not make this lock's algorithm lock-free.
 */
class SpinLock {
public:
    /** @brief Busy-wait until exclusive ownership is acquired; a successful acquire receives writes published by the previous holder's release. */
    void lock() {
        while (flag_.test_and_set(std::memory_order_acquire)) { // A previous value of true means the lock is already held
            std::this_thread::yield(); // A scheduling hint; does not ensure the holder runs and does not provide synchronization
        }
    }
    /** @brief Publish the critical section's writes and release the lock. @pre The calling thread holds this lock. */
    void unlock() {
        flag_.clear(std::memory_order_release); // A subsequent successful acquire synchronizes with this release
    }
private:
    std::atomic_flag flag_{}; ///< false means free; since C++20 default construction clears it (the old ATOMIC_FLAG_INIT form still works but is no longer needed)
};

In use, manage it with a named std::lock_guard<SpinLock> so that exceptional paths cannot forget to unlock. While the holder is preempted, waiters keep burning CPU, and heavy contention also generates cache-coherence traffic. Single-core systems, excessive threads, slow I/O, long critical sections, and blocking operations all make this kind of spin lock a poor fit; a plain std::mutex is usually better. C++20’s atomic_flag::test() can observe the flag without changing it; atomic waiting is a different implementation of waiting, whose support should be probed on the target toolchain.

9. C++20 Cancellation and Coordination Facilities

9.1 Cooperative Cancellation: Request, Check, Exit Safely

Cancellation does not mean forcibly cutting a thread short from the outside. A thread may be holding a lock, updating several fields, or managing a file resource; killing it abruptly would leave a half-finished state.

C++20 provides a set of handles over a shared stop state:

  • stop_source: owns the ability to issue a stop request, via request_stop().
  • stop_token: observes the request via stop_requested(); can be copied to related tasks.
  • stop_callback: registers a callback to run when a request occurs.

A jthread carries its own stop source. If the thread function can accept an injected token, the jthread passes it as the first argument. A request is one-shot: you cannot reset the same stop state back to “no request”; a fresh round of work normally needs a fresh state.

Figure 9-1: The data flow of cooperative cancellation. A request is written into the shared stop state; a task polls the token at safe points or responds passively through a stop_callback. Both paths require the thread to do its own cleanup before exiting.

Long computations should check the token at sensible safe points, for example after processing each batch. Checking too rarely hurts responsiveness; checking too often can add overhead. Plain sleep_for(), blocking I/O, and condition_variable::wait() do not wake up merely because the token has been requested.

 * @brief Program entry point: cancel a thread that is waiting (or has not yet begun to wait).
 * @return Implicitly returns 0.

int main() {
    std::mutex mutex;               // Guards work_ready and cancelled
    std::condition_variable_any cv; // Interruptible waits require the _any overloads
    bool work_ready = false;        // Never becomes ready here: this example only demonstrates the cancellation path
    bool cancelled = false;         // Written by the worker, read by the main thread (synchronized by join)

    /** @brief Wait for work or a stop inside the worker. @param token The handle observing the shared stop state, injected by jthread. */
    std::jthread worker([&](std::stop_token token) { // jthread automatically injects the stop token as the first argument
        std::unique_lock<std::mutex> lock(mutex); // Acquire the mutex; it can be released and reacquired during wait
        // Predicate false and not stopped → wait; a stop request → wake, recheck, and return the predicate's current value.
        /** @brief Check the business condition while holding the mutex. @return work_ready; a stop by itself does not make this predicate true. */
        const bool has_work = cv.wait(lock, token, [&] { return work_ready; });
        if (!has_work) {
            // The return value reflects the predicate; since no work was published, false means we are exiting due to the stop.
            cancelled = true; // Record the reason for exiting inside the critical section
            return;
        }
    });
    worker.request_stop(); // Even if called before the thread starts waiting, the stop state is not lost
    worker.join();         // Wait for the thread to respond to the stop and exit
    assert(cancelled); // After join, verify the worker responded to the stop and exited
    std::cout << "cancelled\n"; // Output the verified cancellation result for this example
}

The output is cancelled. work_ready stays false throughout; only the worker writes cancelled, and the main thread reads it after join. When a stop request and the predicate are both true, the wait result is still decided by the predicate; a real queue must specify whether to “drain pending work first” or give “stop priority”—you cannot infer business policy from a single bool. The definition of interruptible waits appears in C++20 condition_variable_any.

A stop_callback may run synchronously in the thread that calls request_stop(); if a stop was already requested at registration time, the callback runs immediately in the registering thread before registration returns. Destroying a callback can also block waiting for that callback to finish executing in another thread, and destroying it while holding a lock the callback needs can deadlock. Keep callbacks short and never let them throw (an exception escaping a callback calls std::terminate()), and do not request a stop while holding a lock the callback requires, or you may deadlock. Prefer the standard wait overloads above, which avoid hand-assembled callback protocols prone to lost notifications.

A jthread’s destructor requests a stop and then joins, but it can still hang when: the function never checks the token; the thread is blocked on an operation that does not support cancellation; or exiting requires a lock currently held by the destructor. With multiple interdependent jthreads, you should generally request a stop from every thread first, then join them one by one, rather than relying on sequential destructors to untangle mutual waits.

9.3 semaphore: Holding a Count of Permits

Condition-variable notifications do not accumulate; a semaphore holds a permit count. acquire() waits while the count is zero, otherwise decrementing it; release() adds permits and gives waiters a chance to proceed. binary_semaphore suits handoffs with at most one permit, while counting_semaphore<N> handles multiple permits—N is a lower bound on the required maximum, and should not be misread as an exact ceiling for every implementation.

A semaphore has no thread ownership as a mutex does, so one thread may acquire and another release. It suits limiting how many tasks use a resource concurrently or signalling how many items are available; it does not automatically protect an arbitrary container structure. You must not release beyond the allowed maximum count, waiters are not guaranteed fairness, and try_acquire() permits spurious failure.

 *          respectively, and the count always stays between 0 and 1. Expected output: 6. See §9.3.

#include <iostream>  // std::cout
#include <semaphore> // std::binary_semaphore (C++20; requires a recent standard library implementation)

/**
 * @brief Program entry point: bounded single-slot handoff.
 * @return Implicitly returns 0.
 */
int main() {
    std::binary_semaphore empty(1); // Slot-empty permit: the slot starts empty, so the producer may write once
    std::binary_semaphore full(0);  // Slot-full permit: initially there is no data to read
    int slot = 0;                   // Shared single slot: protected by the two semaphores' permit protocol, no mutex needed
    int sum = 0;                    // Consumer-private total, read by the main thread after join

    /** @brief The consumer reads after acquiring the slot-full permit, and permits overwrite only after returning the slot-empty permit. */
    std::jthread consumer([&] {
        for (int i = 0; i < 3; ++i) {
            full.acquire();  // Acquire the 'slot-full' permit: synchronizes with the producer's release, making slot readable
            sum += slot; // The slot-full permit ensures the data is published and the consumer exclusively reads this round's value
            empty.release(); // Return the 'slot-empty' permit only after reading, allowing the producer to overwrite the slot
        }
    });
    for (int value = 1; value <= 3; ++value) {
        empty.acquire(); // Acquire the 'slot-empty' permit: ensures the previous round's data has been consumed
        slot = value; // The slot-empty permit ensures the previous round was read, so the producer writes exclusively
        full.release();  // Publish slot so the consumer's matching acquire can safely receive it
    }
    consumer.join(); // Reap the consumer; reading sum afterward is guaranteed synchronized
    assert(sum == 6); // 1 + 2 + 3
    std::cout << sum << '\n'; // Expected output: 6
}

The expected output is 6. The two directions of handoff prevent “reading before the write completes” and “overwriting before the read completes,” respectively, keeping the count between 0 and 1. One semaphore cannot express both ownership transfers. Multi-producer, multi-consumer queues also involve shared state such as slot indices, which should be guarded by a separate lock.

For real resource permits, use a scope guard to ensure they are returned even on exceptions; here the slot holds only integer operations that throw no business exceptions. The standard rules appear in C++20 semaphore.

9.4 latch: A One-Shot Completion Set

    std::jthread first([&] {

    });
    /** @brief The second thread writes its exclusive element then reports arrival; ready outlives the thread. */

        ready.count_down(); // Publish the second result and decrement the latch count

}

The expected output is 42. A latch waits for a progress point, not necessarily thread exit, so threads still need reaping. This example does not modify the results after decrementing. #include <iostream> // std::cout
#include <thread>   // std::jthread

/**
 * @brief Program entry point: the main thread is also a participant, so only one extra worker is created.
 * @return Implicitly returns 0.

int main() {

    std::barrier<> phase(2); // The main thread is also a participant, so only one extra thread is created
    /** @brief Each round the worker writes its element; the two rendezvous points protect the write and the read, respectively. */
    std::jthread worker([&] {
        for (int round = 1; round <= 3; ++round) {
            values[1] = 2 * round; // The worker fills in its result for this round; reading is allowed only in the next phase
            phase.arrive_and_wait(); // First phase: rendezvous once both sides have finished writing this round
            phase.arrive_and_wait(); // Second phase: wait until the main thread finishes reading before overwriting the next round
        }
    });
    int total = 0; // Main-thread-private total
    for (int round = 1; round <= 3; ++round) {
        values[0] = round; // The main thread writes only its own slot, then rendezvouses with the worker
        phase.arrive_and_wait();        // Rendezvous ①: both values for this round are written
        total += values[0] + values[1]; // Safely read both values between the two rendezvous points
        phase.arrive_and_wait();        // Rendezvous ②: the worker may enter the next round only after the read completes
    }
    worker.join(); // Reap the thread
    assert(total == 18); // (1+2) + (2+4) + (3+6) = 18
    std::cout << total << '\n'; // Expected output: 18
}

The expected output is 18. The second barrier cannot be dropped casually: otherwise the worker might already be writing the next round’s values[1] while the main thread still reads the previous one, creating a data race. The barrier’s phase synchronization and participant constraints appear in C++20 coordinating types.

arrive() only reports arrival, decrements this phase’s count, and returns an arrival token without waiting for other participants; you can then do work that does not depend on the phase’s completion and later call wait(std::move(token)) to await that phase. The token must come from the current or immediately preceding phase of the same barrier. arrive_and_wait() combines the two steps. The completion function runs in a participating thread chosen as the standard permits—you cannot assume it is always the main thread; the end of the completion step strongly happens-before the return of any wait call unblocked by that phase’s completion, so phase results can be delivered safely.

Participants cannot leave unannounced; when a participant will not take part in later phases, use arrive_and_drop() as the protocol requires to reduce the expected count for the current and subsequent phases. A stop request does not automatically remove a participant from a barrier, so cancellation and phase exit must be designed together.

10. From a Correct Program to a Maintainable, Measurable One

10.1 Task Decomposition Matters More Than Thread Count

Identify independent work first, then choose the execution resources. Prefer tasks that only read their inputs and write outputs they own, merging at the end. Multiple threads modifying different elements of a plain array is usually fine, but they must not change the container’s structure at the same time; the bit-packed representation of vector<bool> is an exception that deserves special vigilance.

std::thread::hardware_concurrency() returns a hint about the number of hardware threads that can run concurrently—possibly the logical core count, possibly 0—and says nothing about the current quota or the optimal thread count. Provide a sensible fallback for 0 and cap the thread count at the number of meaningful tasks. Empty jobs should simply return.

When you need per-thread state, thread_local gives each thread its own instance of a variable, eliminating sharing at the source: typical uses are per-thread accumulators, caches, or random-number engines. Instances are destroyed as their threads exit. It is a tool for avoiding sharing, not for making shared data safe—handing a pointer or reference to a thread_local object to another thread still requires you to handle synchronization and the lifetime of the owning thread’s exit. In a thread pool, its lifetime follows the thread rather than the task, so successive tasks reuse the same state. For one-shot tasks like Part I’s Example 5, an ordinary local variable inside the lambda is enough; if you use per-thread accumulators, you must explicitly hand a copy to the reducer before the thread exits—the main thread cannot read another thread’s instance through a thread_local variable of the same name.

For CPU-bound work, start measuring with a number of worker threads close to the available hardware resources; heavy blocking I/O may call for a different strategy. The C++20 standard library offers no general-purpose asynchronous network I/O or ready-made thread pool, and you cannot solve every scenario by creating threads without limit.

False sharing occurs when different threads modify different variables that happen to share a cache line, increasing cache-coherence traffic. It may involve no data race yet still hurt performance. Per-thread local accumulation, less frequent writes, and padding hot data apart when necessary can all help.

Cache locality refers to the tendency to reuse recent or adjacent data. Giving each thread a contiguous range usually helps locality more than chasing pointers at random, but the actual gain must be measured. Blindly padding every object inflates memory usage and can damage locality; likewise, do not assume the cache line size is always 64 bytes.

10.4 The Boundaries of std::execution

Since C++17, some standard algorithms accept execution policies such as std::execution::par, but a policy is not a command to “use N cores.” An implementation may choose to execute serially; parallel implementations may also need an extra back end—some libstdc++ configurations use TBB—so the default compile command cannot be promised to yield parallel execution. This article does not cover back-end configuration or demonstrate parallel speedup. See libstdc++’s execution-policy linkage requirements.

10.5 How to Verify and Measure

Correctness checks come before performance testing: first write down ownership, lock-protected ranges, and exit conditions, then run small deterministic result checks, vary the task count, exercise error paths, and repeat runs. Logging changes scheduling, so it can only help locate problems—it cannot prove an ordering.

On supported platforms, ThreadSanitizer can detect some data races. It cannot prove the absence of logical races, deadlocks, or dangling-lifetime problems; you can build separately in a supported GCC/Clang environment, for example:

When measuring performance, use identical inputs and optimization levels, compare against a serial baseline first; either include or explicitly exclude the costs of thread creation, enqueueing, and merging; use the monotonic steady_clock for time intervals; measure repeatedly and inspect the distribution, recording hardware, thread count, and load. Do not print logs inside the timed hot path. The examples in this article do no timing and claim no real speedup; more threads are not automatically faster.

10.6 Concurrent Testing Is a Set of Protocols

Check deterministic results and invariants first, then vary the number of workers, producers, consumers, and tasks. Shared statistics in tests must also be synchronized—let each thread write an exclusive slot, then aggregate after join. Schedule test progress with promise/future, latch, or a lock-protected predicate; sleep_for() only perturbs scheduling and cannot tell you another thread has finished.

Stress tests should record the random seed and inputs: the same seed reproduces the inputs but not necessarily the thread scheduling. Running 100, 500, or more iterations only raises the chance of finding a bug; a program with a data race need not produce a wrong value, and a faulty relaxed publication need not fail on x86. A happens-before proof must be written separately for memory ordering.

Deadlocks, unsatisfied futures, and close failures should be guarded by timeouts in a separate process; do not leave a thread that may block forever inside the grader’s process. Timeout reports should distinguish a wait failure from a build failure. Cover task exceptions, empty work, invalid inputs, repeated closes, repeated construction and destruction, and the acceptance boundary when shutdown and submit race. CMake handles portable builds, CTest registers behavior tests with timeouts, and Python orchestrates compilation, repeated runs, seeds, and grading; assertions are not a complete grading system.

Tool-based detection is supplementary evidence. TSan finds some data races; AddressSanitizer checks some out-of-bounds and use-after-invalid accesses. Build them separately, first probing whether compilation, linking, and running actually work, and report SKIP explicitly when unsupported. Passing tests, clean sanitizer runs, and a correctness proof are three distinct kinds of evidence. Official TSan documentation

11. Complete Example: A Shutdown-Capable Concurrent Squaring Task Processor

11.1 Requirements and Design Constraints

This section implements a small batch processor: the main thread submits integer tasks, a fixed number of workers pull tasks from a shared queue, and compute their squares. Each task returns its own future, and the caller retrieves results in submission order.

It must meet the following requirements:

  1. Every accepted task is taken exactly once, and computation runs outside the queue lock.
  2. Inputs are restricted to 0 through 1000; invalid inputs propagate invalid_argument through the future without killing the worker.
  3. Once submission ends, the main thread closes the queue; no new tasks are accepted, accepted tasks are all processed, and waiters on the empty queue exit.
  4. Workers are managed by jthread. If thread creation or submission fails, the queue must still be closed so already-started threads can exit before the exception is propagated.
  5. Test empty input, a single thread, multiple threads, valid and invalid tasks; reject zero workers.

This design uses drain-on-close: closing forbids new tasks but still processes accepted ones. Discarding queued tasks on shutdown is a different contract, requiring an explicit decision about how the futures of discarded tasks are satisfied; it should not be folded into the same ambiguous switch.

/**
 * @file example22.cpp
 * @brief A shutdown-capable concurrent squaring task processor (task queue + future result channel).
 * @details The main thread submits integer tasks; a fixed set of jthread workers pull tasks from a shared queue
 *          and compute their squares outside the lock; each task returns its own future; closing drains accepted
 *          tasks and lets waiters exit. Expected output: "all batch checks passed". See §11.
 */
#include <cassert>            // assert: cover every requirement
#include <condition_variable> // std::condition_variable
#include <cstddef>            // std::size_t
#include <future>             // std::packaged_task / std::future
#include <iostream>           // std::cout
#include <mutex>              // std::mutex / std::lock_guard / std::unique_lock
#include <queue>              // std::queue
#include <stdexcept>          // std::invalid_argument / std::logic_error
#include <thread>             // std::jthread
#include <utility>            // std::move
#include <vector>             // std::vector

/**
 * @brief A shutdown-capable task queue: submitters enqueue, workers dequeue, and closing drains then exits.
 * @details All shared state is guarded by the same mutex_; the wait predicate is
 *          "closed_ || !tasks_.empty()", ensuring waiters observe closure and exit.
 * @note The queue must be constructed before the threads that reference it; close it and reap all threads before destroying it.
 * @warning The close semantics are drain-on-close: accepted tasks are all processed, not discarded (see §11.1).
 */
class TaskQueue {
public:
    using Task = std::packaged_task<int()>; ///< Task type: takes no arguments, yields an int result

    /**
     * @brief Submit an integer squaring task.
     * @param input Business input, valid in [0, 1000]; captured by value into the task, decoupling it from the caller.
     * @return The future associated with this task; both its value and its exception are retrieved through it.
     * @throws std::logic_error to reject new tasks when the queue is closed.
     * @note Enqueueing happens inside the critical section, notification after unlocking; the future must be obtained before the task is enqueued.
     */
    std::future<int> submit(int input) {
        /** @brief The squaring computation run by a worker, capturing a copy of input. @return The squared value. @throws std::invalid_argument for out-of-range input, stored by the packaged_task. */
        Task task([input] {
            // The range check both expresses the business rule and avoids signed integer multiplication overflow.
            if (input < 0 || input > 1000) {
                throw std::invalid_argument("input must be in [0, 1000]");
            }
            return input * input; // Range checked, so the square fits in int; stored by the packaged_task
        });
        auto result = task.get_future(); // Obtain the sole read handle before the task is moved into the queue
        {
            std::lock_guard<std::mutex> lock(mutex_); // The same lock guards the queue and closed_; released automatically on scope exit
            if (closed_) {
                throw std::logic_error("queue is closed"); // No tasks accepted after closure
            }
            tasks_.push(std::move(task)); // The queue becomes the sole owner of the task
        }
        cv_.notify_one(); // After unlocking, notify one waiter: a task is available
        return result; // Return the future by move; the shared state is kept alive jointly by task and future
    }

    /**
     * @brief Take one task; wait on the predicate when empty, and report exit when closed and empty.
     * @param[out] task On success, move-assigned the front task; on false it is left as passed in (possibly a valid, already-executed task, not necessarily default-invalid).
     * @retval true A task was obtained; the caller should execute it outside the lock.
     * @retval false The queue is closed with no tasks left; the worker should exit its loop.
     * @note The lock is released atomically while waiting and reacquired before taking the task.
     * @warning A true predicate does not mean a task exists: closed_ also satisfies it, so you must recheck whether the queue is empty.
     */
    bool take(Task& task) {
        std::unique_lock<std::mutex> lock(mutex_); // Hold the queue lock to check state; wait needs to unlock and relock
        /** @brief Check exit-or-take conditions under mutex_. @return Closed or a task is available. */
        cv_.wait(lock, [this] { return closed_ || !tasks_.empty(); });
        if (tasks_.empty()) {
            return false; // The predicate holds and the queue is empty, so it must be closed
        }
        task = std::move(tasks_.front()); // The worker takes ownership of the front task; the old task's state association is released on assignment
        tasks_.pop(); // Removal happens in the same critical section, so no two threads can take the same task
        return true; // Report success; on return the lock is destroyed first, then the caller runs the task
    }

    /**
     * @brief Close the queue: forbid new tasks and wake all waiters to drain and exit.
     * @note Idempotent: repeated calls do not change the contract. The state change is under the lock, notification outside it.
     */
    void close() {
        {
            std::lock_guard<std::mutex> lock(mutex_); // The same lock guards the queue and closed_; released automatically on scope exit
            closed_ = true; // Idempotent: repeated closes do not change the drain contract
        }
        cv_.notify_all(); // Give every waiter a chance to exit, including those that did not get a task
    }

private:
    std::mutex mutex_;           ///< The single lock guarding all members below
    std::condition_variable cv_; ///< The waiting facility paired with mutex_
    std::queue<Task> tasks_;     ///< Unexecuted tasks; accessible only under mutex_
    bool closed_ = false;        ///< Close flag; together with tasks_ forms the wait predicate
};

/**
 * @brief Run a batch of squaring tasks: create the worker group, submit all inputs, close, and wait for the whole batch.
 * @param inputs All inputs; empty input returns an empty result list immediately.
 * @param worker_count Number of workers; throws if zero, and is reduced to the task count if it exceeds it.
 * @return A list of result futures in submission order; all are ready when the function returns.
 * @throws std::invalid_argument when worker_count == 0.
 * @note A blocking batch interface: it waits for the whole batch before returning; the futures' shared state outlives the queue.
 * @warning If thread creation or submission fails, close first to let existing threads exit, then propagate the exception.
 */
std::vector<std::future<int>> run_batch(const std::vector<int>& inputs,
                                       std::size_t worker_count) {
    if (worker_count == 0) {
        throw std::invalid_argument("worker_count must be positive");
    }
    std::vector<std::future<int>> results; // The main thread owns the result handles in submission order
    if (inputs.empty()) {
        return results; // Empty input: create no threads and return an empty list
    }
    if (worker_count > inputs.size()) {
        worker_count = inputs.size(); // Never more threads than tasks
    }
    results.reserve(inputs.size()); // Reserve capacity to avoid reallocation in push_back

    TaskQueue queue; // Construct the shared object before the thread container that references it
    std::vector<std::jthread> workers; // Owns the workers; on exception unwinding it is destroyed before queue
    workers.reserve(worker_count); // Reserve capacity to avoid moving jthreads during growth
    try {
        for (std::size_t i = 0; i < worker_count; ++i) {
            /** @brief Worker entry point: repeatedly take tasks and run them outside the queue lock, exiting once closed and drained. */
            workers.emplace_back([&queue] {
                TaskQueue::Task task; // A default-constructed empty task, move-assigned by take
                while (queue.take(task)) {
                    // take has released the queue lock; exceptions from user computation are stored by the packaged_task.
                    task(); // Execute outside the lock: a slow task cannot hold the queue lock indefinitely
                }
            });
        }
        for (int input : inputs) {
            results.push_back(queue.submit(input)); // Submit one by one and save the result handles
        }
        queue.close(); // Submission complete: close the queue and enter the drain phase
    } catch (...) {
        // If creating the k-th thread or allocating a task fails, first let existing threads exit.
        // Exception unwinding then destroys workers, reaping each thread, before destroying queue.
        queue.close(); // Failure cleanup: wake existing threads so they drain and exit instead of waiting forever
        throw;
    }
    for (auto& worker : workers) {
        worker.join(); // Without holding the queue lock; returns after all accepted tasks are processed
    }
    return results; // The futures' shared state lives on independently of the destroyed tasks and queue
}

/**
 * @brief Program entry point: check the requirements of §11.1 one by one.
 * @return Implicitly returns 0.
 */
int main() {
    assert(run_batch({}, 2).empty()); // Empty input: return an empty result list

    for (std::size_t count : {std::size_t{1}, std::size_t{3}, std::size_t{8}}) {
        auto results = run_batch({0, 2, 3, 1000}, count); // Includes a case with more threads than tasks
        const std::vector<int> expected{0, 4, 9, 1000000}; // Expected squares matching the submission order one-to-one
        for (std::size_t i = 0; i < results.size(); ++i) {
            assert(results[i].get() == expected[i]); // Results are retrieved in submission order
        }
    }

    auto mixed = run_batch({2, -1, 3, 1001}, 2); // Valid and invalid inputs mixed
    assert(mixed[0].get() == 4); // The result for valid input 2 is unaffected by other tasks' failures
    assert(mixed[2].get() == 9); // The task for valid input 3 still runs
    for (std::size_t i : {std::size_t{1}, std::size_t{3}}) {
        bool rejected = false; // Record separately whether each invalid task reported an exception
        try {
            (void)mixed[i].get(); // Invalid input: invalid_argument is rethrown through the future
        } catch (const std::invalid_argument&) {
            rejected = true; // Confirm this get propagated that task's business exception
        }
        assert(rejected); // This invalid input must report failure through its future
    }

    bool zero_rejected = false; // Record whether the zero-worker configuration was rejected
    try {
        (void)run_batch({1}, 0); // Zero workers must be rejected
    } catch (const std::invalid_argument&) {
        zero_rejected = true; // Confirm the invalid configuration was rejected before any thread was created
    }
    assert(zero_rejected); // Verify no batch is created that no one will ever consume

    TaskQueue closed; // Create a separate queue for checking the close contract
    closed.close(); // Close the empty queue once; all later submissions must be rejected
    closed.close(); // Repeated close: idempotent, does not change the contract
    bool submit_rejected = false; // Record whether a post-close submission is rejected
    try {
        (void)closed.submit(1); // A submission after close must be rejected
    } catch (const std::logic_error&) {
        submit_rejected = true; // Confirm submit synchronously threw the queue-closed exception
    }
    assert(submit_rejected); // Verify no new task was accepted after close
    TaskQueue::Task unused; // A default-invalid output task, used to test take on a closed, empty queue
    assert(!closed.take(unused)); // Closed and empty: take reports exit
    std::cout << "all batch checks passed\n"; // Print the completion message after all assertions pass
}

The output is all batch checks passed. run_batch is a blocking batch interface: the internal tasks run concurrently, but the function waits for the whole batch before returning, so the returned futures are already ready. The futures are kept to show that each task stores its own success or exception; you cannot call this interface an “asynchronous submission service that returns immediately.”

11.3 Design and Thread-Safety Rationale

Figure 11-1: Components and data flow of the task processor. Submission, task retrieval, and closing all pass through the same queue lock; computation and result delivery happen outside the lock.

Ownership: the main thread holds the result handles; the queue holds unexecuted tasks; a worker gains exclusive execution rights by moving a task out. The lambda captures the integer by value, never referring to a temporary in the caller. packaged_task is non-copyable, preventing a task from being accidentally duplicated.

Shared state: only the task queue and the close flag need a mutex. Every access to these two pieces of state happens under the same lock. The result state is synchronized by the packaged_task/future protocol, so the queue lock need not protect results.

Waiting and synchronization: submission enqueues under the lock and notifies after unlocking. Workers check the predicate under the lock, release it atomically while waiting, and can take a task only after reacquiring it. The close flag is persistent state, so even if close happens before a thread prepares to wait, the thread observes the closed state when it checks under the lock; it then drains remaining tasks, confirms the queue is empty, and exits. Task execution happens outside the critical section, so a slow task cannot hold the queue lock indefinitely.

Draining: a true predicate does not mean exit immediately. Only an empty queue yields false; if closed but tasks remain, the worker keeps taking them. The move and pop under the lock form one protected removal, so each task is handed to exactly one worker.

Lifetime: the normal path joins explicitly; the error path closes first, then lets the destruction of workers reap the threads, and only finally destroys the queue. No join is performed while holding the lock. Here workers do not accept a stop_token, so the stop request issued by a jthread’s destructor does not affect the drain contract; thread exit depends on the queue’s closed state.

Exceptions: invalid inputs are captured automatically by packaged_task, so later tasks still run. Allocation failures during thread creation or submission enter the cleanup path. This example does not try to recover from severe runtime failures such as the synchronization primitives themselves becoming invalid, nor can it guarantee shutdown of arbitrary user tasks that never return; its computation tasks are integer operations with a finite number of steps.

Result order: completion order is nondeterministic, but the main thread stores and reads the futures in submission order, so the output interface does not depend on scheduling. The internal shared state survives queue destruction and is held by the futures until get retrieves the result.

11.4 Directions for Improvement

Keep these correctness foundations in place, then extend according to real requirements:

  • Turn the unbounded queue into a bounded one: add a “not full or closed” predicate with matching notifications; closing must wake both producers and consumers.
  • For a service that returns immediately, put the queue and workers into a long-lived object with explicit submit, close, and join contracts; never return threads that reference a destroyed local queue.
  • When adding cooperative cancellation, distinguish “stop accepting and drain” from “cancel unexecuted tasks.” The latter must define the exception or cancellation result for each unexecuted future and have long computations check the stop state at safe points.
  • Measure throughput and latency at task granularity before deciding whether to enqueue in batches, reduce wake-ups, or reuse result buffers.

A long-lived service also needs a clear contract: submit enqueueing and the close-state transition use the same lock to fix the acceptance boundary; tasks enqueued before close must complete, while submissions after close are rejected synchronously. shutdown() closes, wakes, and waits for all workers; repeated and concurrent shutdowns require separately serialized reaping—you cannot join the same jthread concurrently. Never join while holding the queue lock.

A worker calling a shutdown that would wait for that same worker is self-waiting; reject such calls and document that pool tasks must not wait on subtasks queued in the same pool. Destruction belongs to a single owner, and external submit/shutdown calls must have finished first; concurrent destruction and member calls are outside the service’s protocol. General tasks can use packaged_task<int()> to stay within this article’s scope: movable callables are allowed, with values and exceptions delivered through the future; drain-on-close requires user tasks to eventually return, while cooperative cancellation is a separate contract.

Do not add priorities, work stealing, and lock-free queues all at once; each increases the state and exit paths you must prove.

12. Summary

Looking back over the whole series, here are engineering practices to check against when writing concurrent code:

  • Minimize shared mutable state first; read inputs only, keep outputs independent, merge at the end.
  • Default to RAII, use jthread where it fits; never let a thread outlive an object it references.
  • For every group of shared data, document the lock that guards it and the business invariant; reads must follow the protocol too.
  • Give lock-managing objects a name; keep critical sections short but complete; use a safe locking scheme for multiple locks; do not hold a business lock while waiting on tasks.
  • Design condition variables around a shared predicate; on close, change state first, then notify, and reap last.
  • Make explicit who satisfies each asynchronous state, who calls get, and when the last reference is released; exceptions must have a recipient too.
  • Use seq_cst as the atomic default; before weakening a memory order, write the synchronization proof and confirm a real need to optimize.
  • Cancellation must cover both compute and wait paths; do not expect destructors, timeouts, or stop requests to forcibly interrupt work.
  • Bound concurrent resources and queue growth; avoid unbounded thread creation and nested waits.
